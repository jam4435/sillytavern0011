# 事件推进研究协议

仅在用户要求研究多轮剧情、事件完成轮数、连续性、跨事件接续或变量正确性时读取并执行。

## 研究目标

必须回答适用项：当前事件在哪一轮开始收束、在哪一轮正式结算；正文首次偏航或停滞轮次；当前事件未结束前是否提前进入后续事件；后续事件能否在正确时间、地点和状态下接续；正文结束与变量结算是否同步；变量错误轮次、类型和比例；参与事件快照是否提前写入角色数据；最终差分、人物经历、关系、位置、参与事件和人物占用是否正确。

## 轮数与执行

1. 用户指定轮数时，将其作为本次检测上限；没有指定时使用 30 轮上限。不要改成自适应批次，也不要擅自增加轮数。
2. 每次只发送一轮，随后立即做紧凑输出审计。未发现明显问题且未达到上限时再发送下一轮。
3. 到达上限、当前研究目标已有结论，或发现明显问题时停止新增回合并报告。只有用户明确要求“错误后继续”时才继续，并使用 `--continue-on-error` 收集后续故障。
4. 跨多个报告文件时保持全局轮次连续，不把每个文件的 `turn: 1` 当成研究第1轮。

## 实验基线

发送前读取目标事件定义、结束时间、地点、参与人物、预设结局与差分，以及下一事件自己的触发时间和地点。生成一次 `--stat-data-snapshot` 保存基线，但只读取这些目标路径：世界时间、进行中/已完成事件、参与事件、人物事件占用、事件结局状态、参与人物位置、经历及关系。若基线已经污染，停止并报告，不能把后续结果当成纯净实验。

## 每轮阶梯式审计

### 第一级：结果

先运行 `scripts/summarize-ui-report.mjs`，只看 `reply`、四区状态、失败区、变量输出摘要和关键错误。检查正文是否承接上一轮、是否仍围绕当前事件、时间与剧情阶段是否相称、是否提前跳场或进入后续事件；检查变量块是否提前写事件经历、路径是否错误、是否应用和持久化成功。没有问题就进入下一轮，不读取完整输入。

### 第二级：对应输入

- 正文异常：先看 `main-output` 原文；需要归因时才读 `main-input`，检查事件详情、COT、当前参与事件和后续线索是否正确注入。
- 变量异常：先看 `variable-output` 的原始返回、合法块、应用与错误；需要归因时才读 `variable-input`，检查当前变量投影、路径存在性、参与事件规则和 `VariableThink` 判断。
- 输入缺失或错误归为提示词/投影问题；输入正确而输出违反规则归为模型遵循问题。

### 第三级：目标变量

输入仍不能解释、调试声称成功但结果矛盾、需要检查隐藏状态时，再生成快照并只读可疑路径。不要默认展开全量 `stat_data`。

## 明显问题停止条件

发现任一项即停止新增回合并报告：正文无玩家明确干涉却明显脱离当前事件；当前事件未收束便正式演出后续事件；正文出现倒退、跳时、瞬移或连续性断裂；main/variable 阶段 `error`，变量 API 空回复、JSON/路径/解析失败或持久化失败；参与事件尚未结束却按回合写入该事件人物经历；事件结算缺失、重复、提前，或参与事件/人物占用出现明确矛盾。轻微措辞差异、合理局部互动和数分钟误差不单独视为明显问题。

## 事件边界检查

正文出现收束、时间到达结束边界、参与事件消失或下一事件出现时，生成一次快照并只读目标路径。分别判定：正文完成轮次、变量正式结算轮次、下一事件开始轮次。核对完成标记、世界事件归档、进行中和参与事件移除、人物占用释放、预设或偏离差分只应用一次，以及下一事件满足自己的时间和地点。

## 报告格式

先给结论，再列逐轮表：全局轮次、正文状态、事件阶段/时间、变量状态、异常。最后汇总事件完成轮数、首次偏航、连续性、跨事件接续、变量失败率、提前经历写入和最终结算；注明实际执行轮数、停止原因、报告文件与快照文件。不要用 runner 的 `success` 代替语义正确性。
