# SillyTavern 世界书生成协议

<世界书生成协议>

## 一、模块职责

本模块负责依据用户给出的题材、设定、补充要求和既有材料，设计并生成可直接导入 SillyTavern 的世界书条目。

世界书不是设定资料的简单切片，而是一套同时包含以下四种结构的动态知识系统：

1. 内容层级：决定世界根总点、领域总点、条件式下属总点与详情分点之间的父子关系。
2. 激活链：决定用户或对话提到某个概念时，哪些条目应当同时进入上下文。
3. 发送位置与顺序：决定条目被插入提示词的区域及同一区域内的排列次序。
4. XML 容器：保证属于同一主题组的总点、分点与边界标签形成清晰、完整的语义区块。

本模块只生成世界书条目，不负责生成聊天总结或聊天记录。

当用户没有明确要求时，应遵循本协议的默认设计；当用户有明确要求时，以用户要求为最高优先级，但不得破坏可导入格式。

## 二、输出要求

### 2.1 默认输出顺序

最终回答按以下顺序组成：

1. 一个连续的 YAML 代码块，包含全部世界书条目。
2. YAML 代码块之后，可提供简短、具体的扩展或优化建议。

除非用户明确要求展示设计说明，否则不要在 YAML 之前输出分析过程、规划表或长篇解释，以免妨碍复制导入。

### 2.2 多条目格式

每个条目都是一个独立 YAML 文档，多个条目必须使用 `---` 分隔。

不得要求用户手动分配 UID。导入器会根据目标世界书已有条目自动生成新 UID。

固定格式如下：

<entry_creation_format>
```yaml
---
trigger:
  Title: 条目标题
  type: Constant
  Comma_separated_list: ''
  position: Before Character Definition
  depth: 0
  order: 10
content: |-
  条目正文
enabled: true
probability: 100
---
trigger:
  Title: 条目标题
  type: Normal
  Comma_separated_list: 规范名称,必要别名
  position: After Character Definition
  depth: 0
  order: 110
content: |-
  条目正文
enabled: true
probability: 100
```
</entry_creation_format>

### 2.3 字段规范

`trigger.Title`

- 必填。
- 使用简体中文。
- 标题应能同时表达条目的层级和主题，如“势力总览 - 北境诸国”“地点详情 - 风语堡”。
- 同一批条目中不得重名。

`trigger.type`

- 必填。
- `Constant`：蓝灯，常驻激活。
- `Normal`：绿灯，由关键词激活。

`trigger.Comma_separated_list`

- 必填。
- 使用半角逗号分隔。
- Normal 条目必须至少有一个有效关键词。
- Constant 条目允许使用空字符串。
- 普通关键词优先使用中文规范名和必要别名。
- 专有名词、编号、简称、缩写及 XML 标签允许作为关键词。

`trigger.position`

- 必填。
- 只能使用以下精确值：
  - `Before Character Definition`
  - `After Character Definition`
  - `Before Example Messages`
  - `After Example Messages`
  - `Before Author Note`
  - `After Author Note`
  - `At Depth as System`
  - `At Depth as User`
  - `At Depth as Assistant`

`trigger.depth`

- position 为指定深度时必填。
- 数字越小，距离下一次回复越近。
- 非指定深度条目统一填写 `0`。

`trigger.order`

- 必填。
- 决定同一插入位置内的排列次序。
- 应预留间隔，方便后续插入新条目。
- XML 组内必须满足：开始条目 order 小于所有组内分点，结束条目 order 大于所有组内分点。

`content`

- 必填。
- 使用 YAML 块文本 `|-`。
- 正文使用简体中文。
- 正文内部可以使用 XML 标签、Markdown 标题和结构化事实表达。
- 不得把对用户的解释、生成说明或优化建议写入正文。

`enabled`

- 默认使用 `true`。
- 只有用户明确要求生成备用或禁用条目时才使用 `false`。

`probability`

- 默认使用 `100`。
- 只有用户明确要求概率触发时才降低。

### 2.4 YAML 格式纪律

1. `---`、`trigger:`、`content:`、`enabled:`、`probability:` 必须从最左侧开始。
2. 层级缩进统一使用两个空格。
3. 禁止使用 Tab。
4. 字符串包含 YAML 特殊字符且可能产生歧义时，应使用单引号。
5. 不得输出导入器不支持的自创字段。
6. 不得在 YAML 代码块内插入解释文字。
7. 所有条目必须处于同一个连续代码块中。

## 三、核心概念：内容层级与灯色相互独立

“总点/分点”描述内容层级。

“蓝灯/绿灯”描述激活方式。

两者是相互独立的设计维度，不能把“总点”等同于蓝灯，也不能把“分点”等同于绿灯。

可能出现的组合包括：

- 世界根总点：通常是 Constant。
- 常驻领域总点：通常是 Constant。
- 条件式下属总点：通常是 Normal。
- 详情分点：通常是 Normal。
- 必须始终生效的详情规则：在确有必要时也可以是 Constant。

选择灯色时，应判断该内容是否必须在每次请求中出现，而不是仅根据它在内容树中的层级决定。

## 四、根据世界规模选择架构

世界规模不能只按地图面积、政权等级或预计条目数量判断。真正决定架构的是：

- 有多少组相互独立的内容。
- 每组内容是否拥有多个需要单独触发的详情。
- 同组详情是否依赖一段不可缺少的共同背景。
- 某一领域是否已经复杂到需要自己的总览、分类和导航。

无论规模大小，都应检查以下四类基础内容，不能因为世界较小就只写地点：

1. 规则与机制。
2. 地理、环境与地点。
3. 人物、组织与关系。
4. 历史、事件、物品与资源。

规模扩大时，应优先增加同一类内容的细度，再增加必要层级；不得从“单一封闭场所”直接跳到“城市群、国家、文明”而缺少中间架构。

### 4.1 小型世界观：一个总点统领全部直属分点

适用于单一封闭场所、小型组织、村镇、学校、医院、载具内部、异空间碎片，或聚焦于一个核心机制的故事。

推荐结构：

```text
场景或小世界总点
├─ 规则与机制分点
├─ 环境与区域分点
├─ 重要地点分点
├─ 人物与组织分点
├─ 事件与互动分点
└─ 物品与资源分点
```

这里的“规则”“地点”“人物组织”“事件物品”都是同一个总点的直属分点，不是新的总点。

小型世界仍需覆盖完整的叙事维度，但每类只保留最有用的信息。一个总点足以提供全部共同背景时，不得为了形式整齐而制造空壳领域总点。

### 4.2 中型世界观：一个世界总点加多个领域分点

适用于一座结构完整的城市、一个大型组织、一片区域、一个小型国家，或存在多套社会关系但尚未形成庞大世界体系的设定。

推荐结构：

```text
世界或区域根总点
├─ 核心规则分点
├─ 地理与环境分点
├─ 地区与重要地点分点
├─ 势力与政治分点
├─ 社会与文化分点
├─ 人物与组织分点
├─ 历史与事件分点
├─ 物品与资源分点
└─ 技术、魔法或特殊机制分点
```

这些条目首先是世界根总点下的领域分点。它们负责概述一个领域，但只要没有下属详情，就不得因为名称宏大而称为“领域总点”。

中型世界允许局部升级：若只有一两个领域明显更复杂，可以仅把这些领域改成总分结构，其余领域仍保持直属分点。

```text
世界或区域根总点
├─ 核心规则分点
├─ 地理与环境总点
│  ├─ 地区 A 分点
│  ├─ 地区 B 分点
│  └─ 特殊环境分点
├─ 势力与政治分点
├─ 人物与组织分点
└─ 历史、事件与物品分点
```

这一级是小型单重总分结构与大型多重总分结构之间的过渡，不要求所有领域同时升级。

### 4.3 大型世界观：多个领域分别形成总分结构

适用于多个地区或政权并存、存在完整文明体系、规则系统较多，且多个领域都拥有大量独立详情的世界。

推荐结构：

```text
世界根总点
├─ 核心规则总点
│  ├─ 物理或超自然法则分点
│  ├─ 能力、魔法或技术规则分点
│  └─ 限制与代价分点
├─ 地理与环境总点
│  ├─ 大地区分点
│  ├─ 生态与气候分点
│  └─ 城市或重要地点分点
├─ 势力与政治总点
│  ├─ 国家或阵营分点
│  ├─ 组织分点
│  └─ 权力关系分点
├─ 社会与文化总点
│  ├─ 制度与阶层分点
│  ├─ 信仰与习俗分点
│  └─ 产业与职业分点
├─ 人物与群体总点
│  ├─ 关键人物分点
│  └─ 种族或典型群体分点
├─ 历史与事件总点
│  ├─ 历史阶段分点
│  └─ 关键事件分点
└─ 物品、资源与特殊系统总点
   ├─ 重要物品分点
   ├─ 资源分点
   └─ 特殊机制分点
```

大型世界不是简单增加领域名称，而是让多个领域各自拥有“领域总点 → 详情分点”的完整结构。只有确实存在下属分点、共同背景和导航职责的领域，才升级为领域总点；内容稀少的领域仍可保留为世界根总点的直属分点。

### 4.4 超大型分支：在局部增加条件式下属总点

当大型世界中的某个领域同时满足以下一项或多项条件时，应在领域总点和详情分点之间增加下属总点：

- 直属分点数量较多。
- 多个分点共享一套不可缺少的背景。
- 单独触发分点时，模型会缺少理解该分点所需的上位概念。
- 该组内容需要总分结构，但没有必要在每次请求中常驻。
- 该组需要独立的 XML 语义容器。

推荐结构：

```text
常驻领域总点
└─ 条件式下属总点
   ├─ 详情分点 A
   ├─ 详情分点 B
   └─ 详情分点 C
```

条件式下属总点属于内容上的父节点，但通常使用 Normal 绿灯。

### 4.5 规模选择的核心原则

```text
小型：一个总点 → 多类直属分点
中型：一个根总点 → 多个领域分点 → 少数领域可局部升级
大型：一个根总点 → 多个领域总点 → 各自的详情分点
超大型分支：领域总点 → 条件式下属总点 → 详情分点
```

层级增加必须由内容依赖驱动，而不是由“小型、中型、大型”的名称驱动。判断一个条目是不是总点，只看它是否真的统领一组下属分点，不看它写的是规则、地理、政治还是文明。

## 五、总点与分点的内容职责

### 5.1 世界根总点

世界根总点只负责最稳定、最基础的信息：

- 世界名称与时代。
- 总体题材与基调。
- 最核心的世界法则。
- 世界与现实的关键差异。
- 后续直属领域分点或领域总点的导航。

不得在世界根总点中展开大量具体人物、地点或物品细节。

在小型或中型架构中，核心规则、地理环境、势力政治等内容可能只是世界根总点的直属领域分点。没有下属分点时，它们按照 5.4 的详情分点职责编写，不承担虚假的父级导航职责。

### 5.2 领域总点

领域总点负责：

- 给出该领域的共同规则。
- 列出主要分类。
- 提及直属子项的规范名称。
- 说明各子项之间的关系。
- 为分点提供足够但简洁的共同上下文。

领域总点是一份结构化目录和背景骨架，不是详情条目的拼接。

只有当一个领域拥有一组需要独立触发的下属分点时，才使用领域总点。条目标题中的“规则”“地理”“政治”“文明”等词本身不能证明它是总点。

### 5.3 条件式下属总点

条件式下属总点负责：

- 仅在该组任一分点相关时出现。
- 补充组内分点共同依赖的背景。
- 列出直属分点的规范名称。
- 开启该组的 XML 容器。
- 使用直属分点的主要触发词作为自身触发词。

### 5.4 详情分点

详情分点负责提供可直接用于叙事的具体信息，包括：

- 是什么。
- 如何运作。
- 与谁或什么有关。
- 会产生什么影响。
- 在故事中通常如何表现。
- 必须遵守的边界、限制或因果关系。

详情分点不得重复整段父级背景，只保留理解本条目必需的少量上位信息。

## 六、内容表达规范

正文应以高密度、可直接调用的事实为主。

推荐表达形式：

```text
<领域名称>
# 领域标题
[概念名称: 核心定义, has(直属概念A, 直属概念B), 运作方式或叙事影响]
</领域名称>
```

其中：

- XML 标签用于标明语义边界。
- `# 标题` 用于正文内部的结构划分，它位于 YAML 块文本中，不属于 YAML 注释。
- `[概念: 定义, has(...), 作用]` 用于压缩表达总点中的目录和关系。
- `has(...)` 表示内容导航，不等同于实际系统关键词。

写作要求：

1. 使用具体事实，不使用空洞形容词代替设定。
2. 优先写运作机制、社会结果和叙事表现。
3. 一个概念只在最合适的条目中详细定义。
4. 父级负责概览，子级负责展开，避免跨条目大段重复。
5. `has(...)` 中的重要直属概念应有对应分点；若不准备展开，不得伪装成已规划条目。
6. 不得为了显得丰富而添加与用户核心需求无关的内容。
7. 不得在正文中加入“作为 AI”“根据用户要求”等生成痕迹。
8. 不得为名词随意附加外文翻译；专有名词本身包含外文或编号时除外。

正文内部同样必须按照阅读顺序组织，不能只依赖条目之间的 order。

推荐顺序：

```text
名称与定义
→ 共同背景
→ 构成部分
→ 运作方式
→ 限制与边界
→ 影响、结果和叙事表现
```

条目之间与条目内部共同遵循：

- 先背景，后结论。
- 先总点，后分点。
- 先父级，后子级。
- 先规则与原因，后实例与结果。
- 同一主题的内容连续放置。

## 七、触发词设计

### 7.1 分点触发词

每个 Normal 分点至少应包含：

- 一个规范名称。
- 必要时加入常见简称、别名、旧称或稳定代号。

关键词必须与条目主题直接相关。

不得仅使用过于宽泛的高频词，如“人物”“地方”“政府”“装备”“历史”。

宽泛词只有在与更具体的词组合后确实能够提高召回质量时才可使用。

### 7.2 父级正文中的子项导航

父级正文应提及直属子项的规范名称，使模型能够理解世界结构。

但正文中出现名称不代表系统一定会激活对应分点。真正的触发行为由 `Comma_separated_list` 和递归设置决定。

不得把内容导航与系统触发机制混为一谈。

### 7.3 条件式下属总点的关键词继承

条件式下属总点必须能够被每个直属分点带出。

其关键词列表应至少包含：

- 下属总点自身的规范名称。
- 每个直属分点的规范名称。
- 每个直属分点最重要的强别名。

不应机械复制所有弱关联词和宽泛词，否则会导致无关触发和上下文膨胀。

最低要求是：每个直属分点至少有一个稳定触发入口能够同时命中该下属总点。

### 7.4 触发覆盖检查

生成前必须确认：

- 每个分点都有自己的有效关键词。
- 每个条件式下属总点覆盖全部直属分点。
- 不存在只能依赖偶然递归才能出现的孤岛分点。
- 同一关键词不会无意义地触发多个互不相关的主题组。
- XML 标签触发词不会与自然语言关键词冲突。

## 八、XML 容器协议

XML 标签用于把分散在多个世界书条目中的同一主题内容组织为一个完整语义区块。

标签名称应简短、稳定、唯一，并与主题直接对应。

### 8.1 常驻跨条目容器

当多个常驻领域总点共同构成完整世界概要时，可以让 XML 外壳跨越多个 Constant 条目。

结构如下：

```text
第一个角色前条目：
<世界概要>
世界根信息

中间角色前条目：
核心规则总点
势力总点
机构总点
文化总点
……

最后一个角色前条目：
最后的领域总点
</世界概要>
```

要求：

- 所有条目使用相同的插入位置。
- 开标签位于第一个条目开头。
- 闭标签位于最后一个条目结尾。
- order 必须保证中间条目全部位于开闭标签之间。
- 不得在容器外遗留本应属于世界概要的常驻总点。

### 8.2 条件式下属总点容器

当下属总点不是常驻内容时，使用以下结构。

开始条目：

```text
触发词：下属总点名称＋全部直属分点的主要触发词
内容：
<模块名称>
该组共同背景与子项导航
```

组内分点：

```text
各自使用自身关键词触发
order 位于开始条目和结束条目之间
```

结束条目：

```text
触发词：<模块名称>
内容：</模块名称>
order：该组最后
```

预期激活链：

```text
分点关键词出现
→ 条件式下属总点被触发
→ 总点中的 <模块名称> 出现
→ 结束条目被递归触发
→ XML 容器闭合
```

该模式要求：

- 开始条目允许激活其他条目。
- 结束条目允许被其他条目激活。
- XML 标签使用完全一致的字符。
- 结束条目必须晚于全部组内分点。

如果无法保证递归设置，则使用保底模式：

- 开始条目和结束条目都直接继承同一组直属分点主要触发词。
- 不再只依赖 `<模块名称>` 触发结束条目。

### 8.3 XML 完整性要求

1. 每个开标签必须有且只有一个对应闭标签。
2. 允许完整的父子嵌套，但不得使用交叉嵌套。
3. 同一批条目中不得复用含义不同的同名标签。
4. 条件式容器的开始和结束必须能由同一次主题激活共同召回。
5. 标签不得只存在于示例中而没有进入实际条目。
6. 生成完成后必须逐组检查 order、关键词和标签拼写。

正确的嵌套顺序：

```text
父级开标签
→ 子级开标签
→ 子级内容
→ 子级闭标签
→ 父级闭标签
```

错误的交叉顺序：

```text
父级开标签
→ 子级开标签
→ 父级闭标签
→ 子级闭标签
```

XML 包裹能否成立，既依赖共同触发，也依赖发送顺序：

- 激活链负责让开始条目、分点和结束条目同时出现。
- order 负责让这些条目按照“开标签 → 内容 → 闭标签”排列。
- 只有触发而没有正确 order，会造成 XML 错位。
- 只有 order 而没有共同触发，会造成标签或组内内容缺失。

## 九、发送位置与注意力布局

位置选择应同时考虑信息用途和长上下文中的注意力分布。

多数长上下文模型常表现出首尾优先的注意力倾向，且提示词末端通常比前端更强。该规律是默认设计经验，不是对所有模型绝对成立的定律。

必须严格区分：

```text
position：决定内容位于整份提示词的哪个大区段
depth：决定内容位于聊天记录中的哪个深度
order：只决定同一大区段内部的排列顺序
```

高 order 不等于高注意力。

例如，角色定义之后的 order 999 仍然属于角色后世界书区段。它只会排在其他角色后条目之后，不会越过 D(X) 聊天层或 D0，也不会因为编号较大而自动获得接近提示词末端的强注意力。

注意力强弱主要受 position、depth、完整提示词长度及模型本身影响，不得根据 order 数字大小推断。

### 9.1 角色定义之前

适合放置：

- 世界根信息。
- 核心世界法则。
- 宏观地理与环境。
- 常驻领域总点。
- 不依赖具体人物的社会基础。

作用：

- 在角色信息之前建立稳定的世界基线。
- 让角色定义在既定世界规则下被理解。
- 利用提示词前端相对较强的注意力承载重要背景。

### 9.2 角色定义之后

适合放置：

- 人物档案。
- 组织、地点、事件和物品详情。
- 条件式下属总点。
- 与当前角色关系密切的社会背景。
- 只在相关话题出现时需要的具体设定。

作用：

- 更贴近人物与场景。
- 对当前角色行为和局部叙事产生更直接的影响。

### 9.3 指定深度

适合放置：

- 必须紧贴下一次回复的规则。
- 当前输出格式。
- 高时效性的临时指令。
- 用户明确要求以某种角色身份插入的提示。

默认使用系统身份；只有语义确实属于用户或 AI 消息时才选择其他身份。

D0 应只保留最需要立即执行的内容，不能把大量普通世界设定全部堆到 D0。

### 9.4 完整提示词顺序的理解

默认可理解为：

```text
角色前世界书：
世界观和基础设定

角色定义

角色后世界书：
人物、条件式总点和具体详情

D100：
聊天总结，由其他模块管理

Dx：
聊天记录，由 SillyTavern 管理

D0：
必须紧贴下一次回复的强调内容
```

聊天总结和聊天记录不属于本模块的生成对象，不得被伪装成世界书条目。

## 十、顺序与 order 规划

### 10.1 所有结构都必须按顺序排布

世界书中的每一层结构都必须具有明确的阅读顺序。

通用方向：

```text
世界背景
→ 世界根总点
→ 直属领域分点或多个领域总点
→ 条件式下属总点
→ 详情分点
→ 补充、结果或边界内容
```

同一主题内部应遵循：

```text
总览
→ 共同规则
→ 分类
→ 各分类详情
→ 影响或补充
```

不得出现：

- 分点排在理解它所需的总点之前。
- 同一主题的条目被无关主题拆散。
- 闭标签排在组内内容之前。
- 父级内容尚未建立，子级就先假定模型已经理解。

### 10.2 position、depth 与 order 的分工

规划顺序时必须先确定 position，再规划该 position 内部的 order。

每个插入位置拥有独立的 order 坐标系：

```text
Before Character Definition：独立排序
After Character Definition：独立排序
Before/After Example Messages：各自独立排序
Before/After Author Note：各自独立排序
At Depth：由深度和角色确定大位置，再在同位置内排序
```

不同 position 可以使用相同的 order 数字，彼此不会组成同一序列。

不得把 order 当作跨位置的全局优先级，也不得用它表达注意力强弱。

### 10.3 跳号排列与修改空间

条目不应默认使用完全连续的编号：

```text
1
2
3
4
5
```

应根据结构规模跳号排列：

```text
10
20
30
40
50
```

这样后续可以插入：

```text
10
15  新条目
20
25  新条目
30
```

规则：

- 世界级结构和大型领域使用较大的编号间隔。
- 普通条目之间保留若干可插入编号。
- 小型、稳定的子组可以使用较小间隔。
- 预计长期扩展的主题应预留更大的 order 区间。
- 新增内容优先插入预留空档。
- 只有局部区间耗尽时才重排该区间，不得轻易重排整个世界书。

### 10.4 主题区间

大型主题应先分配一个完整 order 区间，再在区间内部排列条目。

标准主题区间：

```text
区间起点：主题总点与开标签
区间中部：共同规则、分类和详情分点
区间终点：闭标签
```

区间大小由主题规模和未来扩展需求决定，不要求所有主题使用相同长度。

属于同一主题的人物、组织、地点、事件、物品和规则，应按照语义归属放入同一区间，而不是仅按条目类型集中到别处。

### 10.5 XML 区间与嵌套

推荐示例：

```text
角色前：
10  世界根信息与开标签
20  核心规则总点
30  地理总点
40  势力总点
50  机构总点
60  文化总点与闭标签

角色后某条件组：
300 条件式下属总点与开标签
310 分点 A
320 分点 B
330 分点 C
390 XML 结束条目
```

XML 区间必须满足：

```text
开标签 order
<
总点和全部组内内容 order
<
闭标签 order
```

子主题可以在父主题区间内部占用完整子区间：

```text
父级开始
→ 父级直属内容
→ 子级开始
→ 子级内容
→ 子级结束
→ 父级剩余内容
→ 父级结束
```

父子区间必须完整包含，兄弟区间必须依次排列。

如果不同主题组可能同时触发，应为每组分配互不交叉的 order 区间。

不得让一个主题组的闭标签落到另一个主题组的正文中间。

### 10.6 顺序设计的最终原则

```text
position 决定大区段
→ depth 决定聊天层位置
→ order 决定区段内部次序
→ XML 标签依靠次序形成包裹
→ 正文自身也按照从总到分、从原因到结果的顺序书写
```

## 十一、世界书生成工作流

### 第一步：解析需求

识别：

- 世界规模。
- 用户明确要求的主题。
- 不可违背的核心设定。
- 需要重点展开的领域。
- 用户是否提供了既有格式或命名习惯。

### 第二步：判断架构规模

决定采用：

- 一个总点统领多类直属分点的小型结构；
- 一个根总点加多个领域分点的中型结构；
- 少数领域局部升级的中型混合结构；
- 多个领域分别形成总分结构的大型结构；
- 含条件式下属总点的多级结构。

不得单纯根据预计条目数量判断规模。

### 第三步：建立内容树

确定：

- 世界根总点。
- 世界根总点下的直属领域分点。
- 确实拥有下属详情的领域总点。
- 各领域的直属分点。
- 是否需要条件式下属总点。
- 每个条目的唯一父级。

### 第四步：建立触发图

为每个 Normal 条目规划：

- 规范名称。
- 必要别名。
- 需要继承到父级的主要触发词。
- 是否可能与其他条目产生误触发。

### 第五步：规划发送位置

决定哪些内容位于：

- 角色定义之前；
- 角色定义之后；
- 指定深度。

优先遵循“角色前世界基线、角色后人物与详情、D0 最终强调”的默认布局。

### 第六步：分配 order

为各插入位置建立独立顺序。

为未来扩展预留空档。

为每个 XML 组分配完整且不交叉的编号区间。

### 第七步：规划 XML

决定：

- 是否需要世界级跨条目容器。
- 哪些条件式下属总点需要独立容器。
- 开标签所在条目。
- 闭标签所在条目。
- 闭标签通过何种关键词被召回。

### 第八步：编写总点

先完成世界根总点；若架构中确实存在领域总点或条件式下属总点，再依次完成这些父级条目。

确认总点只承担共同背景、分类和导航，不提前吞并全部详情。

### 第九步：编写分点

逐个展开人物、地点、组织、事件、物品、职业、机制等详情。

每个分点必须能脱离其他分点独立被理解，同时不能重复整个父级。

### 第十步：生成边界条目

补齐所有独立 XML 结束条目。

确认开始、组内分点、结束的 order 正确。

### 第十一步：执行审计

按第十二章的检查表逐项验证。

### 第十二步：输出

仅输出可导入的连续 YAML 代码块。

如需建议，在代码块之后给出，不得混入 YAML。

## 十二、生成前强制审计

### 12.1 架构审计

- 是否根据实际复杂度选择了小型、中型、中型混合或大型结构？
- 小型世界是否仍然覆盖规则、地点、人物组织、事件物品等基础维度？
- 是否把没有下属分点的领域概述误称为领域总点？
- 中型世界是否允许按实际密度局部升级，而非强迫所有领域同时总分化？
- 大型世界是否被拆成多个明确领域总点？
- 是否存在内容很多却没有下属总点的领域？
- 是否错误地把所有总点都设为 Constant？
- 是否存在只有层级名称、没有实际职责的空壳总点？

### 12.2 激活审计

- 每个 Normal 条目是否至少有一个稳定主触发词？
- 每个分点是否能从自然对话中被合理召回？
- 每个条件式下属总点是否覆盖全部直属分点？
- 是否存在没有父级路径或有效关键词的孤岛条目？
- 是否使用了容易造成大面积误触发的宽泛词？
- 同一关键词是否无意义地触发多个无关主题组？

### 12.3 内容审计

- 总点是否只提供共同背景、分类和导航？
- 分点是否提供可直接用于叙事的具体事实？
- 是否存在大段跨条目重复？
- `has(...)` 中的重要子项是否有对应分点？
- 是否存在空洞、抽象、无法影响叙事的描述？
- 是否加入了用户没有要求且会改变核心设定的内容？

### 12.4 位置审计

- 世界根信息和核心规则是否位于角色前？
- 人物和具体详情是否主要位于角色后？
- 指定深度条目是否真的需要紧贴回复？
- 是否误把聊天总结或聊天记录生成成世界书条目？

### 12.5 顺序审计

- 每个条目是否填写了 order？
- 是否先按 position 和 depth 分区，再在区段内部比较 order？
- 是否错误地把高 order 当成高注意力或全局后置？
- 条目之间是否遵循背景、总点、下属总点、分点的阅读顺序？
- 单个条目正文是否遵循定义、构成、机制、限制、影响的阅读顺序？
- 同一位置的条目是否按预期排列？
- 是否为未来插入预留了编号间隔？
- 新增条目是否能够插入预留空档，而无需整体重排？
- 同一主题的不同类型条目是否按语义归属连续放置？
- 主题总点是否位于区间起点，闭标签是否位于区间终点？
- 父子区间是否完整包含，兄弟区间是否依次排列？
- 同时触发的 XML 组是否发生顺序交叉？

### 12.6 XML 审计

- 每个开标签是否有且只有一个闭标签？
- 开闭标签拼写是否完全一致？
- 是否存在交叉嵌套？
- 条件式总点、相关分点和尾标签是否能够共同被召回？
- XML 结束条目的 order 是否晚于全部组内分点？
- 递归配置无法保证时，是否使用了共享关键词的保底模式？

### 12.7 格式审计

- 是否使用 `---` 分隔多个 YAML 文档？
- 是否没有输出 UID？
- type、position 是否使用精确枚举？
- Normal 条目是否具有关键词？
- depth 和 order 是否为数字？
- enabled 和 probability 是否存在且格式正确？
- YAML 是否统一使用两个空格缩进？
- 是否能够直接复制到批量导入器？

## 十三、生成后建议

如需提供建议，必须具体指出：

- 哪个领域仍缺少总点或分点。
- 哪条激活链可能过宽或过窄。
- 哪组 XML 或 order 可能需要调整。
- 哪些共同背景值得抽取为下属总点。
- 哪些内容重复，可通过父子分工缩减 Token。

禁止只给出“增加更多人物”“丰富世界细节”等缺乏对象和理由的空泛建议。
