武侠物品 / 秘籍“品阶”当前实现与后续完善（2026-07-02）

一、当前已落地

1. 底层存档字段已经统一从 `品质` 改为 `品阶`。
   - `src/武侠/utils/variableReader.ts`
     - `UserProfile.包裹` 已定义为 `类型 / 品阶 / 物品描述 / 数量`
     - `parseInventory()` 已按 `item.品阶` 读取
   - `src/武侠/utils/gameInitializer.ts`
     - 开局包裹模板已写成 `类型 / 品阶 / 物品描述 / 数量`
   - `src/武侠/data/出身选项.json`
     - 出身自带物品也已改为 `品阶`
   - `src/武侠/types.ts`
     - `OriginItemInfo` 也已改为 `品阶`

2. 当前开发版不再兼容旧字段 `品质`。
   - 读取链不再 fallback 到 `item.品质`
   - 现阶段的结论很明确：新数据必须写 `品阶`
   - 如果外部脚本、手工存档、旧批量数据还在写 `品质`，现在会直接掉字段

3. 前端行囊栏内部语义已经统一为 `rank / 品阶`。
   - `src/武侠/types.ts`
     - `InventoryItem` 使用 `rank`
   - `src/武侠/components/panels/InventoryPanel.tsx`
     - 普通物品仍显示：
       - 凡品 / 精品 / 珍品 / 极品 / 绝品 / 神品
     - 秘籍仍显示：
       - 粗浅 / 传家 / 上乘 / 镇派 / 绝世 / 传说
   - 也就是说，现在是“统一叫品阶”，但不同物品类型保留不同文案映射

4. 秘籍已经和功法数据库直接挂钩，不再只是“换皮后的普通物品品质”。
   - `src/武侠/utils/variableReader.ts`
     - `parseInventory()` 对 `类型 === 秘籍` 的物品会按物品名读取功法数据库
     - 描述优先取数据库 `功法描述`
     - 品阶优先取数据库 `功法品阶`
     - `martialArtInfo` 已填充：
       - `description`
       - `rank`
       - `requirements`
   - `src/武侠/components/panels/InventoryPanel.tsx`
     - 秘籍详情优先显示 `martialArtInfo.description`
     - 秘籍品阶优先显示 `martialArtInfo.rank`
     - 秘籍可额外显示 `requirements`

5. 功法数据库已经在主流程里预加载。
   - `src/武侠/App.tsx`
     - 初始化读取存档前会 `loadMartialArtsDatabase()`
     - “续写江湖”前会 `loadMartialArtsDatabase()`
     - 新开局初始化完成后也会再次 `loadMartialArtsDatabase()`
   - 这保证了行囊里的秘籍在大多数主流程里能及时拿到数据库元信息

二、当前真实数据模型应如何理解

1. 普通物品
   - 底层变量真实字段就是：
     - `类型`
     - `品阶`
     - `物品描述`
     - `数量`
   - 前端展示“品阶”，不是“品质”

2. 秘籍物品
   - 底层变量字段仍然是普通物品结构，没有额外存一个独立 `功法品阶`
   - 但读取时会按物品名去功法数据库补全
   - 所以当前模型是：
     - 包裹负责“我有哪本秘籍、数量多少”
     - 功法数据库负责“这本秘籍真正的描述、品阶、修炼限制”

3. 当前不建议再给包裹里的秘籍单独补一个存档字段 `功法品阶`
   - 因为现在数据库已经是更可信的来源
   - 重复存一份只会引入双写和漂移风险
   - 除非后续要支持“同名秘籍的不同版本 / 残卷 / 仿本 / 污损本”，否则没必要先加

四、当前仍然存在的真实风险

1. `itemManager.ts` 仍然只完整处理“数量”，没有完整处理物品元信息。
   - `src/武侠/utils/itemManager.ts`
     - 扣减到 0 时会删除整个物品节点
     - `restoreItemCount()` 如果物品已不存在，只会写回：
       - `{ 数量: originalCount }`

2. 这会带来两个直接问题。
   - 普通物品被删空后再恢复：
     - `类型 / 品阶 / 物品描述` 会丢失
   - 秘籍被删空后再恢复：
     - `类型` 会丢失
     - `parseInventory()` 不再把它识别成 `秘籍`
     - 也就不会再走功法数据库补全链路

3. 所以当前最大的剩余完善项，不是再加字段，而是修复“删空后恢复”的元信息丢失。

五、推荐的下一步完善顺序

1. 先修 `itemManager` 的完整快照恢复。
   - 在消费前缓存完整物品对象，而不是只记原始数量
   - 恢复时写回完整结构：
     - `类型`
     - `品阶`
     - `物品描述`
     - `数量`
   - 如果是秘籍，至少要保证 `类型 === 秘籍` 能恢复

2. 给 `itemManager` 补测试。
   - 普通物品：
     - 删空
     - 恢复
     - 验证 `类型 / 品阶 / 描述 / 数量` 都在
   - 秘籍物品：
     - 删空
     - 恢复
     - 验证能再次命中数据库补全

3. 审计所有外部写包裹的地方，确认没有遗留 `品质`。
   - 当前系统已经不兼容 `品质`
   - 所以任何漏网写法都会直接形成新脏数据

4. 如果以后真要做“秘籍实体化玩法”，再考虑下一层建模。
   - 适用场景：
     - 同一本秘籍存在不同版本
     - 秘籍残卷有独立描述和独立品阶
     - 秘籍本身要带耐久、残缺度、装订状态之类的物品属性
   - 到那时再考虑是否引入额外字段，如：
     - `秘籍来源`
     - `秘籍版本`
     - `秘籍残缺度`
   - 但不是现在这一步要解决的问题

六、当前结论

1. 现在这条线已经不是“展示上假装有品阶”。
   - 底层字段已经真实改成 `品阶`
   - UI 术语也统一成 `品阶`
   - 秘籍元信息已经真实接到功法数据库

2. 当前设计的最合理理解是：
   - 普通物品：包裹字段自身即为真值
   - 秘籍物品：包裹负责持有关系，功法数据库负责语义真值

3. 接下来最值得做的不是继续加字段，而是把“物品恢复链路”补完整。
