最新落地状态（2026-07-01 第二次确认）

1. 当前实现已将物品底层字段从 `品质` 切到 `品阶`。
2. 新写入结构以 `类型 / 品阶 / 物品描述 / 数量` 为准。
3. 读层为了兼容旧存档，仍然接受老字段 `品质`，但优先读取 `品阶`。
4. 前端行囊栏内部语义也已统一为 `rank / 品阶`。
5. 秘籍仍保留专属映射：
   - 粗浅 / 传家 / 上乘 / 镇派 / 绝世 / 传说
6. 普通物品仍保留原有映射：
   - 凡品 / 精品 / 珍品 / 极品 / 绝品 / 神品

说明：
以下内容保留了本次讨论过程中“改造前现状”和“方案分歧”的分析，便于回溯；如果与当前实现有冲突，以上述“最新落地状态”为准。

物品变量 / 行囊栏现状整理（2026-07-01）

一、当前真实数据结构

1. 玩家包裹的真实变量位于 `stat_data.user数据.包裹`。
   - 这不是数组，而是「以物品名为 key 的对象」。
   - 当前模板字段固定为：
     - 类型
     - 品质
     - 物品描述
     - 数量

2. 现有代码中的锚点：
   - `src/武侠/utils/variableReader.ts`
     - `UserProfile.包裹` 的类型定义只包含 `类型 / 品质 / 物品描述 / 数量`
     - `parseInventory()` 只把 `item.品质` 映射成前端 `quality`
   - `src/武侠/utils/gameInitializer.ts`
     - 开局初始化写死了 `包裹.$template = { 类型, 品质, 物品描述, 数量 }`
   - `src/武侠/data/出身选项.json`
     - 出身自带物品也沿用同一结构
   - `src/武侠/types.ts`
     - `OriginItemInfo` 也是 `类型 / 品质 / 物品描述 / 数量`

3. 结论：
   - 当前“物品”没有独立的 `品阶` 字段。
   - 当前“秘籍物品”也没有独立的 `功法品阶` 字段。
   - 现阶段真正有 `功法品阶` 的是“功法”数据，不是“包裹物品”数据。

二、当前前端为什么会让人误以为“秘籍也有品阶”

1. `src/武侠/components/panels/InventoryPanel.tsx` 里，`QUALITY_CONFIG` 给同一个 `quality` 配了两套文案：
   - 普通物品走 `labelGeneric`
     - WHITE -> 凡品
     - GREEN -> 精品
     - BLUE -> 珍品
     - PURPLE -> 极品
     - GOLD -> 绝品
     - RED -> 神品
   - 秘籍物品（`item.type === 'SECRET'`）走 `labelSecret`
     - WHITE -> 粗浅
     - GREEN -> 传家
     - BLUE -> 上乘
     - PURPLE -> 镇派
     - GOLD -> 绝世
     - RED -> 传说

2. 这里的 `粗浅 / 传家 / 上乘 / 镇派 / 绝世 / 传说` 只是显示文案。
   - 它们不是来自包裹变量里的独立字段。
   - 它们本质上只是把同一个“品质”换了一套秘籍风格的显示名称。

3. 所以目前的真实情况是：
   - 变量层：只有“品质”
   - UI 层：秘籍会把“品质”显示得像“品阶”
   - 结果：语义漂移，容易让人误判成“物品也有单独品阶”

三、类型系统中的现状

1. `src/武侠/types.ts` 中：
   - `MartialArt.rank` 明确定义的是“功法品阶”
   - `InventoryItem` 只有 `quality`
   - `InventoryItem.martialArtInfo?.rank` 虽然被预留出来了，但当前读链没有填充

2. `src/武侠/utils/variableReader.ts` 中：
   - `parseInventory()` 当前只产出：
     - id
     - name
     - type
     - quality
     - count
     - description
   - 没有给 `martialArtInfo` 赋值
   - 也没有从包裹变量中读取任何“秘籍品阶”字段

3. 结论：
   - 类型层存在“未来可扩展入口”
   - 但当前实现还没有把它接通

四、读写链上还需要注意的地方

1. 当前包裹不仅仅有“初始化”和“读取”，还有运行时写入。

2. `src/武侠/utils/itemManager.ts` 现在只关心“数量”：
   - 扣减物品时，只更新 `数量`
   - 数量减到 0 时，直接删除整个物品节点
   - 撤销恢复时，如果物品已不存在，会只写回：
     - `{ 数量: originalCount }`

3. 这意味着：
   - 当前系统默认把物品元信息视为静态背景数据
   - 一旦物品被删空再恢复，`类型 / 品质 / 物品描述` 都可能丢失
   - 如果后续要给秘籍物品增加独立 `功法品阶`，这里也必须一并补齐

五、当前问题的本质

当前不是“缺一个文案”这么简单，而是“数据语义”和“前端表达”没有对齐：

1. 变量层的概念只有“品质”
2. UI 层对秘籍套用了“功法品阶风格”文案
3. 类型层又预留了 `martialArtInfo.rank`
4. 写链对物品元信息保存也不完整

所以现在最需要先定的是：
到底要不要把“包裹中的秘籍”当成一种拥有独立功法语义的对象来建模。

六、当前讨论后的推荐路线

方案 A：展示语义统一为“品阶”，变量字段暂不改

目标：
保留现有存档结构与映射关系，但在前端展示语义、文档语义上统一使用“品阶”。

核心约定：
1. 变量层继续存 `品质`
2. 前端展示层统一称 `品阶`
3. 普通物品的品阶文案仍然是：
   - 凡品 / 精品 / 珍品 / 极品 / 绝品 / 神品
4. 秘籍物品继续使用当前专属映射：
   - 粗浅 / 传家 / 上乘 / 镇派 / 绝世 / 传说

这意味着：
1. `品质` 是底层存档字段名
2. `品阶` 是前端和策划语义
3. 同一个底层枚举值，在不同物品类型上可以映射成不同的品阶名称

建议做法：
1. `InventoryPanel.tsx` 继续保留 `labelGeneric` 和 `labelSecret`
2. 以后凡是在 UI 上需要出现“品质/品阶”这个概念名称时，统一写“品阶”
3. 如果后续要补详情字段、筛选、排序、提示文案，也统一使用“品阶”措辞
4. 文档上明确注明：
   - “变量字段名仍叫品质”
   - “展示概念统一叫品阶”

优点：
1. 保留当前秘籍映射，不会牺牲表现力
2. 不需要迁移旧存档
3. 不需要改初始化、出身数据、读写链
4. 对玩家看到的语义更顺口，也更贴近武侠语境

缺点：
1. 会形成“存档字段叫品质，前端叫品阶”的术语分层
2. 后续开发时必须明确区分“显示术语”和“底层字段”，否则容易再次混淆

方案 B：真实建模（给秘籍物品单独补语义）

目标：
让包裹里的秘籍不再只是“特殊显示名的品质物品”，而是拥有自己的功法语义。

建议不要直接加通用字段 `品阶`，而是优先考虑：
`功法品阶?: string`

原因：
1. 这个字段只对秘籍类物品有意义
2. 现有系统里“功法”已经使用 `功法品阶` 这个名称
3. 用相同术语更容易和功法体系对齐，避免“物品品阶”和“功法品阶”混用

建议落点：
1. 变量结构
   - `user数据.包裹[物品名]` 在秘籍类型下可选增加 `功法品阶`
2. 初始化模板
   - `gameInitializer.ts` 的包裹模板补可选字段
3. 出身数据
   - `出身选项.json` 中若存在秘籍物品，可显式写入 `功法品阶`
4. 类型定义
   - `UserProfile.包裹` 的 item 类型补 `功法品阶?: string`
   - `OriginItemInfo` 补 `功法品阶?: string`
5. 投影层
   - `parseInventory()` 为秘籍填充 `martialArtInfo.rank`
   - 必要时同时填 `martialArtInfo.description`
6. UI
   - 秘籍详情优先显示真实 `martialArtInfo.rank`
   - 如果旧数据没有该字段，再回退到现有 `quality -> 旧秘籍文案` 映射
7. 写链
   - `itemManager` 在删除前需要缓存完整物品对象
   - 恢复时要能恢复完整元信息，而不是只恢复数量

优点：
1. 概念真实
2. 能支撑后续“秘籍品阶”玩法扩展
3. `InventoryItem.martialArtInfo` 这个预留字段终于有实际用途

缺点：
1. 改动面明显更大
2. 要处理旧存档兼容
3. 要补全物品恢复逻辑，否则字段容易丢

七、当前结论

按这次讨论，当前优先采用方案 A。

也就是：
1. 不去强行把普通物品展示改回“品质”
2. 直接承认前端这一层展示的是“品阶”
3. 普通物品继续用 `凡品 / 精品 / 珍品 / 极品 / 绝品 / 神品`
4. 秘籍继续用 `粗浅 / 传家 / 上乘 / 镇派 / 绝世 / 传说`

这套方案本质上是“术语统一”，不是“数据重构”。

后续只有在你明确要做下面这些能力时，再上真实建模更合理：
1. 秘籍参悟条件和功法品阶挂钩
2. 秘籍掉落/商店/奇遇按品阶分层
3. 秘籍 UI 详情要显示真正的功法信息而不是物品皮肤文案
4. 秘籍使用后需要把“物品中的功法信息”准确转移到“已掌握功法”

八、如果现在就要落地，我建议的具体顺序

如果走方案 A：
1. 检查 `InventoryPanel.tsx` 及相关物品 UI 中，凡是出现概念名称的地方统一写“品阶”
2. 保留当前 `labelGeneric / labelSecret` 映射
3. 在文档里明确“品质是字段名，品阶是展示概念”
4. 如果后面新增行囊筛选、tooltip、详情标签，也默认沿用“品阶”说法

如果走方案 B：
1. 先补数据结构和类型定义
2. 再补 `parseInventory()` 到 `martialArtInfo` 的投影
3. 再补 UI 展示
4. 最后补 `itemManager` 的完整恢复能力
5. 对旧存档做 fallback，避免直接读炸或显示空值

九、当前更推荐的决策

除非你已经准备让“秘籍物品”真正参与功法系统，我建议继续停在方案 A。

理由很直接：
1. 你已经明确更偏好“品阶”这个展示语义
2. 秘籍现有映射本身也符合武侠语境
3. 当前系统的真实源数据仍然没有独立品阶字段
4. 写链对物品元信息保存并不完整
5. 现在直接上真实建模，容易把“术语问题”扩成“存档兼容 + 物品恢复 + 玩法定义”三件事一起做

如果后面确认要做“秘籍就是可携带的功法实体”，再升级到方案 B 会更稳。
