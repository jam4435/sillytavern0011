# AI 自动化接口

## 目的与边界

`WuxiaAutomation` 为同一酒馆页面内的 Tavern Helper 脚本、浏览器自动化或后续本地 companion 插件提供结构化测试入口。

它只开放两项能力：

- 读取当前游戏、调试、消息和聊天级 `stat_data` 快照。
- 复用底部状态栏的真实玩家发送链推进一轮，并返回结构化报告。

接口不会开放任意变量写入、删除楼层或绕过现有消息生命周期的 `generate()` 调用。

## 获取接口

游戏前端挂载后会同时发布：

```ts
const automation = await waitGlobalInitialized<WuxiaAutomationApi>('WuxiaAutomation');
```

以及当前武侠 iframe 内的：

```ts
window.WuxiaAutomation;
```

全局接口版本固定在 `automation.version`。当前版本为 `1`。

接口通过以下页面内事件维护生命周期和运行状态：

```text
wuxia:automation-ready          # 新实例可用
wuxia:automation-state-changed  # page 或 busy 发生变化
wuxia:automation-disposed       # 当前 iframe 实例销毁
```

自动化桥收到 `state-changed` 后会校验实例 ID，重新调用当前实例的 `getSnapshot()` 并更新 Relay；旧 iframe
迟到的通知不会覆盖新实例状态。因此 `booting → game` 和 `busy` 变化不再依赖手动读取 snapshot。

跨 Tavern Helper iframe 的正式调用应优先使用 `waitGlobalInitialized()`；`window` 入口主要用于控制台和浏览器自动化调试。

## 读取快照

```ts
const snapshot = automation.getSnapshot();
```

快照包含：

- `page / busy / ready`（实时 snapshot 是最终事实来源；Relay 会在 page/busy 变化后主动刷新）
- 当前聊天 ID
- 当前正文和选项
- `getVariables({ type: 'chat' }).stat_data`
- 最新 `LatestDebugRound`
- 当前 `VariableChangeSummary`
- 最近八条聊天楼层的活动 swipe 文本
- 最近 80 条 iframe 生命周期黑匣子记录 `iframeLifecycle`

返回对象均为隔离副本。修改快照不会修改 React 状态、聊天楼层或游戏变量。

## 推进真实玩家回合

```ts
const report = await automation.runTurn('前往客栈打听最近的江湖消息');
```

`runTurn()` 与底部状态栏共用 `App.handlePlayerSend()`，因此无论行动来自玩家、Codex CLI 还是 Relay，都会走同一条业务发送链，并保留：

- 地图和物品待发送指令
- 用户与 assistant 真实楼层
- 发送前变量补全和前端派生变量同步
- 主模型 `generate()`
- inline / extra 变量模式
- 状态效果回合递减
- 调试轮次与变量变更追踪
- 正文模型与额外变量模型的请求级 HTTP 429 有限重试

返回的 `WuxiaAutomationTurnReport` 包含：

- `requestId / chatId / startedAt / finishedAt`
- user / assistant 楼层 ID
- 主模型 raw 回复
- 回合前后的聊天级 `stat_data`
- 完整调试轮次
- 变量追踪摘要
- 写入信号和变量验证结论
- 结构化错误

同一时间只允许一个自动化回合。若 UI 正在生成或已有 `runTurn()` 执行，后续调用会返回 `ok: false`，不会创建新楼层。

### 自动化链路中的模型失败重试

`runTurn()` 复用真实玩家发送链，因此正文 `generate()` 和额外变量 `requestConfiguredText()` 遇到 HTTP 429
时，会在各自模型请求边界内最多重试 2 次。重试不会再次创建 user / assistant 楼层，也不会重复追加变量块或触发 ERA。

设置页自动推进和 `runTurn()` 还会在安全落盘边界内，对非 429 请求异常、空回复和变量响应校验失败最多重试 2
次。该策略只覆盖尚未写入聊天/ERA 的模型请求；持久化已经开始后的失败会直接返回失败，不重放整个回合。

调试报告中的 `debug.main` 和 `debug.variable` 会分别保留：

- `retry429Count`：当前阶段已执行的 429 重试次数。
- `retry429LastDelayMs`：最近一次重试前的等待时长。
- `retryFailureCount`：当前阶段已执行的自动推进普通失败重试次数。
- `retryFailureLastDelayMs`：最近一次普通失败重试前的等待时长。

重试耗尽后，报告保留“已自动重试 2 次”的阶段错误并返回 `ok: false`。CLI、Relay、浏览器桥和
`WuxiaAutomation.runTurn()` 本身不得再次调用整个回合，因为模型失败前可能已经创建 user 楼层，或额外变量失败前已经创建 assistant 楼层。

若超长 `Retry-After`、断连或 iframe 换代导致 RPC 先结束，仍按后文的超时恢复规则读取 snapshot 对账；无法唯一确认结果时返回
`OUTCOME_UNKNOWN`，禁止重放原行动。

## 回合锁 ACK 与稳定 iframe

真实发送和重新生成在修改聊天楼层前，会先向隐藏楼层脚本发送：

```text
wuxia:turn-lifecycle { phase: "start", roundId, chatId }
```

隐藏楼层脚本保存内存锁后返回：

```text
wuxia:turn-lock-ack { phase: "locked", roundId, scriptRuntimeId, lockedAt }
```

前端只接受同一 `roundId`
的 ACK。2 秒内未确认时，本轮立即失败，不创建 user 楼层，也不调用正文模型，避免留下没有助手回复的孤立楼层。

回合完成或失败后，前端等待 `wuxia:turn-lifecycle { phase: "finish" }` 处理完成。隐藏楼层脚本随后只清理额外楼层 DOM，并持续保留同一宿主节点；它不会改写 `mesid` 或调用 `refreshOneMessage()`，所以同一聊天的正常回合不会换代 iframe。

黑匣子完整记录保存在 `localStorage.wuxia_iframe_lifecycle_black_box_v1`，最多 240 条；`getSnapshot()`
返回最近 80 条。切换聊天调用 `reloadIframe()` 前会写入原因标记；没有原因标记的 `pagehide` 记为 `external-or-unknown`。若固定宿主已被外部删除，隐藏楼层脚本记录 `stable-shell-lost`，并采用现存宿主但不主动刷新。

诊断实例换代时优先检查：

1. `turn-lock-requested / acquired / acknowledged` 是否齐全。
2. `turn-main-generation-started` 后是否出现 `turn-main-generation-returned`。
3. `iframe-pagehide.details.reason` 和随后 `iframe-boot.details.pendingReloadReason`。
4. 同一聊天是否出现不应发生的 `iframe-pagehide / iframe-boot` 或新的自动化实例；只有聊天切换应有项目内 reload 标记。

## 变量验证

`variableVerification.verdict` 有四种值：

| 值              | 含义                                                           |
| --------------- | -------------------------------------------------------------- |
| `not-requested` | 本轮未发现 Insert / Edit / Delete 声明                         |
| `applied`       | 所有已声明变量均由最终 `stat_data` 验证为 `applied` 或 `no-op` |
| `failed`        | 存在解析错误、`not-applied` 或 `diverged`                      |
| `inconclusive`  | 发现变量声明，但当前追踪结果不足以证明全部落地                 |

`signalObserved` 只表示观察到可能属于本轮的 ERA 写入信号，不能单独证明写入成功。最终判断必须结合：

1. `statDataBefore / statDataAfter`
2. `variableChanges.aiReply.comparisons`
3. `debug.variable.status / error`

变量真相源仍然只有聊天级 `stat_data`。

## 等待参数

```ts
await automation.runTurn('继续观察', {
  settleTimeoutMs: 10_000,
  settleDelayMs: 120,
});
```

- `settleTimeoutMs`：发现变量声明后等待写入信号的时间，范围 `0-30000ms`。
- `settleDelayMs`：写入信号后留给变量追踪器回读的时间，范围 `0-1000ms`。

超时不会把某个 `era:writeDone` 事件伪装成成功；报告会把 `timedOut` 设为 `true`，并继续返回最终 `stat_data` 和比较结果。

## 浏览器 skill 的稳定标识

现有 DOM 提供以下稳定标识用于首轮浏览器自动化：

| 标识                                      | 位置               |
| ----------------------------------------- | ------------------ |
| `data-wuxia-automation="player-input"`    | 玩家输入框         |
| `data-wuxia-automation="send-turn"`       | 发送按钮           |
| `data-wuxia-automation="latest-reply"`    | 最新正文与选项容器 |
| `data-wuxia-automation="story-option"`    | 剧情选项           |
| `data-wuxia-automation="debug-section"`   | 调试页各段         |
| `data-wuxia-automation="open-variables-tab"` | 变量页签        |
| `data-wuxia-automation="stat-data-snapshot"` | 原始完整 `stat_data` 只读 JSON |
| `html[data-wuxia-automation-version="1"]` | 接口就绪和版本     |

外部 AI 的真实推进默认使用 `pnpm wuxia:ui`。普通 `--inspect-only` 只检查 iframe、空闲状态和基础 DOM，不读取完整变量；
只有本轮变量调试不足以解释问题时才显式运行：

```powershell
pnpm wuxia:ui -- --inspect-only --stat-data-snapshot
```

runner 会打开变量页，读取其直接来自 `getVariables({ type: 'chat' }).stat_data` 的隐藏只读 JSON，再关闭弹窗。它不会抓取
受折叠、搜索、分组或隐藏字段影响的变量树文本，也不会保存或写入变量。完整快照可能很大，因此不得作为每轮默认报告字段。

## skill / 插件边界

Tavern Helper 脚本可以直接使用该接口。只能访问文件和终端的外部 AI 进程无法直接读取浏览器内存，还需要以下任一传输层：

- 可控制当前 SillyTavern 页面的浏览器连接器。
- 仅监听 `127.0.0.1` 的 companion MCP / WebSocket 插件。

传输层只应转发 `getSnapshot()` 和 `runTurn()`，不要复制生成、楼层写入或变量同步逻辑。

## 旧本地 CLI 桥（兼容诊断）

Relay/旧 CLI 不再是外部 AI 推进或完整变量读取的默认路径。真实推进使用 UI runner；完整变量诊断使用变量页的
`stat-data-snapshot`。以下桥接仅为旧环境兼容和专项协议排错保留。

自动化使用独立的 `pnpm wuxia:relay` 服务，默认仅监听 `127.0.0.1:6622` 并注册 `/wuxia`
namespace。角色卡脚本“武侠自动化桥（本地开发）”会连接该 namespace，并把 CLI请求转发到本接口。

```text
Codex Skill / 终端
  -> tools/wuxia-cli
  -> http://127.0.0.1:6622/wuxia
  -> 酒馆助手后台脚本
  -> WuxiaAutomation
```

Relay 不启动 Webpack、`tavern_sync` 或酒馆助手实时监听，也不发送 `iframe_updated`、`message_iframe_updated` 或
`script_iframe_updated`。因此启停 Relay 不会刷新武侠前端，`pnpm watch` 也不再承载 `/wuxia` 自动化服务。

使用前确认：

1. 本地静态服务仍在 `http://localhost:5500` 提供 `dist`。
2. 运行 `pnpm build:src:fast` 后刷新酒馆，使“武侠自动化桥（本地开发）”重新加载最新构建。
3. 已将最新的“隐藏楼层”角色卡脚本手动复制到酒馆并启用。
4. 运行 `pnpm wuxia:relay`。
5. 已进入武侠游戏主界面。

Relay 可以在独立终端中长期运行：

```powershell
pnpm wuxia:relay
```

```powershell
pnpm --silent wuxia status
pnpm --silent wuxia snapshot
pnpm --silent wuxia turn --input "前往客栈打探消息"
```

CLI 的 stdout 始终是一份 JSON。退出码 `0` 表示成功，`2` 表示参数错误，`3` 表示服务/桥接页面不可用，`4`
表示酒馆端明确失败，`5` 表示真实回合结果未知。

当真实回合的 RPC 应答超时、断连或自动化实例在回合中换代时，Relay 会先读取一次新的 `snapshot` 对账；满足以下条件时会返回恢复报告，且不会重发行动：

1. 快照已空闲，调试轮次的用户输入与原行动一致。
2. 存在该行动对应的 user 楼层及其后的 assistant 楼层。
3. 主模型已结束；`extra` 模式还要求变量阶段已是 `success`、`error` 或 `skipped`。

恢复报告会标记 `recovered: true` 和
`recoveryReason: 'turn-timeout-snapshot-reconciled'`。若快照证实正文与变量阶段均成功，报告为 `ok: true`；若快照证实主模型或变量阶段错误，则保留真实错误并返回 `ok: false`。若快照中保存的是该行动的终态调试错误，则返回
`recoveryReason: 'turn-persisted-debug-error'` 和真实失败阶段，而不是 `OUTCOME_UNKNOWN`。

只有无法从快照确认结果时才返回 `OUTCOME_UNKNOWN`。此时先执行 `snapshot` 对账，**禁止自动重放**原行动。

桥的状态推送在 iframe 重载或重新发现实例后可能短暂保留 `booting`。发送前和故障判断以一次新的 `snapshot` 为准：只有
`ready: true`、`page: 'game'` 且 `busy: false` 才可运行回合；不要只根据旧状态推送判定页面不可用。

桥状态附带单调递增的 `stateRevision` 和可选的 `snapshotCapturedAt`。Relay 会拒绝同一连接内 revision 更小或同值的迟到状态，避免旧 `booting/error` 覆盖较新的 `game` 快照；这两个字段为兼容字段，不改变协议版本。

### 可选鉴权

本机调试默认依赖 `/wuxia`
namespace 的来源校验。调通后建议在启动 Relay 前设置随机令牌，并在酒馆脚本变量“访问令牌”中填入相同值：

```powershell
$env:WUXIA_BRIDGE_TOKEN = '<随机令牌>'
pnpm wuxia:relay
```

默认端口是 `6622`，可以通过 `WUXIA_RELAY_HOST` 和 `WUXIA_RELAY_PORT` 修改。CLI 或酒馆桥需要连接非默认地址时，使用
`WUXIA_BRIDGE_URL` 或桥脚本的“服务地址”变量指定完整 `/wuxia` URL。

非 loopback 的 SillyTavern 地址默认会被拒绝。确实需要时，通过逗号分隔的完整 Origin 显式允许：

```powershell
$env:WUXIA_BRIDGE_ALLOWED_ORIGINS = 'http://192.168.1.20:8000'
```

项目级剧情推进 Skill 位于 `.agents/skills/wuxia-ai-advance-story`，默认使用 UI runner。只有专项排查旧桥协议时才使用
Relay/旧 CLI。

## 测试建议

提示词回归会真实新增聊天楼层并修改存档变量。建议在复制的聊天或专用测试存档中运行：

```text
getSnapshot
  -> AI 选择或编写下一步行动
  -> pnpm wuxia:ui 真实发送
  -> 检查 debug.main.combinedPrompt / output
  -> 检查 debug.variable
  -> 若调试结果仍无法解释变量问题，再按需读取变量页完整 stat_data
```

不要把 `runTurn()` 当作 dry-run。
