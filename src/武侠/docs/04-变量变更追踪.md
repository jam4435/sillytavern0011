# 变量变更追踪

## 目的

变量变更条只回答三件事：

1. 本回合变量模型声明了哪些变量变化。
2. 回合结束时这些 AI 声明是否真的落到了最终聊天级 `stat_data`。
3. 除 AI 变量模型之外，还有哪些后台实际修改，以及它们来自哪里。

它是“本回合结果视图”，不是 ERA 内部事件审计器。中间 rollback / resync / raw writeDone 不应直接决定 AI/后台身份。

## 唯一状态真相源

所有 before / after / final 值只从：

```text
getVariables({ type: 'chat' }).stat_data
```

读取。

禁止拿以下内容直接当最终变量状态：

- React `GameState`
- `era:writeDone` payload
- sourced/direct 完成事件 payload
- ERA 临时缓存
- 消息变量的合并投影视图

事件只提供“这次写入是谁发起的、已经完成”的元数据；真正的值仍重读聊天级 `stat_data`。

## AI 变量的定义

AI 身份由“本回合实际负责变量更新的模型输出块”决定，不由 ERA producer 推断。

### inline 模式

正文模型自己输出的：

- `<VariableInsert>`
- `<VariableEdit>`
- `<VariableDelete>`

就是本回合 AI 变量声明。

### extra 模式

正文模型负责正文；额外变量模型输出的变量动作块就是本回合 AI 变量声明。

因此对变量变更条而言，inline / extra 没有本质区别：

```text
AI变量 = 当前变量模型返回的变量动作块
```

`<VariableThink>` 只作为 AI 思考摘要展示，不参与变量路径分类。

## 后台变量的定义

后台变量有两类来源。

### 1. 最终 assistant 楼层中的后台变量块

结算时解析最终 assistant 楼层全部变量动作块：

```text
后台变量块
=
最终 assistant 楼层全部变量动作块
-
本回合 AI 变量模型返回的变量块
```

这里使用动作 + 完整路径 + 目标值做语义匹配，而不是按字符串换行/缩进匹配。

### 2. 不经过 assistant 变量块的直接实际修改

有些后台写入直接修改聊天变量，不一定在 assistant 楼层产生 Variable 块，例如：

- 变量编辑器
- 前端派生变量
- restore / 迁移
- 某些事件脚本或直接聊天变量事务

这些通过统一写入包装层的 `source / reason / operation` 记录来源，并在完成后重读 `stat_data` 生成精确差分，也必须进入“后台变更”。

如果外部代码既没有走统一来源包装，也没有留下最终楼层变量块，回合结算还会用 baseline → final 的剩余差分做最后兜底，避免真实变化彻底消失；这种项来源显示为兜底来源，而不是伪造具体模块。

## 来源标签

后台的“是否后台”与“具体来自哪里”是两个不同概念：

```text
变量块身份
决定：AI / 后台

source / reason
决定：后台具体来源
```

统一来源类型目前包括：

- `event-script`
- `frontend`
- `variable-editor`
- `restore`

ERA 写入统一通过 `emitEraVariableWriteAndWait()` 携带：

- `source`
- `operation`
- `reason`
- `attribution`

匹配原始 `era:writeDone` 后，只发送一次 `wuxia:eraVariableWriteDone` 来源完成事件。

`emitSourcedEraVariableWriteAndWait()` 只是兼容旧调用名，内部复用同一个统一入口，不再二次补发来源事件。

直接聊天变量写入通过：

- `runDirectChatVariableWrite()`
- `writeDirectChatTransaction()`

在写入完成后发送 `wuxia:directVariableWriteDone`。

这两个函数与 inline / extra 模式无关；它们只是“没有必要通过 assistant 变量块完成的直接聊天变量写入”的统一包装。

## raw era:writeDone 的职责

`era:writeDone` 仍然是 ERA 自己的底层完成信号，用于：

- 等待特定 message / action / transaction 完成
- 控制消息生命周期
- 写后校验

但变量变更 tracker **不再使用 raw `era:writeDone` 判断 AI/后台来源**。

原因很简单：raw 事件本身没有完整业务 source。让 tracker 先消费 raw，再等 sourced 事件事后 promote/demote，只会制造不必要的时序竞态。

现在的规则是：

```text
raw era:writeDone
    -> 流程完成确认

wuxia:eraVariableWriteDone
    -> 来源已知的后台/AI checkpoint 元数据
```

不存在旧版的：

- promote
- demote
- reconcile
- producer priority
- late AI target 回提

## 回合工作流程

### 普通发送

```text
开始回合
  ↓
保存 baseline stat_data
  ↓
发送前前端派生 / direct 后台写入
  ↓
各自通过 source 事件记录后台实际 diff
  ↓
模型返回
  ↓
登记 AI 变量块
  ↓
AI 变量写入完成
  ↓
建立 AI checkpoint（只推进后续后台写入的 before 起点）
  ↓
事件脚本 / 前端 / 其他后台结算
  ↓
按 source 记录后台实际 diff
  ↓
wuxia:turn-completed 及后处理结束
  ↓
显式 settle
  ↓
读取最终 assistant 楼层 + final stat_data
  ↓
生成最终变量变更条
```

### 重新生成 / 重 roll

重新生成必须排除旧 swipe 的内部回滚。

正确顺序：

```text
开始重新生成
  ↓
回滚旧 swipe
  ↓
同步重新生成前派生变量
  ↓
正文模型生成新回复
  ↓
【此时才建立新的 tracker baseline】
  ↓
登记 AI 变量块
  ↓
写入新 swipe / ERA
  ↓
后台结算
  ↓
settle
```

因此旧 swipe 的：

- 境界回退
- 修为回退
- 地点回退
- 删除旧人物经历

只是重新生成准备动作，不会被显示成新回复的“后台变更”。

## AI 状态判断

AI 是否成功只由三样东西决定：

- baseline 值
- AI 声明值
- final `stat_data` 值

规则：

```text
baseline 已经等于声明值，final 也相同
  -> no-op

final == AI声明
  -> applied / 已落地

final == baseline 且 != AI声明
  -> not-applied / 未落地

final != baseline 且 final != AI声明
  -> diverged / 值不一致
```

不再因为“这个路径中途也被后台改过”就把最终已经等于 AI 声明的值判成未落地。

例如：

```text
baseline 修为 = 4000
AI声明 = 5000
final = 5000
```

无论中间发生过什么，AI 项最终显示“已落地”。

如果：

```text
baseline = 4000
AI声明 = 5000
后台随后改成 4800
final = 4800
```

则：

- AI 区：`4000 -> 4800`，AI 声明 5000，状态“值不一致”
- 后台区：如果来源事件完整，可展示精确的 `5000 -> 4800` 及具体 source

## 差分限量

AI 与后台分别计数、分别最多保留 `MAX_STORED_VARIABLE_CHANGES` 条。

不能先对整个 baseline → final diff 截断再筛 AI，否则大量后台变化可能把后面的 AI 路径挤掉。

AI 最终差分使用分类桶遍历，AI / background 各自独立统计省略数量。

## 刷新恢复

当前回合观测保存在 `sessionStorage`。

当前版本：

```text
wuxia.variableChangeTurn.v16
```

版本升级时旧 tracker 状态直接清理，避免旧归因结构污染新模型。

## 必须保持的约束

1. before / after / final 值只认聊天级 `stat_data`。
2. AI 身份只由当前变量模型输出块决定。
3. 最终楼层排除 AI 块后的动作块属于后台块。
4. 没有楼层块的 direct 实际写入也必须显示为后台。
5. 后台具体来源只认调用方显式传入的 `source / reason`，不从 raw ERA 时序猜。
6. raw `era:writeDone` 不参与玩家变量条的 AI/后台归因。
7. 重新生成 baseline 必须建立在旧 swipe 回滚完成之后。
8. 回合必须在事件脚本等后处理完成后显式 settle，再读最终快照。
9. 消息边界可以做最终兜底，但不能伪造具体 source。
10. tracker 只观测，不负责修改业务变量。

## 常见故障

| 现象 | 优先检查 |
| --- | --- |
| AI 当前值与声明相同却显示未落地 | final `stat_data` 是否真的在 settle 后读取；是否仍运行旧比较规则 |
| 后台出现大量旧回复回退 | regenerate baseline 是否建立在 old swipe rollback 之前 |
| 同一后台变化重复出现 | ERA 统一入口是否又被旧 sourced 包装二次发事件 |
| 后台来源全部显示泛化 ERA | 调用方是否通过统一包装传了正确 `source / reason` |
| direct write 消失 | 是否经过 `runDirectChatVariableWrite / writeDirectChatTransaction`，或 final diff 兜底是否执行 |
| AI 项被大量后台 diff 挤掉 | 是否对 AI / background 分桶后再分别限量 |
| UI 与真实变量不一致 | 是否错误使用 `GameState` / payload，而不是聊天级 `stat_data` |
