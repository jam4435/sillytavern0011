# 事件与自动补全

## 目的与边界

本文说明前端如何依赖 ERA、酒馆助手变量函数和消息边界完成刷新与后台补全。具体事件脚本逻辑在独立目录，不在本文展开。

## 监听重点

`hooks/useEventListeners.ts` 关注三类信号：

| 信号 | 作用 |
| --- | --- |
| `MESSAGE_SENT` | 绑定回合、建立追踪基线 |
| `MESSAGE_RECEIVED / MESSAGE_UPDATED / MESSAGE_SWIPED / CHAT_CHANGED` | 刷新正文、选项、`GameState`，并做消息边界兜底 |
| `era:writeDone` | ERA 写入完成后刷新与追踪 |
| `wuxia:directVariableWriteDone` | 直接聊天变量写入完成后刷新与追踪 |

## 主链路

```text
事件到达
  -> readGameDataPure() 刷新 UI
  -> scheduleGameDataCompletion() 排队检查
  -> 必要时走 ERA 写回
  -> era:writeDone
  -> 重读 chat.stat_data
  -> 若完成信号异常，则由消息边界兜底补读
```

直接写入链路单独处理：

```text
变量函数直接写入
  -> wuxia:directVariableWriteDone
  -> 重读 chat.stat_data
```

直接写入不得伪造 `era:writeDone`。

## 纯读取与补全分离

- `readGameDataPure()` 只把当前变量投影到 UI。
- `scheduleGameDataCompletion()` / `flushPendingGameDataCompletion()` 负责后台补全调度。
- 不要把“读取”写成“顺手补全”，否则容易形成循环。

## 属性补全

属性补全根据以下输入判断是否需要写回：

- 初始属性
- 当前境界
- 功法加成
- 现有属性字段是否缺失或落后

普通属性更新走 ERA，不走直接变量写入。

## 功法补全

AI 只需要产出最小功法数据；前端根据 `data/_合并后功法.json` 补足展示和持久所需字段。

触发条件通常是：

- 新功法出现
- 掌握程度变化
- 缺失字段需要补足

两条链路要区分：

- 显示补齐：只补 UI，不改持久变量
- 持久补全：走 ERA 写回缺失字段或新特性

普通功法操作走 ERA，不走直接变量写入。

## 初始化独立

初始化与普通补全不是一回事：

- 初始化负责建立首份可读 `stat_data`
- 已有存档接管负责恢复当前聊天
- 平时的功法/境界/属性补全按普通 ERA 链路处理

## 消息边界兜底

消息边界用于处理三类情况：

- 写入完成事件晚到
- 外部操作改了聊天变量
- 某次完成信号缺失

兜底动作是重读聊天级 `stat_data` 并按需要补排队列，不是伪造写入完成。

## 必须保持的约束

1. 监听器集中在 Hook 中注册和注销。
2. `readGameDataPure()` 保持只读。
3. 普通功法/境界操作与后台补全走 ERA。
4. 直接写入只发 `wuxia:directVariableWriteDone`，不得伪造 `era:writeDone`。
5. `stat_data` 是最终验证与差分真相源。
6. 初始化独立，消息边界只负责兜底。
