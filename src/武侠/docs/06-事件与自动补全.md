# 事件与自动补全

## 目的与边界

本文说明 React 前端如何监听酒馆/MVU/ERA 事件，以及属性、角色和功法数据如何在后台补全。具体事件脚本逻辑位于独立的 `src/事件脚本/`，不在本文展开。

## 全局监听

`hooks/useEventListeners.ts` 集中注册：

| 事件 | 主要用途 |
| --- | --- |
| `MESSAGE_SENT` | 绑定变量追踪回合的 user 楼层 |
| `MESSAGE_RECEIVED` | 刷新正文、选项和游戏状态 |
| `MESSAGE_UPDATED` | 响应楼层编辑或额外变量追加 |
| `MESSAGE_SWIPED` | 响应 swipe 切换 |
| `CHAT_CHANGED` | 清理回合状态并读取新聊天 |
| `Mvu.events.VARIABLE_UPDATE_ENDED` | 调度精确补全和变量差分 |
| `era:writeDone` | 纯读刷新、变量追踪和写入完成通知 |

事件监听应集中在 Hook 中，组件不要重复注册同一批全局事件。

## 纯读取与补全分离

`variableReader.ts` 将读取与写入拆开：

```text
事件到达
  -> readGameDataPure() 立即刷新 UI
  -> scheduleGameDataCompletion*() 排队检查
  -> 必要时调用 ERA API 写入
  -> era:writeDone
  -> 再次纯读刷新
```

这样可避免“读取一次就写一次”的递归循环。

## 角色属性补全

触发条件通常包括：

- 新玩家或 NPC 出现。
- 境界变化。
- 影响计算的输入发生变化。
- 现有属性字段缺失。

补全根据初始属性、境界和功法加成计算战斗/资源属性，并使用 ERA 对象写入 API 更新。

## 功法补全

AI 通常只需要生成最小功法数据。前端根据 `data/_合并后功法.json` 补充：

- 类型
- 描述
- 品阶
- 已解锁特性
- 升级信息

新增功法和掌握程度变化是主要触发条件。已有且完整、输入未变化的数据应跳过。

## 队列与缓存

补全系统使用：

- 状态缓存判断输入是否实际变化。
- 更新锁避免同一类补全重入。
- 调度队列合并短时间内的重复请求。
- `flushPendingGameDataCompletion()` 在生成前等待队列清空。

缓存只用于减少重复工作，不能作为持久数据源。切换聊天或全量扫描时必须允许重新建立缓存。

## 与事件脚本的关系

事件脚本和游戏前端都可能在同一回合写变量：

- 事件脚本通常带 `directChatWrite` 和具体 `reason`。
- 前端补全通过 ERA API 产生 `writeDone`。
- 变量条将这些写入归入后台变更。

不要根据写入发生在 AI 回复之后就假定它属于 AI。

## 必须保持的约束

1. 全局监听器必须在 Hook 卸载时全部 `stop()`。
2. UI 刷新使用纯读取，补全通过队列异步执行。
3. 补全写入必须有防重入和状态变化检测。
4. 生成前必须等待已排队补全。
5. MVU 未就绪时允许消息边界全量扫描兜底。
6. 后台补全不能被归为 AI 回复变量。

## 修改后验证

- 新角色出现后补全属性且只写一次。
- 境界或掌握程度变化后更新对应字段。
- 无变化的连续消息不重复写入。
- MVU 延迟初始化时消息边界兜底仍生效。
- 切换聊天不会沿用上一聊天的补全缓存。
- 补全写入在变量条后台分类中可见。
