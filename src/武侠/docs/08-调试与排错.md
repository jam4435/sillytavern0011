# 调试与排错

## 目的与边界

本文提供当前有效的定位顺序，不记录历史修复细节。

## 先看哪里

| 位置                                       | 主要用途                                   |
| ------------------------------------------ | ------------------------------------------ |
| 设置页调试                                 | 看最近一轮输入、正文、变量输出和同步验证   |
| 分类日志                                   | 看初始化、消息、事件、游戏、API、UI、数据  |
| 变量变更条                                 | 看 AI 声明、实际落地、后台差分             |
| 酒馆楼层                                   | 看 user/assistant 楼层、swipe、raw 回复    |
| iframe 生命周期黑匣子                      | 看回合锁 ACK、固定宿主、外部刷新和实例换代 |
| `getVariables({ type: 'chat' }).stat_data` | 看最终持久变量真相                         |

判断变量问题时，`stat_data` 是唯一差分真相源。

## 开启分类日志

开发构建下可设置：

```js
localStorage.setItem('wuxia_debug_categories', 'message,event,data');
```

可用分类：

```text
init,message,event,game,api,ui,data
```

## 变量问题定位

### 最终变量没变

1. 先看聊天级 `stat_data`，不要先看 React `GameState`。
2. 如果是普通操作，检查对应 ERA 写入和 `era:writeDone`。
3. 如果是变量编辑器或其他直接写入，检查 `wuxia:directVariableWriteDone`。
4. 如果两类完成信号都没抓到，再看消息边界兜底是否补读成功。
5. 已收到匹配 `era:writeDone` 但最终值暂未出现时，先看调试中的“变量应用状态/变量快照验证”；它应显示等待快照而非直接把声明判为 `not-applied`。

### 变量条归因错误

1. 检查 baseline 是否建立在写入之前。
2. 检查 AI 声明路径和值是否真的匹配实际差分。
3. 检查是否把直接写入错误伪装成 `era:writeDone`。
4. 检查追踪是否始终回读聊天级 `stat_data`。

### 后台补全循环

1. 检查 `readGameDataPure()` 是否意外触发写入。
2. 检查补全缓存、防重入和去重是否生效。
3. 检查写回后聊天级 `stat_data` 是否已与目标值一致。
4. 检查消息边界是否反复把同一轮补全重新排队。

## 消息问题定位

### 正文生成但界面没刷新

1. 检查 raw assistant 楼层是否存在。
2. 检查消息边界事件是否到达。
3. 检查 `readGameDataPure()` 是否成功重读。
4. 检查正文显示是否被正则过滤为空。

### 重新生成后变量不一致

1. 检查目标 swipe 是否正确。
2. 检查是否等待了匹配楼层的 ERA 完成信号。
3. 检查旧变量回滚和新变量重算是否都落到了聊天级 `stat_data`。

### 自动化桥显示 `booting`，但页面实际已进入游戏

新版前端会在 `page` 或 `busy` 变化时发送 `wuxia:automation-state-changed`，桥校验实例 ID 后主动读取实时
snapshot 并更新 Relay。正常的 `booting → game` 不再需要手动 snapshot 才能刷新。

1. 若 `booting` 仍持续数秒，先确认武侠前端和“武侠自动化桥（本地开发）”均已重载到最新构建。
2. 读取新 snapshot；`ready: true`、`page: 'game'`、`busy: false` 是可发送条件。读取 snapshot 仍会作为状态
   缓存的兜底刷新。
3. 若新快照仍是 `booting`，说明前端初始化本身尚未完成，应检查 `loadMartialArtsDatabase()` 等启动步骤，
   不能在初始化期创建 user 楼层。
4. 若 snapshot 已是 `game`、但 Relay 仍是 `booting`，记录 bridge 的 `sessionId`、`automationInstanceId`、
   `stateRevision` 与 `snapshotCapturedAt`，检查状态变化事件是否被旧脚本遗漏或是否存在第二个 bridge。

## 稳定 iframe 与回合锁

生命周期黑匣子保存在：

```js
JSON.parse(localStorage.getItem('wuxia_iframe_lifecycle_black_box_v1') || '[]');
```

最多保留 240 条。自动化接口的 `snapshot.iframeLifecycle` 会返回最近 80 条，CLI 可直接通过 `pnpm --silent wuxia snapshot`
读取。

重点事件：

| 事件                                 | 含义                                                       |
| ------------------------------------ | ---------------------------------------------------------- |
| `turn-lock-requested`                | 武侠前端请求隐藏楼层锁住当前 iframe                        |
| `turn-lock-acquired`                 | 隐藏楼层脚本已经保存本轮锁                                 |
| `turn-lock-acknowledged`             | 武侠前端已收到同一 `roundId` 的 ACK                        |
| `turn-lock-ack-timeout`              | 2 秒内没有 ACK；本轮不会创建 user 楼层                     |
| `stable-shell-collapse-deferred-by-turn-lock` | 回合中推迟清理额外楼层，不是错误                    |
| `stable-shell-adopted / lost`        | 固定宿主被采用，或已被外部酒馆重绘删除                     |
| `iframe-reload-requested`            | 项目代码因切换聊天即将调用 `reloadIframe()`                |
| `iframe-pagehide`                    | 武侠前端 iframe 即将卸载                                   |
| `iframe-boot`                        | 新武侠 iframe 已启动，并记录上一个刷新原因                 |
| `automation-instance-ready/disposed` | 自动化实例创建或销毁                                       |

换代原因格式：

- `reloadIframe:chat-changed`：切换了聊天。
- `external-or-unknown`：没有经过项目内已标记入口，重点检查手动刷新、酒馆重绘或实时监听热更新。

常见判断：

1. 有 `turn-lock-requested`，没有 `turn-lock-acquired`：隐藏楼层脚本未收到事件或仍是旧版本。
2. 已有 `turn-lock-acquired`，随后出现新的
   `hidden-floor-script-boot`，但没有正常解锁：后台脚本在回合中被重新加载，内存锁丢失。
3. 锁仍有效时只出现 `stable-shell-collapse-deferred-by-turn-lock`：保护正常工作。
4. `iframe-pagehide` 的原因是 `external-or-unknown`：刷新来自回合锁控制范围之外。
5. 正常完成应依次看到 ACK、正文返回、assistant 楼层和解锁；同一聊天不应随后出现 `iframe-pagehide`、`iframe-boot` 或新的 automation instance。

## 最小回归

- 初始化新档或读取已有聊天
- 手动发送一轮
- 自动推进至少两轮
- 重新生成一次
- 做一次普通功法或境界操作
- 做一次直接变量编辑
- 展开变量条检查 AI 与后台分类
- 切换聊天并返回
- 检查一轮黑匣子包含锁定 ACK 与正常解锁，且同一聊天没有 iframe 换代；切换聊天后才出现带原因的换代
