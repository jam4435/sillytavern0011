# 调试与排错

## 目的与边界

本文提供当前有效的定位顺序，不记录历史修复细节。

## 先看哪里

| 位置                                       | 主要用途                                   |
| ------------------------------------------ | ------------------------------------------ |
| 设置页调试                                 | 看最近一轮用户输入、最终送模提示词、正文输出、变量输出和同步验证 |
| 分类日志                                   | 看初始化、消息、事件、游戏、API、UI、数据  |
| 变量变更条                                 | 看 AI 声明、实际落地、后台差分             |
| 酒馆楼层                                   | 看 user/assistant 楼层、swipe、raw 回复    |
| iframe 生命周期黑匣子                      | 看回合锁 ACK、固定宿主、外部刷新和实例换代 |
| `getVariables({ type: 'chat' }).stat_data` | 看最终持久变量真相                         |

判断变量问题时，`stat_data` 是唯一差分真相源。

## 开启分类日志

开发构建下可设置：

```js
localStorage.setItem('wuxia_debug_categories', 'message,event,data');
```

可用分类：

```text
init,message,event,game,api,ui,data
```

## 变量问题定位

### 最终变量没变

1. 先看聊天级 `stat_data`，不要先看 React `GameState`。
2. 如果是普通操作，检查对应 ERA 写入和 `era:writeDone`。
3. 如果是变量编辑器或其他直接写入，检查 `wuxia:directVariableWriteDone`。
4. 如果两类完成信号都没抓到，再看消息边界兜底是否补读成功。
5. 已收到匹配 `era:writeDone` 但最终值暂未出现时，先看调试中的“变量应用状态/变量快照验证”；它应显示等待快照而非直接把声明判为 `not-applied`。

### 变量条归因错误

1. 检查 baseline 是否建立在写入之前。
2. 检查 AI 声明路径和值是否真的匹配实际差分。
3. 检查是否把直接写入错误伪装成 `era:writeDone`。
4. 检查追踪是否始终回读聊天级 `stat_data`。

### 后台补全循环

1. 检查 `readGameDataPure()` 是否意外触发写入。
2. 检查补全缓存、防重入和去重是否生效。
3. 检查写回后聊天级 `stat_data` 是否已与目标值一致。
4. 检查消息边界是否反复把同一轮补全重新排队。

## ERA 历史日志与事件写入诊断（测试版）

历史分叉若出现“SelectedMks 一致、事件状态不一致”，优先区别：
1. 某个消息首次应用时就没有产生有效 EditLog；
2. 同一个 MK 后续重算将非空 EditLog 覆盖为 `[]`；
3. 事件脚本通过不受 ERA 回滚管理的 direct write 改动事件状态。

这些属于不同问题，不应在尚未定位时直接保留旧日志、取消哈希校验或批量重置事件状态。

普通诊断保存在 `era_diagnostics_v1`（最多 600 条），关键事件写入/回滚诊断另外保存在
`era_critical_diagnostics_v1`（最多 300 条），不写入聊天变量。
普通队列满载、watchdog 大量写入时，先读取**独立的关键诊断**：

```js
const critical = window.ERADiagnostics?.critical?.()
  ?? JSON.parse(localStorage.getItem('era_critical_diagnostics_v1') || '[]');
console.log('关键事件诊断', critical);
console.log('历史恢复事件系统五子组', critical.filter(entry => entry.event === 'history-checkout-event-system-audit'));
```

每次历史恢复分别记录 `before-full-sync`、`after-full-sync`、
`after-event-prepare` 三个阶段的事件系统子组哈希与条目数。
每条 `history-checkout-event-system-audit` 还包含 `eraLogInventory`：
`selectedMksLength`、`editLogKeysCount`、各消息 MK 的 `logCount`
与 `eventSystemLogCount`。比较全同步前后记录，可判断缺失的回滚日志是在复制分支时
就不存在，还是同步阶段被覆盖；仅记录日志条数和路径所属根，不记录叙事内容或完整变量值。
这三个阶段在新调试代码安装之后的新尝试才有记录；**旧日志无法追溯补建**。
ERA 强制完全重算还会记录 `rollback-event-state-audit`，其中 `steps` 逐 MK 记录：
`messageId`、`allLogCount`、`eventSystemLogCount`、
`beforeHash`、`afterHash`、`changedBuckets` 与 `eventLogPathChecks`。
`before=new` 表示回滚前实际值是否与日志新值一致，
`before=old` 表示回滚前是否已经是日志旧值，
`after=old` 表示回滚后是否等于日志旧值。
此处只保存路径与匹配结果，不保存游戏变量具体值；如果多个操作修改同一路径，
`after=old` 不一定单独成立，应结合整楼日志逆序语义分析。

```js
(() => {
  const entries = window.ERADiagnostics?.critical?.() ?? [];
  const recent = entries.filter(x => x.event === 'rollback-event-state-audit').slice(-1);
  copy(JSON.stringify(recent.map(x => x.details), null, 2));
  console.log('已复制逐 MK 回滚审计：', recent.length);
})();
```

历史恢复时，ERA 强制同步内部还额外记录三段 `full-resync-event-state-audit`：
`before-rollback`（回滚全部旧 MK 之前）、`after-rollback`（旧 MK 回滚完、消息尚未重放）和
`after-replay`（消息重放完、SelectedMks 最终更新之前）。这些轻量指纹与封存指纹算法不同，
**只能在同一类诊断的不同阶段之间比较**，不能直接与历史节点封存的 16 位哈希对比。

```js
(() => {
  const records = window.ERADiagnostics?.critical?.() ?? [];
  const rows = records.filter(x => x.event === 'full-resync-event-state-audit').slice(-3)
    .map(x => x.details);
  copy(JSON.stringify(rows, null, 2));
  console.log('已复制全同步内部三阶段诊断', rows.length);
})();
```

ERA 和武侠可作为两个 webpack bundle 加载诊断模块，但它们共享相同的 localStorage 存储键。
每次追加日志必须读取最新存储，不得复用模块初始化时的缓存，否则武侠的 `after-full-sync`
可能覆盖 ERA 刚记录的 `after-rollback`。从修复之前的诊断中看到内部记录缺失，不代表
内部重算没有执行。内部审计若失败会在控制台输出警告，诊断错误本身不会打断游戏操作。

### 历史分叉：确定未来 MK 是在哪个阶段消失的

`history-branch-mk-lifecycle-audit` 是只读跨 iframe 关键诊断，仅在
`fork_branch` journal 存在时采集。使用相同 `transactionId` 串联：

- `source-before-branch-create`：来源聊天执行 `/branch-create` 前；
- `branch-create-returned`：若旧 iframe 在 slash 返回后仍然存活，会补充采样（可能缺失）；
- `era-module-loaded`：新 iframe 的 ERA 入口最早采样，发生在该模块注册自动同步监听之前；
- `era-chat-changed-before-queue` / `era-app-ready-before-queue`：监听事件但尚未入 ERA 队列；
- `era-auto-resync-before` / `era-auto-resync-after`：自动同步前后（含无变化或快速返回分支）；
- `checkout-before-explicit-full-sync`：历史恢复主动要求完全同步之前；
- `era-full-resync-before` / `era-full-resync-after`：强制重算前后。

每条记录包含 `chatId`、`messageCount`、`selectedMksLength`、
`futureMksCount`、`futureEditLogCount`、`futureEventSystemLogCount`、
`unselectedEditLogKeysCount` 和 `activeEventLogCounts`。
`variablesAvailable/metaAvailable` 为 false 的采样表示新 iframe 数据尚未就绪，不能将该次 0 个 MK 当作截断证据。
诊断仅存 MK、变量路径计数及进行中事件名称，不存变量具体值，不改变分叉、回滚或事件处理。

```js
(() => {
  const entries = window.ERADiagnostics?.critical?.() ??
    JSON.parse(localStorage.getItem('era_critical_diagnostics_v1') || '[]');
  const records = entries.filter(x => x.event === 'history-branch-mk-lifecycle-audit');
  const last = records.at(-1)?.details?.transactionId;
  const rows = records.filter(x => x.details?.transactionId === last).map(x => ({
    time: x.isoTime,
    ...x.details,
  }));
  copy(JSON.stringify(rows, null, 2));
  console.log('已复制分叉 MK 生命周期诊断', { transactionId: last, rows: rows.length });
})();
```

判定方式：
1. 来源快照存在未来 MK，新 iframe 的第一个 `metaAvailable=true` 且在 ERA 同步之前的快照已不存在：
   **MK 链在 ERA 第一次同步前就已截断**，检查 `/branch-create` 的聊天变量复制/裁剪行为。
2. 新 iframe 同步前仍有未来 MK，但 `era-auto-resync-after` 不再有：
   **ERA 自动同步删除了未来 MK**，应检查增量同步与日志清理。
3. `futureMksCount=0` 但 `unselectedEditLogKeysCount>0`，表示未来 MK
   可能已经从选择链消失，但仍有未选中的 EditLogs；这些日志不一定全部属于未来楼层，
   需结合来源快照的 MK 标识逐项对照。
4. 来源快照本来没有未来 MK，或新 iframe 数据未就绪：**本次日志不能归因**，
   不能据此宣称是 `/branch-create` 或 ERA 同步造成。

`ERADiagnostics.clear()` 会同时清空两种诊断队列，复现前不要误清空。

普通诊断仍可按以下命令读取：

```js
JSON.parse(localStorage.getItem('era_diagnostics_v1') || '[]')
  .filter(entry =>
    [
      'message-apply-log-audit',
      'event-state-changed-without-editlog',
      'action-blocks-produced-empty-editlog',
      'nonempty-editlog-overwritten-by-empty',
      'branch-sensitive-event-state-write',
      'event-edit-skipped',
      'event-insert-skipped',
    ].includes(entry.event),
  );
```

- `message-apply-log-audit`：记录 messageId、mk、楼层中原始操作顺序、写入前后六组事件根的指纹，以及旧/新 EditLog 数量。
- `nonempty-editlog-overwritten-by-empty`：原日志非空、本次重算产出空日志；它也可能是合法重算结果，不能单凭此记录定性为 bug。
- `action-blocks-produced-empty-editlog`：楼层有动作块，但最终未产生有效变更，结合后续直接写入日志判断是否提前变更。
- `event-state-changed-without-editlog`：事件根变动但本楼无任何回滚日志，应重点核查。
- `branch-sensitive-event-state-write`：由 direct writer 记录事件根变更的写入来源、理由和路径（不存放变量值）。
- `event-edit-skipped`：事件 Edit 因父/叶子路径不存在或目标值早已相等而被跳过；附带 messageId 与旧值是否仍与目标不同的布尔判断。
- `event-insert-skipped`：事件 Insert 在已有不可递归的路径上被跳过；需结合相邻 direct write 与同楼执行顺序分析。

ERA 按消息中动作块出现顺序执行，不再把 Insert/Edit/Delete 分组重排；尤其要用“删除旧人物占用 → 插入新人物占用”的实际事件交接进行回归测试。

## 消息问题定位

### 正文生成但界面没刷新

1. 检查 raw assistant 楼层是否存在。
2. 检查消息边界事件是否到达。
3. 检查 `readGameDataPure()` 是否成功重读。
4. 检查正文显示是否被正则过滤为空。

### 重新生成后变量不一致

1. 检查目标 swipe 是否正确。
2. 检查是否等待了匹配楼层的 ERA 完成信号。
3. 检查旧变量回滚和新变量重算是否都落到了聊天级 `stat_data`。

### 自动化桥显示 `booting`，但页面实际已进入游戏

新版前端会在 `page` 或 `busy` 变化时发送 `wuxia:automation-state-changed`，桥校验实例 ID 后主动读取实时
snapshot 并更新 Relay。正常的 `booting → game` 不再需要手动 snapshot 才能刷新。

1. 若 `booting` 仍持续数秒，先确认武侠前端和“武侠自动化桥（本地开发）”均已重载到最新构建。
2. 读取新 snapshot；`ready: true`、`page: 'game'`、`busy: false` 是可发送条件。读取 snapshot 仍会作为状态
   缓存的兜底刷新。
3. 若新快照仍是 `booting`，说明前端初始化本身尚未完成，应检查 `loadMartialArtsDatabase()` 等启动步骤，
   不能在初始化期创建 user 楼层。
4. 若 snapshot 已是 `game`、但 Relay 仍是 `booting`，记录 bridge 的 `sessionId`、`automationInstanceId`、
   `stateRevision` 与 `snapshotCapturedAt`，检查状态变化事件是否被旧脚本遗漏或是否存在第二个 bridge。

## 稳定 iframe 与回合锁

生命周期黑匣子保存在：

```js
JSON.parse(localStorage.getItem('wuxia_iframe_lifecycle_black_box_v1') || '[]');
```

最多保留 240 条。自动化接口的 `snapshot.iframeLifecycle` 会返回最近 80 条，CLI 可直接通过 `pnpm --silent wuxia snapshot`
读取。

重点事件：

| 事件                                 | 含义                                                       |
| ------------------------------------ | ---------------------------------------------------------- |
| `turn-lock-requested`                | 武侠前端请求隐藏楼层锁住当前 iframe                        |
| `turn-lock-acquired`                 | 隐藏楼层脚本已经保存本轮锁                                 |
| `turn-lock-acknowledged`             | 武侠前端已收到同一 `roundId` 的 ACK                        |
| `turn-lock-ack-timeout`              | 2 秒内没有 ACK；本轮不会创建 user 楼层                     |
| `stable-shell-collapse-deferred-by-turn-lock` | 回合中推迟清理额外楼层，不是错误                    |
| `stable-shell-adopted / lost`        | 固定宿主被采用，或已被外部酒馆重绘删除                     |
| `iframe-reload-requested`            | 项目代码因切换聊天即将调用 `reloadIframe()`                |
| `iframe-pagehide`                    | 武侠前端 iframe 即将卸载                                   |
| `iframe-boot`                        | 新武侠 iframe 已启动，并记录上一个刷新原因                 |
| `automation-instance-ready/disposed` | 自动化实例创建或销毁                                       |

换代原因格式：

- `reloadIframe:chat-changed`：切换了聊天。
- `external-or-unknown`：没有经过项目内已标记入口，重点检查手动刷新、酒馆重绘或实时监听热更新。

常见判断：

1. 有 `turn-lock-requested`，没有 `turn-lock-acquired`：隐藏楼层脚本未收到事件或仍是旧版本。
2. 已有 `turn-lock-acquired`，随后出现新的
   `hidden-floor-script-boot`，但没有正常解锁：后台脚本在回合中被重新加载，内存锁丢失。
3. 锁仍有效时只出现 `stable-shell-collapse-deferred-by-turn-lock`：保护正常工作。
4. `iframe-pagehide` 的原因是 `external-or-unknown`：刷新来自回合锁控制范围之外。
5. 正常完成应依次看到 ACK、正文返回、assistant 楼层和解锁；同一聊天不应随后出现 `iframe-pagehide`、`iframe-boot` 或新的 automation instance。

- 手动发送一轮
- 自动推进至少两轮
- 重新生成一次

## 历史事件封存与写入时序取证（只读）

为定位“同一 MK 重算后事件状态不同”，增加三组 `history-event-forensics` 诊断：

- `era-transaction-before`、`era-transaction-confirmed`、`era-transaction-reread-confirmed`：
  事件脚本通过 `writeEraTransaction()` 发起事务前、ERA 确认后或超时回读确认后；
  记录 `transactionId`、`reason`、`chatId`、`messageId`、`selectedMk`、
  实际 `confirmedMessageId/confirmedMk`（如有）、动作类型和事件路径。
- `history-node-sealed`：`finalizeCurrentTurn()` 成功保存历史节点之后，
  记录 `nodeId`、`messageId`、`mk`、`sealedEventStateHash`、
  `sealedEventSystemHash` 及当时事件指纹。
- `direct-event-write`：项目直接写入真实改动了六大事件根时，记录
  `source`、`reason`、`writeId`、变更路径及同一变量事务内的 `before/after` 指纹。

`eventSnapshot` / `before` / `after` 提供与历史树校验**相同的 16 位算法**：
`eventStateHash`、`eventSystemHash`、事件五个分组 `eventBuckets`、
每个进行中事件的名称和指纹（`ongoingEvents`）及各人物占用的事件名和指纹
（`characterOccupancy`）。最多展示前 16 个事件及 16 个人物，有明确省略数量。
不记录事件内容、位置、入场时间的具体值，不影响真实写入或历史封存。

为避免 ERA 的逐叶 `event-insert-skipped` 刷掉有价值的时序证据，
这些记录另存在 `localStorage['wuxia_history_event_forensics_v1']`（最近 120 条）。
跨 iframe 和独立 bundle 共享；不要在复测前清空。仅记录新运行版本之后实际发生的写入，
过去没有取证的楼层无法凭当前数据追溯首次写入。

在游戏 iframe 控制台执行：

```js
(() => {
  const all = JSON.parse(localStorage.getItem('wuxia_history_event_forensics_v1') || '[]');
  const rows = all.map(entry => ({
    time: entry.isoTime,
    stage: entry.details?.stage,
    ...entry.details,
  }));
  copy(JSON.stringify(rows, null, 2));
  console.log('已复制历史事件取证', {
    records: rows.length,
    phases: [...new Set(rows.map(row => row.stage))],
  });
})();
```

推荐测试：根目录构建（含 ERA、武侠与事件脚本）→ 刷新 → 正常生成至少一个
事件开始/结束回合 → 封存节点 → 再试一次历史分叉 → 导出上述 JSON。
先比对同一事务的 before/confirmed，再把确认后的指纹与节点封存指纹对照；
如果节点封存以后出现 `direct-event-write` 或新的事件事务，可据此找出改变时刻。
若只有已存在路径导致插入跳过，没有实际写入，不能把 skip 当作事件启动事务。
