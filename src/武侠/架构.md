# 金庸群侠传前端架构入口

## 文档用途

本文件只保留稳定边界、关键入口和阅读顺序，不复述实现细节。

## 项目边界

> **当前开发阶段：测试版，尚未正式上线。** 目前没有已发布用户版本与历史配置的迁移压力；涉及默认值、提示词结构、设置结构或运行模式的架构调整，优先直接收敛到当前认为正确的方案，不为未上线旧行为额外保留兼容/迁移层。除非后续明确进入发布阶段或某项改动另有兼容要求，否则不要默认设计旧配置迁移逻辑。

金庸群侠传是运行在酒馆助手无沙盒 iframe 中的 React 武侠 RPG 前端。

- 聊天楼层保存 user/assistant 消息与 swipe。
- 聊天级 `stat_data` 保存当前游戏持久变量。
- React `GameState` 只是 UI 投影，不是持久源，也不是差分依据。
- 普通变量写入分两类：可回滚 ERA 写入、可重算或非版本化的酒馆助手变量函数直接写入。
- 消息边界事件负责刷新与兜底，不负责代替真实写入。
- 初始化链路独立于普通回合写入链路。

## 核心约定

### 1. `stat_data` 是唯一差分真相源

- 差分、写入验证统一以 `getVariables({ type: 'chat' }).stat_data` 为准。
- `getAllVariables()` 只用于读取合并视图并投影到 `GameState`。
- sourced write event 可以携带由 writer 在自己的 stat_data 事务边界内计算出的实际 diff；它是对真相源差分的运输，不是独立真相源。
- 不要用 React 状态、未匹配的原始事件 payload 或临时缓存判断“是否真的写入成功”。

### 2. 普通操作优先走 ERA

- AI 变量块、额外变量、功法普通操作、境界普通操作、后台补全，统一视为 ERA 写入链路。
- ERA 写入完成后等待匹配的 `era:writeDone`，再重读聊天级 `stat_data`。
- 同一事件开始、参与或结算涉及的多个对象操作使用 `era:transactionByObject`
  一次提交，必须保持 operation 顺序并只产生一次消息/API/EditLog 完成链。
- 事件、参与记录、人物占用、角色差分、世界归档和后续线索都是分支敏感状态，不得在正常流程中 direct write。

### 3. 直接写入走变量函数 + 专用事件

- 变量编辑器或其他直接聊天变量修改，使用酒馆助手变量函数，例如 `updateVariablesWith()`。
- 项目内 direct write 优先统一经过 `writeDirectChatTransaction()`，在同一个 updater 内复制 before/after `stat_data` 并计算本次 writer 自己的实际 diff。
- 直接写入完成后发 `wuxia:directVariableWriteDone`，携带 `source/reason/changes`；观测事件监听器失败不得反向否定已完成的业务写入。
- 直接写入不得伪造 `era:writeDone`。
- ERA sourced wrapper 在发出 ERA 事件前记录 before，精确匹配自己的 `era:writeDone` 后读取 after，再发送 `wuxia:eraVariableWriteDone` 的 `source/reason/changes`。
- ERA 的 before/after 等待窗口可能与 AI 或其他后台写入交错，因此 `changes` 必须再按本次 ERA payload/transaction operations 的目标路径裁剪；禁止把等待窗口内无关路径归给当前 source。
- 变量变更 tracker 不再用共享的“上次快照 → 当前快照”给 source 猜归属；有 `changes` 时直接记账，只有旧事件缺少 `changes` 时才走兼容 fallback。
- AI 身份与后台来源分开判定：变量更新固定由独立额外变量模型承担；正文模型中的 `VariableThink / VariableInsert / VariableEdit / VariableDelete` 永远不作为 AI 变量声明来源。即使额外变量模型合法返回 0 个动作，也不得回退或改认正文变量块。
- 正文模型返回后、变量模型请求前统计可见正文（去除选项/标签/空白）；少于 300 字时本轮登记为空 AI 变量声明并直接跳过额外变量模型，300 字及以上才允许发起变量模型请求。
- 最终 assistant 变量块减去 AI 模型变量块，只用于后台楼层块完整性校验；最终 `stat_data` 负责 AI 是否落地及漏 instrumentation 的最终兜底。
- 同路径楼层 fallback 的 before 必须来自真实观测到的 AI checkpoint 或已记录后台写入，不能用 AI 声明值冒充实际历史状态。

### 4. 消息边界只做兜底

- `MESSAGE_RECEIVED`、`MESSAGE_UPDATED`、`MESSAGE_SWIPED`、`CHAT_CHANGED` 用于刷新正文、选项和补偿重读。
- 当写入完成事件缺失、延迟或来自外部操作时，消息边界负责兜底重读 `stat_data`。

### 5. 同一聊天固定 iframe 宿主

- 隐藏楼层脚本在当前聊天首次折叠时采用一个宿主 DOM，后续只删除其他楼层，不改写宿主 `mesid`，不调用
  `refreshOneMessage()`。
- 回合 lifecycle、ACK 和超时继续协调 ERA 屏障与楼层清理；它们不负责把宿主同步到最新楼层。
- 查看或覆写 assistant 原文必须直接读取聊天数据，并使用
  `setChatMessages(..., { refresh: 'none' })`；聊天切换和历史 checkout 才允许正常 iframe 换代。
- 主页面正文可在当前聊天的可用 assistant 回合之间前后浏览，也可按 User/Assistant 楼层号跳转；浏览只改变 React 的正文投影，不切换聊天、不改宿主 `mesid`。楼层校订允许修改该回合配对 User active swipe 与 Assistant active swipe；Assistant `<era_data>` 保持只读，变量动作块变更后必须执行 ERA `manual_sync`。

### 6. 初始化独立

- 新游戏初始化、开局建档、已有存档接管是独立链路。
- 初始化负责建立首份可用 `stat_data` 与界面初值，不与普通功法/境界操作混成一条规则。
- 角色创建页的本地“存档”是可重复加载、可继续修改的创建方案，不是聊天游戏存档。方案必须保存完整结算上下文（最终选择、抽取/洗炼来源、已支付点数、命盘与免费洗炼/保底状态、武缘来源与费用、自定义境界等）；加载后进入确认页，但允许逐步返回任意创建步骤继续编辑，不因曾用于开局而自动删除或锁定。
- 开局自定义地点的前三段必须来自统一 `武侠地点表.yaml`，创建页使用“一级大域 → 二级区域 → 三级地点”联动选择，不允许自由输入或另建地点枚举；最终仍持久化为 `一级/二级/三级` 完整路径，后续继续复用统一地点校验与地图体系。
- 开局武功的随机路线统一为“武缘三择一”：每次寻访固定消耗 5 点，从当前合法且未选择的武功池中随机显现最多 3 门不重复候选；玩家最多承下一门，也可以不选直接继续或主动放弃本次候选，已支付的 5 点不返还。承下的武功锁定且不再追加品阶点数。按谱直接选择仍按武功品阶消耗点数并允许取消返还，两条路线共用同一总点数池。
- 自定义出身的起始境界仍持久化为完整境界字符串，但创建页交互拆为“大境界 → 小境界”两个紧凑选择栏；切换大境界时优先保留同名小阶段，避免把全部完整境界塞进单一长列表。
- 已有聊天初始化不得 direct 补做应归属于历史楼层的事件结算；聊天切换先等待 ERA 路径同步，再重算 direct 派生字段。
- 玩家七维初始属性统一使用 `0～20` 刻度，福缘不再使用旧版 `-6～14` 特殊刻度；开局基础值统一为 6、共用同一套阶梯点数规则。旧聊天与旧角色配置仅迁移一次：旧福缘 `+6`，聊天以 `前端变量.福缘刻度版本 = 2` 标记完成，保证强弱档位与原存档一致。
- 奇经八脉交会穴对七维初始属性统一以 20 为上限；达到 20 后继续命中关窍时按该脉既有最终属性 `+6%` fallback 处理。

### 7. 历史树不保存状态快照

- 角色级 `wuxia_history_tree_v2` 只保存聊天/楼层/swipe locator、父子边、短预览和校验哈希。
- 每个成功完成事件处理的 assistant swipe 自动成为节点；题名和钉住不创建 checkpoint。
- 仅从历史节点继续时创建原生 branch chat；原聊天未来不修改。
- checkout 使用 120 秒 localStorage journal 跨 iframe 重载续接，并在 ERA full sync 与哈希校验完成前锁定新回合。
- 历史树按角色累积所有历史局的节点；谱牒默认用 `filterTreeToRelatedComponent`
  只展示与当前聊天连通的脉络（沿 parentId 无向连通分量），工具栏可切换"显示全部行迹"。过滤仅作用于展示，不改动持久化数据。
- `manual_full_sync` 在 ERA 框架内是异步合批任务；checkout 发起时必须携带唯一 `syncId`，只认 ERA 在
  `era:writeDone(actions.resync)` 的 `syncIds`
  中回传该 ID 的信号（写入链再静默一段时间）才能进行事件检查与封存校验。不能以 `eventEmit` 返回、也不能以任意一次 resync
  writeDone 作为完成信号——`/branch-create` 切聊天触发的 `chat_changed` 增量同步同样会发 resync
  writeDone，误认会让校验跑在完全重算中途的状态上。
- 变量状态由聊天路径、ERA `SelectedMks`/`EditLogs` 与可重算缓存恢复，不保存逐节点 `stat_data` 补丁。

### 8. 聊天改名是独立的聊天生命周期事务

- 实际酒馆聊天存档的改名不属于 ERA、普通变量写入或节点题名。它调用 `SillyTavern.renameChat()`，会导致 iframe 换代。
- 主档仅在初始化成功后给出一次命名窗，默认 `角色名 · 开局地点`；关闭或“保留当前名称”直接进入开局。
- 只有 `fork_branch`
  的新聊天自动命名：根卷名加节点题名，未题名时按父链长度使用“第 N 段”；既有分支切换、原地 swipe 和普通节点绝不改名。
- `wuxia_chat_rename_journal_v1`
  在 localStorage 中保存 120 秒改名事务。新 iframe 必须验证真实新聊天身份和名称后，原子迁移历史 locator/branch、头像缓存与未发送分叉草稿；失效或身份不符时不得迁移。
- 改名期间发送、重新生成、checkout 与前端派生变量写入均暂停。自动分支命名失败仅保留酒馆自动名称，不回滚已校验提交的分支。

### 9. 模型失败只在安全请求边界重试

- 正文发送、正文重新生成和额外变量模型遇到 HTTP 429 时，首次失败后最多自动重试 2 次；真实玩家发送与自动化 `runTurn()`
  共用该请求级策略，人物经历自动总结不参与。
- 优先遵循服务端 `Retry-After`，无法取得时依次等待 1 秒、2 秒。普通手动发送的非 429 错误不得自动重试。
- 设置页自动推进还会对正文模型和额外变量模型的非 429 请求异常、空回复与落盘前响应校验失败最多重试 2 次，依次等待 1 秒、2 秒。
- 额外变量模型回复必须在追加变量块前完成格式与安全校验；正文模型不承担变量动作生成、校验或写入。楼层、变量块或 ERA 写入已经发生后的失败不得重放。
- 重试必须包住单次模型请求，且位于楼层、swipe、变量块和 ERA 持久化写入之前，避免同一逻辑回合重复落盘。
- CLI、Relay、浏览器桥和 `WuxiaAutomation.runTurn()` 不得重放整个回合；结果未知时必须读取快照对账。

### 10. 事件通知使用可选前端适配器

- 事件脚本通过版本化通知桥发布结构化 `EventNotice`，武侠前端以 `registerAdapter()` 注册当前 iframe 的展示器。
- 通知桥使用动态全局名和 `discover / ready / disposed`
  握手应对事件脚本与楼层 iframe 独立换代；只允许最新挂载的前端实例接管展示。
- 适配器同步返回 `true` 才表示已接管；缺失、拒绝、版本不兼容或抛错时立即回退酒馆 `toastr`，不得等待前端或影响事件事务。
- 前端事件通知栈与生成中/请求错误使用的 `StatusToast` 相互独立，通知关闭和超时没有确认、取消或回滚语义。

### 11. 势力系统与武学谱系规范

- **极简持久化与纯函数衍生**：17 大门派/体系、182 个武学传承节点（入门/基础/进阶/核心/镇派五层）及掌门/传人名单作为静态数据（`sects.json` / `门派功法谱系.json`），绝不在存档中冗余存放。NPC 势力归属由 `角色数据[NPC名].身份` 与静态名单纯函数动态聚类。
- **玩家势力持久化**：玩家数据统一存放于 `stat_data.user数据.势力`，以势力名直接作为 Key，不设置主势力，也不使用 `当前主势力 / 所属势力` 包装层：
  ```json
  {
    "全真教": {
      "体系类型": "宗门",
      "身份": "三代亲传弟子",
      "师承": "丘处机",
      "贡献": 150,
      "状态": "在籍"
    },
    "桃花岛": {
      "体系类型": "世家",
      "身份": "记名门客",
      "师承": "黄药师",
      "贡献": 50,
      "状态": "记名"
    }
  }
  ```
- **贡献字段统一**：运行时统一使用数值字段 `贡献`；宗门的“门派贡献”、帮会的“帮贡”、行伍的“军功”、世家的“家族声望”等差异只在 UI 显示层体现。
- **交互动作回退安全**：拜师、投身、请教、切磋、晋升动作均采用「自动发送一轮 User 消息 + 消息体内嵌 ERA 变更块」机制；玩家行动陈述必须保持简洁客观（如 `User向师尊丘处机请教《全真剑法》`），严禁预设主观对白，为 AI 演绎保留空间。
- **兼容金庸式奇遇**：势力只约束对应组织内的正统拜师、晋阶与差事路线，玩家仍可通过野外奇遇、秘籍或高人指点自由兼修其他武学。

### 12. 任务系统与同级任务变量规范

- **系统定位**：任务系统初期作为势力系统的下属差事模块（`<SectTaskList />`），后续可平滑独立为历练/江湖悬赏模块；变量设计保持架构通用。
- **正式任务与候选池分层**：玩家已经接取的任务继续采用与 `stat_data.参与事件` 平级的顶层键值对结构（`stat_data.任务`），以任务名为唯一键防重复；尚未接取的候选差事统一存放在 `stat_data.前端变量.可选任务.【势力名】`。候选池中的每个任务对象与正式 `任务.【任务名】` **完全同构**，不增加 id、生成时间、难度等中间字段。常规变量 AI 不得新增或删除正式任务，只允许修改已有正式任务的 `任务执行情况`：
  ```json
  {
    "任务": {
      "终南豺狼谷除狼患": {
        "所属势力": "全真教",
        "任务详情": "近日终南山豺狼谷常有恶狼盘踞侵扰山民，速去剿除恶狼，护持山门清宁。",
        "任务地点": "大宋/终南山/豺狼谷",
        "任务执行情况": "未到达地点",
        "任务奖励": {
          "贡献增量": 30,
          "修为增量": 50,
          "获得物品": {
            "铜钱": {
              "类型": "杂物",
              "品阶": "凡品",
              "物品描述": "流通铜钱。",
              "数量": 200
            }
          }
        }
      }
    }
  }
  ```
- **候选差事生成与接取**：玩家点击“查看/刷新差事”时，不创建 User/Assistant 聊天楼层；前端调用与额外变量模型同一套后台 API 配置，使用专门任务结构提示词一次生成多个候选差事，经地点白名单与结构校验后用 ERA 写入 `前端变量.可选任务.【势力名】`，并把本次查看到的差事信息追加到 Command Queue。玩家点击某个候选差事的“接取”后，不再调用 AI，由前端 ERA 原子事务把该任务原结构写入顶层 `任务.【任务名】`，同时从对应候选池移除，并追加一条已接取的叙事指令。
- **提示词边界**：候选任务的完整变量结构模板只存在于后台任务生成请求中，严禁塞入正文 User 输入；正文模型只会在玩家下一次真实发言时通过 Command Queue 获知“查看了哪些差事 / 已接下哪项差事”的叙事事实。
- **执行状态流转**：正式接取后从 `"未到达地点"` $\rightarrow$ `"进行中"` $\rightarrow$ `"已完成"`。
- **双通道结算机制**：
  1. 通道 1（前端即时 ERA 事务）：前端直接读取 `任务[任务名].任务奖励`，发起 `era:transactionByObject` 执行奖励差分（如增加贡献、修为、物品），并从 `stat_data.任务` 中删除该任务键；
  2. 通道 2（指令栏剧情回填）：向指令栏 Command Queue 追加待发送提示词（如师门长辈验看成果并嘉许），确保剧情演进与数值结算兼顾。

### 13. 三部曲世界观与奇遇事件（Encounter）体系

- **三部曲全系覆盖**：编年事件体系从最初的射雕-神雕双线正式扩展为涵盖《天龙八部》（约 1092 年）、《射雕英雄传》（约 1200 年）、《神雕侠侣》（约 1238 年）的三部曲完整历史底稿（共 1119 条事件资产，含 1010 条普通开局事件）。
- **统一全域地理**：由 `武侠地点表.yaml` 与 `mapCoordinates.ts` 动态构建覆盖大理、吐蕃、西夏、辽国、金国、大宋、西域、蒙古、海外九大政权/大域的完整网格，全部事件地点 100% 严格合法。
- **18 条跨部奇遇事件（`kind: encounter`）**：三部小说各设 6 条专属奇遇（共 18 条），采用 `conditional: true` 动态条件触发。奇遇不作为新游戏开局普通事件（`kind: ordinary`），主要提供特定机缘、风味体验与受控功法/物品奖励，绝不轻易泛滥发放唯一绝学。

### 14. 角色天赋（Traits）机制规范

- **持久化位置**：`stat_data.user数据.天赋` 存储 `{ [天赋名]: "天赋描述" }` 键值映射。
- **统一分类**：天赋分类只保留 `天资 / 体质 / 性情 / 气质 / 命格 / 缺陷`；旧的“经历 / 专长”不再作为机制分类，按特质本质归并到上述六类。
- **两轴递推定阶**：正面天赋的品阶不再只看单一数值，而是分别评估“机械收益”和“Prompt 收益”两个轴。两轴各按 `无=0 / 弱=1 / 中=2 / 强=3 / 极强=4` 估值，同轴多个弱收益可以合并抬升强度；综合强度 `0/1/2/3/4/5+` 依次对应 `粗浅/传家/上乘/镇派/绝世/传说`，花费固定为 `3/8/14/18/24/30`。弱机械与弱 Prompt 同时存在时，应自然递推到上乘，而不是继续按单一效果压在传家。
- **缺陷先判极性**：数值、硬限制或 Prompt 的核心结果如果属于净负面，统一进入“缺陷（残缺档）”，再按轻度/中度/重度/绝灭四档返还 `-3 / -6 / -10 / -20` 点；少量补偿收益不改变其主体为缺陷的判断。
- **Prompt 可以承担真实机制**：并非所有复杂剧情效果都要求前端结构化。关系倾向、因果偏置、情境倍率、免疫/护持、NPC 行为影响等难以可靠编码的效果允许继续只存在于 `description / flavorPrompt` 中；但定阶时必须按它真实能带来的收益强度计算，不能因为“只写在 Prompt”就视作纯风味降阶。
- **结构化机制仍优先纯函数折算**：适合确定性计算的百分比属性加成/扣减、功法修炼/升级限制、熟练度折扣等继续由天赋数据库提供，并在 `calculateAllAttributes` / `variableReader` 中纯函数合流；Prompt 不得重复把已经折算进面板的战力再额外放大。
- **七维统一刻度**：属性极值触发天赋全部以当前 `0～20` 七维刻度判断，福缘与其他六维一致使用 `0～1 / 2～5 / 13～16 / 17～20` 四档，不再保留旧 `-6～14` 福缘区间。

### 15. 小总结、大总结、叙事记忆与人物经历分层

- **小总结是一层 Assistant 对应一份摘要**：卡内摘要模式由世界书条目“对话摘要指令”要求 assistant 在本层正文后追加独立 `<summary>`；兼容预设模式则读取玩家预设实际生成的 XML 摘要标签。最近 N 条 assistant 回复向模型保留正文并移除小总结，更早且已有小总结的回复仅保留小总结。
- **小总结补完只补缺失楼层**：设置页“小总结补完工作台”扫描当前聊天每个可用 Assistant 的 active swipe；每次把 5～10 个连续 Assistant 楼层作为一批，以 JSON 携带 `message_id / needs_summary / content / existing_summary`。中间已经有小总结的楼层仍作为连续剧情上下文输入，但禁止重写；模型只按 `message_id` 返回缺失楼层的小总结。完整 JSON 可以部分成功，漏返回楼层继续保持缺失；JSON 截断、API/内容过滤报错或写后回读失败都记录在工作台，不能把失败楼层标成已有小总结。
- **小总结补完允许受控追加，但不得改写正文**：补完成功时只向目标 Assistant 当前 active swipe 的正文与 ERA 变量块之间插入对应摘要 XML，并同步该楼 `message` 字段；其它 swipe、正文内容与变量块保持原样。只有写入后重新读取并检测到有效摘要标签，才算该楼补完成功。
- **大总结是“小总结的总结”**：较旧的小总结按固定批次经额外模型继续压成章节记忆，写入 `stat_data.叙事记忆.章节摘要`，并同步 `已归档至楼层` / `已归档摘要数`。大总结归档必须走 ERA 事务；世界书“记忆区”只负责把章节记忆投影到稳定提示词位置。
- **大总结不得改写历史楼层**：章节归档后，`CHAT_COMPLETION_PROMPT_READY` 只在本次最终提示词中裁掉已经由大总结覆盖的旧小总结及其配对 user 消息；大总结本身不得为了压缩去重写聊天正文、swipe 或历史树内容。旧版“原始旧聊天直接回溯成章节记忆”的实现只保留兼容代码，不再作为设置页的小总结补完入口。
- **世界事件是客观史册**：已完成大事件继续由 `stat_data.世界事件` 保存时间、地点和最终概要；`参与事件.结局`只是事件进行中的可修改工作区，完成后归档并删除，不作为第三份长期聊天摘要。
- **人物经历只记个人长期影响**：普通对话、短时情绪和连续场景动作不得逐回合写入。新经历值以游戏内日期前缀 `(年.月.日) 内容` 保存；自动压缩只处理最旧原始条目、保留近期条目，并把旧批次替换为不会再次参与压缩的 `阶段经历N`。

### 16. 世界知识与派生上下文分层

- **世界背景只保存稳定常识**：`世界背景.yaml` 使用 `<世界背景>` 作为正文侧稳定知识锚点，负责世界基本规则、NPC 认知边界、朝廷与江湖的一般关系，以及九个一级世界大域的长期风貌。当前君主、掌门、战争、国界、人物生死、盟敌与势力兴衰属于动态事实，必须服从当前变量、世界事件、游戏时间和实际剧情。
- **势力使用绿灯按需注入**：17 个核心势力各自使用独立世界书条目，扫描最近 3 楼关键词；条目禁止互相递归激活。势力条目只描述组织性质、长期风格、接触规则和信息边界，不重复武学数据库数值，也不静态写死当前首领与关系。
- **重要地点由当前位置纯函数派生**：`data/locationLore.ts` 以严格三级路径保存少量关键地点的稳定背景；`frontendDerivedVariables.ts` 根据 `user数据.所在位置` 生成 `前端变量.当前地点信息`。第四级场景变化不改变三级地点背景，未命中资料库时写为 `null`，不得残留上一地点资料。
- **派生缓存不是历史事实**：`前端变量.周围地点 / 当前地点信息 / 战力区 / 修为变化参考` 都可由真实状态重新计算，不进入 ERA 历史语义。checkout、聊天切换或真实状态恢复后重新计算即可。
- **玩家变量变更条过滤派生缓存**：上述纯派生缓存及旧版 `前端变量.随机数` 不进入玩家可见的 AI/后台实际变化、数量统计和异常统计；`奇经八脉`、`永久属性修正` 等真实前端状态仍正常追踪。统一路径分类位于 `frontendVariableKeys.ts`，不得按整个 `前端变量` 顶级对象粗暴过滤。
- **随机数属于请求级上下文**：战斗随机数在 `战斗骰子.txt` 准备本次模型提示词时即时生成，每次模型请求独立取值，不再持久化到 `stat_data`。派生同步会清理旧存档残留的 `前端变量.随机数`。

## 双模型提示词边界

- **正文模型与变量模型职责彻底分离**：正文模型只负责剧情正文与叙事输出；变量模型只负责根据本轮 User 输入、Assistant 正文和当前状态判断持久变量变化。变量更新只有独立额外变量模型这一条正式链路。
- **正文上下文继续由酒馆默认提示词链路与世界书组装**：正文侧的动态状态提示保留在世界书体系中，允许使用 EJS / ERA 宏进行条件渲染；其最终送模文本应使用稳定 XML 标签作为语义锚点，并尽量采用紧凑、统一、低 token 的结构。正文提示中不得继续保留 VariableThink / VariableInsert / VariableEdit / VariableDelete 等变量更新协议和仅服务变量写入的权限说明。
- **正文状态投影只保留叙事所需事实**：例如当前时间、玩家状态、当前事件、正式任务、后续线索、附近传闻、当前地点背景、可用地点、相关人物等。正文侧不按“本轮是否必用”动态裁剪功法、包裹、势力、人物经历、关系网等长期叙事资料；只剔除纯变量结算、纯前端来源和变量操作元数据。参与事件只注入叙事详情与已有结局，不注入 `insert / update / delete` 差分快照；正式任务注入所属势力、任务详情、任务地点与执行情况，不注入机械任务奖励。
- **XML 标签只作为提示词的顶层定位锚点**：正文侧继续用少量稳定 XML 标签定位语义块，标签内部统一优先使用去除无歧义引号、逗号和大括号的紧凑 YAML；单值时间可直接写为 `<时间>1202年3月16日 15时45分</时间>`。正文不再注入整个 `世界信息` 对象，只注入当前时间；`<可用地点>` 只暴露当前地点、活动区与合并去重后的可前往地点，不暴露“普通移动 / 事件目标 / 地图指定”等前端来源分类。变量模型的 `<variable>` 内继续采用“真实路径标题 + 紧凑对象 + 压缩记录”表达：复杂可写状态用去除无歧义引号的紧凑对象，只读元数据用 `键:值|键:值` 压缩记录，事件/任务先给完整真实路径再给只读记录与 `可写:{...}`，避免细粒度 XML 与重复路径造成 token 浪费。
- **变量模型上下文由前端代码独立构建，不依赖世界书 EJS**：TypeScript 只负责安全读取、筛选和确定性格式化；`变量输入模板.txt` 负责前序轮次/本轮 User/本轮正文与变量数据块的组合，`变量数据格式.txt` 专门负责 `<variable>` 内各动态 slot 的排列与根键。动态变量数据统一按真实对象层级输出紧凑嵌套对象，不再用 `user数据.初始属性`、`参与事件.【事件名】` 等点路径标题模拟结构；参与事件直接输出 `参与事件:{【事件名】:{描述,地点,结局,insert,update,delete}}`，任务、玩家、角色等同理。变量数据格式、变量输入模板与变量指导均支持 `@if slot / @else / @endif` 条件块，条件按对应 slot 是否非空判定。叙事表现标尺位于前序轮次之前；前序轮次、本轮 User、本轮正文直接传纯文本；参与事件/任务不存在时对应块省略。
- **变量上下文组装规则必须可在设置页方便修改**：底层读取、筛选、权限和安全约束由 TypeScript 保证；展示结构和 section 组合顺序使用轻量模板/声明式配置表达，目标是接近伪代码而非要求用户编辑 TypeScript。设置页可恢复项目内置默认配置。
- **变量提示词占位符必须可检查**：设置页展示 `{{latestUserBody}}`、`{{playerContext}}`、`{{participationEvents}}`、`{{tasks}}`、`{{locationContext}}`、`{{relevantCharacters}}` 等可用占位符时，应允许点击查看语义说明、数据来源/筛选规则、空值行为和当前聊天实际预览；默认模板升级时只自动替换项目旧默认，玩家自定义模板保持原样。
- **「变量模板」「变量指导」退出世界书**：改为项目内置默认资源，并允许设置页覆盖；变量模型主提示词同样由设置维护。项目内置源码位于 `src/武侠/prompts/变量输入模板.txt`、`变量数据格式.txt`、`变量主提示词.txt`、`变量模板.txt`、`变量指导.txt`，通过 `?raw` 导入，开发时可直接查看和修改文本文件；其中 `变量数据格式.txt` 是实际动态变量数据的运行时排版模板，`variablePromptDefaults.ts` 负责导入与历史默认签名迁移。变量模板只定义路径/结构/权限，复杂示例压成局部结构；静态 schema 中枚举统一写 `enum(...)`、类型并集写 `oneof(...)`、权限写 `[权限]`，不再复用 `|` 或 `/` 承担多种结构语义；变量检查清单、最终执行要求与输出协议统一归入变量指导，避免代码硬编码与多份规则互相冲突。额外变量模型的 300 字可见正文阈值及现有两阶段生成/提示 UI 保持现状。

## 稳定约束

1. 持久游戏状态必须落在聊天变量或聊天楼层，不能只改 React 状态。
2. `readGameDataPure()` 只读；补全写回单独调度。
3. 变量值差分只认聊天级 `stat_data`；AI 变量声明只认独立额外变量模型输出块，正文模型变量块不参与 AI 身份判定；后台具体来源只认统一写入包装显式传入的 `source / reason`。
4. 普通功法/境界操作走 ERA；初始化独立。
5. 直接写入必须通过统一 direct 包装并发 `wuxia:directVariableWriteDone`；ERA 项目写入通过统一等待包装在 raw `era:writeDone` 匹配后发唯一 `wuxia:eraVariableWriteDone` 来源事件。raw `era:writeDone` 不参与玩家变量条归因。
6. 消息边界与 baseline→final 只负责兜底补齐真实变化，不得伪造 event-script/frontend/variable-editor 等具体来源；重新生成的 baseline 必须在旧 swipe 回滚完成后建立。
7. AI 自动化必须复用真实玩家发送链；写入结论仍以最终 `stat_data` 和变量比较为准。
8. 创建真实 user 楼层前必须取得隐藏楼层脚本的回合锁 ACK；同一聊天不得主动重绑固定宿主，iframe 生命周期诊断必须跨换代持久化。
9. 模型 429 与设置页自动推进的普通模型失败最多各重试 2 次，且重试边界不得包含任何聊天楼层、swipe、ERA 持久化写入或整轮自动化调用。
10. 历史节点不保存状态补丁；分支敏感事件状态必须由 ERA 事务进入消息历史，direct
    write 仅用于派生、根初始化、版本迁移或非版本化用户操作。
11. 历史 checkout journal 存在且未超时时，任何发送、重新生成和事件检查都必须暂停；失败不得静默生成。
12. 聊天改名 journal 存在且未超时时，任何发送、重新生成、checkout 和前端派生变量写入都必须暂停；只有验证新旧聊天身份后才可迁移引用。
13. 节点题名只属于历史树元数据，不能作为普通节点触发酒馆聊天改名；实际聊天改名只发生在主档初始化、`fork_branch`
    自动命名和用户手动操作。
14. 事件通知适配失败只能回退酒馆弹窗，不能中断或改变事件读写链；旧前端实例不得覆盖新实例。
15. 奇经八脉至少达到二流初期方可冲穴，进度属于分支敏感状态；修为扣除、进度和关窍初始属性变化必须由同一个 ERA 事务提交并按 transactionId 精确确认。
16. 提前十天可发现事件由事件脚本写入
    `前端变量.可发现事件`；它是可重算的前端只读预告，不得提前写成进行中或参与事件，也不得混入附近传闻提示词。十天窗口内同一传闻区域（地点前两级）若同时出现一串候选，只公开时间最早的一条；该区域首事件仍在进行时继续阻塞后续预告，待其退出进行中后下一条才浮现。前端必须区分“附近传闻 / 江湖风闻 / 后续线索”语义，不得再把三者渲染成完全相同的线索样式。
17. 势力系统与任务系统严格区分持久化分层：玩家**已接取**的势力差事统一存储于顶层 `stat_data.任务`（与 `stat_data.参与事件` 平级）；后台生成但尚未接取的候选差事存储于 `stat_data.前端变量.可选任务.【势力名】`，候选任务对象与正式任务完全同构；玩家势力归属存储于扁平的 `user数据.势力.【势力名】`。不设置主势力，不使用 `当前主势力 / 所属势力` 包装层；17 大门派 182 个武学传承节点与成员谱系为静态只读资产，禁止把全量谱系冗余写入聊天存档。
18. 任务结算必须走前端即时 ERA 事务与指令栏 Command Queue 剧情回填双通道，自动按差分执行 `insert / update` 并清理任务键，严禁私自绕过差分修改底层未定义结构。
19. 奇遇事件（`kind: encounter`）采用动态条件触发（`conditional: true`），只作为大世界游历偶发机缘，不作为新开局普通主线事件（`kind: ordinary`）；奇遇功法/物品奖励受严格品阶与师承唯一性边界约束。
20. 角色天赋（Traits）在读取与计算时由纯函数（`traitsDatabase.ts` / `attributeCalculator.ts`）动态合流折算战力属性与升级折扣；功法学习限制（如经脉尽断禁止修内功）在开局初始化与后续学艺时必须严格校验拦截。
21. 对话压缩分为“小总结 / 大总结”两层：小总结补完只能向缺失摘要的旧 Assistant 当前 active swipe 受控追加摘要 XML，不得改写正文、其它 swipe 或 ERA 变量块，且必须写后回读确认；大总结不得改写任何旧聊天楼层，只能写入聊天级 `stat_data.叙事记忆` 并在最终 prompt 中裁剪已覆盖的旧小总结。小总结、大总结、`世界事件` 与 `人物经历` 必须保持各自职责。
22. “无用模块过滤”从当前预设显示正则中自动识别可成对清理的 XML 模块，设置页只展示 XML 标签名，不暴露底层原正则；玩家通过预设级总开关与逐模块勾选决定是否过滤，也可添加自定义 XML 标签。过滤同时作用于新 assistant 回复持久化、`CHAT_COMPLETION_PROMPT_READY` 主模型最终上下文、额外变量模型读取正文，以及小总结补完送模正文；旧版正则签名选择仅作为迁移 fallback。VariableThink / VariableInsert / VariableEdit / VariableDelete / summary / era_data，以及兼容预设模式下配置的摘要标签必须受保护。

23. 世界知识按稳定/动态/派生三层分工：世界背景和势力绿灯只存稳定常识；世界事件与聊天变量保存动态事实；重要地点背景和周围地点由当前位置实时派生。禁止把动态首领、人物生死或战争状态写回静态 lore。
24. 玩家变量变更条不得统计 `前端变量.周围地点 / 当前地点信息 / 战力区 / 修为变化参考 / 旧随机数` 等纯派生缓存；但 AI 若主动声明修改这些只读派生路径，声明本身仍保留用于落地/越权异常判断。
25. 战斗随机数是一次模型请求的临时输入，不属于聊天分支状态；不得重新写入 ERA 或长期 `stat_data`。
