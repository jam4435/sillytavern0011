# 墨剑录 (Ink & Blade) 项目架构文档

## 1. 项目概述

**墨剑录**
是一个基于酒馆助手的沉浸式武侠RPG前端界面，通过读取和生成聊天消息中的变量来驱动游戏状态。本项目利用 React 构建，与酒馆助手的原生功能深度集成。

## 3. 核心概念与实现

### 3.1. 页面流程

```mermaid
graph TD
    Init[App 初始化] -- 检查存档 --> Check{hasSavedGame?};
    Check -- 已开局 --> D[Game];
    Check -- 未开局 --> A[StartScreen];
    A -- 点击 --> B(SplashScreen);
    B -- 新的故事 --> C[NewGameSetup 7步流程];
    C -- 踏入江湖 --> D[Game];
```

**开局检测逻辑**: 检查是否存在 assistant 消息 + user数据特征字段（性别/境界/用户名）

**7步角色创建流程**:

1. 天资选择（决定总点数30/40/55/70）
2. 七维属性分配
3. 天赋选择（含抽卡系统）
4. 武功选择（含抽卡系统）
5. 出身选择
6. 身份设置
7. 确认保存

### 3.2. 状态管理

游戏状态与酒馆聊天记录绑定，实现"存档于楼层"：

- **数据读取**: 使用 `getAllVariables()` API 获取合并后的变量表
- **重要**: 游戏变量存储在 `stat_data` 键下，user数据在 `stat_data.user数据`
- **数据监听**: 通过 `eventOn` 监听 `MESSAGE_RECEIVED` 和 `CHAT_CHANGED` 事件
- **自动补全**: 前端在读取变量时会自动检测并补全缺失的属性和功法信息

### 3.2.1. 前端变量自动补全机制

前端在 `readGameData()` 读取变量时，会自动检测并补全/更新以下数据。

**重要**: 为避免每次消息都触发不必要的更新，系统使用**缓存机制**来检测状态变化，只有当检测到实际变化时才执行更新。

#### 缓存机制

系统维护两个内存缓存来跟踪状态：

| 缓存                   | 键格式                        | 存储内容             | 用途                     |
| ---------------------- | ----------------------------- | -------------------- | ------------------------ |
| `characterStateCache`  | `"玩家"` 或 `"角色:{角色名}"` | 境界、是否存在       | 检测新人物或境界变更     |
| `martialArtStateCache` | `"{拥有者}:{功法名}"`         | 掌握程度、是否已补全 | 检测新功法或掌握程度变动 |

#### 角色属性自动计算 (`autoUpdateCharacterAttributes`)

**触发条件**（基于缓存检测）：

1. **新人物出现** - 缓存中不存在该角色
2. **境界变更** - 缓存中的境界与当前不同

```mermaid
graph LR
    A[读取变量] --> B{缓存检查}
    B -- 新人物 --> C[计算属性]
    B -- 境界变更 --> C
    B -- 无变化 --> E[跳过并更新缓存]
    C --> D{写入方式}
    D -- 属性字段不存在 --> F[era:insertByObject]
    D -- 属性字段存在 --> G[era:updateByObject]
    F --> H[更新缓存]
    G --> H
```

**属性计算公式**: 根据初始属性 + 境界 + 功法加成，计算战斗属性（臂力、根骨、机敏、洞察）和资源属性（气血、内力）

**气血/内力格式**: `"当前值/最大值"` 字符串格式（如 `"800/1000"`）

#### 功法自动补全 (`autoUpdateMartialArts`)

**触发条件**（基于缓存检测）：

1. **新增功法** - 缓存中不存在该功法
2. **掌握程度变动** - 缓存中的掌握程度与当前不同（需要解锁新特性）

AI 生成的功法数据通常只包含功法名和掌握程度，前端根据功法数据库 `data/_合并后功法.json` 自动补全完整信息：

```mermaid
graph LR
    A[读取功法] --> B{缓存检查}
    B -- 新功法 --> C{检查字段完整性}
    B -- 掌握程度变动 --> D[更新特性: era:updateByObject]
    B -- 无变化 --> E[跳过并更新缓存]
    C -- 缺少基本字段 --> F[补全: era:insertByObject]
    C -- 字段完整 --> E
    D --> G[更新缓存]
    F --> G
```

| 场景         | 触发条件                    | 处理方式               | ERA API              |
| ------------ | --------------------------- | ---------------------- | -------------------- |
| **补全**     | 新功法 + 缺少类型/描述/品阶 | 添加不存在的字段       | `era:insertByObject` |
| **更新特性** | 掌握程度变动                | 根据新掌握程度解锁特性 | `era:updateByObject` |
| **跳过**     | 无变化（缓存命中）          | 不执行任何写入         | -                    |

**补全后的功法结构**:

```yaml
功法名:
  类型: '内功/外功/轻功/剑法等'
  功法描述: '功法的详细描述...'
  功法品阶: '粗浅/传家/上乘/镇派/绝世/传说'
  掌握程度: '初窥门径' # 保留AI生成的值
  特性:
    初窥门径: '特性描述...' # 只包含已解锁的特性
```

#### 防重复调用保护

为避免写入触发的 `era:writeDone` 事件导致无限循环，补全函数使用双重保护机制：

1. **标记位锁**:
   - `isUpdatingCharacterAttributes` - 角色属性更新锁
   - `isUpdatingMartialArts` - 功法补全更新锁

2. **缓存机制**: 即使锁被释放，缓存检查也会阻止对未变化数据的重复更新

### 3.3.1. 额外变量更新模式

设置中的 `summarySettings.variableUpdateMode` 控制正文变量更新方式：

| 模式     | 行为                                                                                   | 关键边界              |
| -------- | -------------------------------------------------------------------------------------- | --------------------- |
| `inline` | 默认模式，变量指导世界书照常参与正文生成                                               | 保持旧提示词注入方式  |
| `extra`  | 正文生成时禁用精确条目 `变量指导`，正文写入后额外调用同一套额外模型配置生成 ERA 变量块 | 不新增第二套 API 配置 |

`extra` 模式完整链路：

```mermaid
sequenceDiagram
    participant Frontend as useMessageHandler
    participant WB as 世界书
    participant Tavern as 酒馆消息/生成
    participant Extra as extraVariableUpdateManager
    participant Model as 额外模型
    participant ERA as ERA

    Frontend->>Extra: prepareExtraVariableUpdateTurn(summarySettings)
    Extra->>WB: 精确查找并禁用「变量指导」，记录原始状态快照
    Frontend->>Tavern: generate({should_stream: true})
    Tavern-->>Frontend: 正文回复
    Frontend->>Tavern: 写入 assistant 楼层并立即刷新正文显示
    Frontend->>Extra: executeExtraVariableUpdate(assistantMessageId, latestRawReply)
    Extra->>Extra: 构造最近5层正文 + 渲染后变量上下文 + 变量指导
    Extra->>Model: requestConfiguredText(..., shouldStream:false, skipWIAN:true)
    Model-->>Extra: VariableThink/Insert/Edit/Delete 块
    Extra->>Tavern: 追加合法变量块到目标楼层/当前 swipe
    Extra->>ERA: era:apiWrite
    ERA-->>Extra: era:writeDone
    Extra-->>Frontend: finalMessageText
    Frontend->>Frontend: 重新解析变量块与选项，正文显示剥离变量块
```

额外变量 prompt 的输入约束：

- 最近正文只取最新 5 条有效 assistant 正文，并在发送给额外模型前剥离旧的
  `<VariableThink>`、`<VariableInsert>`、`<VariableEdit>`、`<VariableDelete>` 块。
- `输出提示词` 不把原始模板发给外部模型；先在酒馆前端环境内用
  `EjsTemplate.prepareContext(..., assistantMessageId)`、`EjsTemplate.evaltemplate`、`substitudeMacros` 和 Tavern
  regex 渲染，失败时退回前端构造的变量快照。
- 变量块只接受
  `<VariableThink>`、`<VariableInsert>`、`<VariableEdit>`、`<VariableDelete>`；Insert/Edit/Delete 内必须是严格 JSON 对象。
- 为兼容模型误用说明别名，写入前会把根键 `玩家数据` 归一为 `user数据`，把 `同场景角色` 归一为 `角色数据`。

并发保护：

- `extraVariableUpdateBusy` / `extraVariableUpdateReserved` 防止并发发送和并发变量更新。
- `useSummaryDetection` 在额外变量更新运行中跳过本次自动总结检测，避免总结模型与变量模型同时写入 ERA。
- 重新生成先创建一个不含变量块和旧 MK 的临时 swipe，通过 `manual_sync`
  让 ERA 原生回滚旧 swipe 变量；生成完成后覆盖该临时 swipe，并通过 `era:apiWrite`
  强制按新正文重算变量。任一步失败都会切回原 swipe 并再次执行 `manual_sync` 恢复变量。
- ERA 等待器会同时校验目标 assistant 楼层和 `writeDone.actions`，避免把事件脚本或其他写入产生的 `era:writeDone`
  误认为本次同步完成。

#### 3.6.5. 额外模型与自动总结模块

额外模型配置统一挂在 `DisplaySettings.summarySettings`，由 `settingsManager.ts`
负责 localStorage 迁移与默认值补全。设置页对外显示为“额外模型”，内部按 `API / 自动总结 / 额外变量`
分组；其中 API 配置被自动总结和额外变量更新复用，不拆成两套凭据。

| 模块                            | 职责                                                                                      |
| ------------------------------- | ----------------------------------------------------------------------------------------- |
| `summaryApiClient.ts`           | 提供 `requestConfiguredText` 通用文本请求；`requestSummaryText` 是自动总结的兼容包装      |
| `summaryManager.ts`             | 扫描 `stat_data.user数据` 与 `stat_data.角色数据` 的 `人物经历`，按阈值顺序总结并写回 ERA |
| `useSummaryDetection.ts`        | 监听 `MESSAGE_RECEIVED`，在未总结、未额外变量更新时触发总结检测                           |
| `extraVariableUpdateManager.ts` | 管理 `变量指导` 世界书条目状态、构造额外变量 prompt、校验变量块、追加楼层并同步 ERA       |
| `messageActions.ts`             | 封装 ERA 事件与 `writeDone` 匹配等待、最新 assistant 临时 swipe 回滚/生成/失败恢复流程    |

`requestConfiguredText` 的两条后端路径：

1. `apiMode: 'preset'`：调用酒馆助手 `generateRaw()`，只传入单条 user
   prompt，并用 overrides 清空世界书、角色描述、示例对话和 chat history；额外变量更新还会启用
   `skipWorldInfoAndAuthorNote`，在生成事件中补写 `skipWIAN`，避免世界书和作者注再次进入请求。
2. `apiMode: 'custom'` 且 `source: 'custom'`：直接请求酒馆后端
   `/api/backends/chat-completions/generate`，构造 OpenAI 兼容 messages，请求头通过 `SillyTavern.getRequestHeaders()`
   获取。

自动总结写回策略：

- `checkSummaryTrigger` 统计玩家和 NPC 的 `人物经历` 条目数，支持对象和字符串两种格式，并过滤 `$` 开头模板字段。
- 触发条件包括待处理角色数阈值、总条目数阈值、单角色条目阈值。
- `executeAllPendingSummaries` 顺序处理待总结角色，解析 `<summary>` 内容后转为新的 `人物经历` 对象，通过
  `era:updateByObject` 写回。

#### 3.6.6. 设置面板运行时控制台

`SettingsPanel.tsx` 已不只是外观设置组件，而是前端的运行时控制台。它按
`appearance / regex / summary / variables / advance / debug` 六个页签组织入口；其中 `summary`
对应额外模型配置，`variables` 和 `advance` 会直接读写聊天变量或复用发送流程。

| 页签         | 架构职责                                                                                                           |
| ------------ | ------------------------------------------------------------------------------------------------------------------ |
| `appearance` | 修改正文、背景等显示设置，并通过 `applySettingsToDOM` 写入 CSS 变量                                                |
| `regex`      | 维护前端正文显示用正则，规则来源包括手动、全局酒馆正则和当前预设正则                                               |
| `summary`    | 配置统一额外模型请求层，手动检查/触发自动总结，切换正文变量更新模式                                                |
| `variables`  | 读取 `getVariables({type:'chat'}).stat_data`，提供树形浏览和叶子值编辑，保存时通过 `replaceVariables` 回写聊天变量 |
| `advance`    | 复用 `useMessageHandler.handleAutoAdvanceTurn` 连续执行回合，记录每轮 user/assistant 楼层、纯文本回复和完整回复    |
| `debug`      | 展示前端调试日志和正则导入/应用状态，辅助定位提示词、变量和显示过滤问题                                            |

自动推进不是独立生成通道：`handleAutoAdvanceTurn` 内部调用普通
`handleSendMessage`，因此它继承正文生成、额外变量更新、ERA 同步和错误处理的同一套流程。

## 4. 变量结构

### 4.1. getAllVariables() 返回结构

```
getAllVariables() 返回:
├── name, LAST_RECEIVE_TOKENS, ... (系统变量，忽略)
└── stat_data (游戏变量)
    ├── 世界信息
    │   └── 时间 { 年, 月, 日, 时 }
    ├── user数据              ← 玩家信息（扁平结构）
    │   ├── 用户名, 性别, 外貌, 状态, 境界, 修为
    │   ├── 所在位置
    │   ├── 功法 {}           ← 注意是"功法"不是"武功"
    │   ├── 初始属性, 属性
    │   └── 包裹 {}
    └── 角色数据              ← NPC角色
```

### 4.2. 玩家属性结构

- **初始属性** (`InitialAttributes`): 开局设定的七维属性（臂力, 根骨, 机敏, 悟性, 洞察, 风姿, 福缘），后续基本固定。
- **当前属性** (`CurrentAttributes`): 战斗中实时变化的五维属性（臂力, 根骨, 机敏, 悟性, 洞察），不包含风姿和福缘。
- **战斗/资源属性**: 气血、内力等由前端根据当前属性、境界、功法实时计算。
- **注意**: 所有属性的键名（key）均为中文，以保持变量表的统一性。

### 4.3. 变量映射表

| 中文变量路径                  | TypeScript类型               | 描述         |
| ----------------------------- | ---------------------------- | ------------ |
| `stat_data.user数据`          | `PlayerData`                 | 玩家完整信息 |
| `stat_data.user数据.功法`     | `Record<string, MartialArt>` | 已学功法     |
| `stat_data.user数据.初始属性` | `InitialAttributes`          | 七维初始属性 |
| `stat_data.事件系统`          | `EventSystem`                | 事件系统     |

> **注意**: 功法和包裹中可能包含 `$template` 模板字段，解析时需过滤
