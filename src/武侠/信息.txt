## 一、当前运行链与真值边界

### 1. 真值与维护目录

- 游戏变量真值是 `getVariables({ type: 'chat' }).stat_data`。
- 当前世界书真源是 `世界书/金庸群侠传1/世界书/*`。
- `角色卡/金庸群侠传/世界书/*` 是过时的卡包拆分副本，不作为默认编辑目标。
- 只修改仓库文件不会自动改变酒馆运行时；仍需 push 世界书或重新打包、导入。

### 2. 正文伴随与额外模型的变量更新链

- 正文伴随的变量更新（内部模式名 `inline`）：正文模型直接读取世界书中的 `变量指导`，在正文末尾输出 ERA 变量块。
- 额外模型变量更新（内部模式名 `extra`）：正文生成时禁用正文侧的 `变量指导`；正文落楼后，前端重新读取精确名称为 `变量指导` 的世界书条目，并组合前端专用变量投影。
- 额外模型变量更新不再执行或复用 `输出提示词`；它使用前端专用的严格 JSON 变量投影，正文叙事上下文与extra变量上下文已经拆开。
- extra读取最新 assistant 正文作为唯一变化来源，并附带其前1轮或2轮完整`user + assistant`作为只读理解上下文，默认1轮。
- 正常的 EJS 合并变量读取与聊天变量 fallback 共用同一个投影构建器，不再维护两套字段范围。

## 二、已经确认的变量权限

### 1. AI 可写范围【已确认】

- `世界信息.时间`
- `user数据`
- `角色数据`
- 当前提示词中已经存在的：
  - `参与事件.<事件名>.结局`
  - `参与事件.<事件名>.insert`
  - `参与事件.<事件名>.update`
  - `参与事件.<事件名>.delete`

AI 不得自行新增、改名或缩写参与事件键。

### 2. 系统维护、AI 只读范围【已确认】

- `事件系统`
- `世界事件`
- `前端变量`
- `附近传闻`
- `后续事件线索`
- `后续事件线索计数`

这些字段由前端或事件脚本生成、刷新、归档、递减或删除。AI 可以把其中展示的信息用于叙事，但不得对这些路径输出 Insert/Edit/Delete。

### 3. “字段所有权矩阵”的含义

字段所有权矩阵是给维护者看的工程约束，不需要原样塞给 AI：

| 路径 | 维护者 | AI 权限 | 是否可作为上下文 |
| --- | --- | --- | --- |
| `世界信息.时间` | AI | 可写，只能前推 | 是 |
| `user数据` | AI 与前端动作协作 | 可写，但不得重复前端已结算动作 | 是 |
| 同场 `角色数据` | AI | 可写 | 是 |
| `参与事件.描述` | 事件脚本 | 只读 | 是 |
| `参与事件.结局/insert/update/delete` | AI 在参与期间调整 | 有条件可写 | 是 |
| `世界事件` | 事件脚本 | 只读 | 筛选后提供 |
| `前端变量` | 前端 | 禁写 | 只投影必要派生信息 |
| `事件系统/附近传闻/后续事件线索及计数` | 事件脚本 | 禁写 | 按叙事需要提供 |

实际给模型的规则只需简明列出“允许写哪些路径”和“哪些展示块只读”。

## 三、参与事件的实时变量与结局快照

### 1. 处理原则【已确认】

1. `参与事件.insert/update/delete` 是加入事件时复制的原定结算快照。AI 只修改或删除其中已经存在、且被玩家介入改变的差分项，不向快照新增原本不存在的结果。
2. 正文产生的新变化如果没有对应到现有 `insert/update/delete` 项，按已经发生的事实直接修改当前 `user数据/角色数据`。
3. 事件实际走向与当前 `参与事件.结局` 有差异时，无论是否命中已有差分项，都要修改 `结局`。
4. 命中已有差分项的结果只修改或删除快照，不再把同一结果提前写入当前 `角色数据`，避免事件结束时重复结算。
5. `参与事件.描述`只读；临时位置、伤势或状态等不在原定差分中的即时变化直接写当前变量。

### 2. 运行时限制

- `参与事件.insert/update/delete` 在事件结束时会被包装为 `角色数据`差分。
- 因此参与事件差分只能描述 NPC 的最终变量变化，不能承载 `user数据`。
- 参与事件差分快照完全不负责 `user数据`。正文中玩家变量确实变化时，始终按普通实时变化直接写 `user数据`；如果事件结局文字因此与现状不同，再同步修改 `结局`。

### 3. 提示词组织方向【本轮已实施】

事件发展底稿与参与事件快照放在同一个“当前事件上下文”区。事件使用规范短键作为标签，方括号文本只读，JSON 对象才表示有条件可写变量：

```text
<参与事件>
<射雕第7回02-初遇黄蓉>
[1219年10月20日13时 至 1219年10月20日15时｜地点：大宋/张家口/大酒店｜事件描述……]
{"结局":"……","insert":{},"update":{},"delete":{}}
</射雕第7回02-初遇黄蓉>
</参与事件>
```

事件标签必须与 `参与事件` 的实际键完全一致，用于区分多条参与事件；事件背景和描述只读，只有 JSON 中四个字段可按规则写入。

### 4. 事件运行时规范键【本轮已实施】

- 普通事件的运行时 canonical key 统一为 `射雕第7回02-初遇黄蓉` 这类格式；活跃真源630个普通事件均可无冲突转换。
- 世界书物理文件名和条目分类名继续保留 `射雕事件条目-第7回-02-初遇黄蓉`，loader 负责派生运行时规范键，不批量重命名688个源文件。
- `事件系统`各状态、人物事件占用、`参与事件`、`世界事件`、事件结局状态、附近传闻、后续线索及计数、人物经历中的事件记录键，都必须使用同一运行时规范键。
- 不再长期保留“完整名/短名/展示名”三套身份；展示标题由规范键派生。
- 58个登场事件使用独立 kind 元数据，不再依赖键名中是否含有“登场事件/事件条目”判断类型。
- loader 已为事件定义附加不可枚举的 kind 与来源元数据；事件类型判断不再解析键名文本。688个物理事件条目均能派生规范键且没有冲突。
- 本次采用开发期清空策略，不迁移旧名：检测到`前端变量.事件运行时键版本`不是当前版本时，先清空事件系统各状态、参与事件、世界事件、附近传闻、后续线索及计数、事件结局状态和 NPC 人物经历中的事件记录，再以规范键重新初始化。新游戏直接写入当前版本。
- 已审计604条后续事件引用，其中581条可以解析；其余23条是世界书原始数据中的`XX/待定/全书完`等占位或悬空引用，继续按原策略跳过，本轮不改事件源文件。

即时人物状态仍保留在 `user数据/角色数据`，避免出现第二套当前状态真值。

### 5. 事件弹性窗口与完成流程【本轮已实施】

#### 根因

旧实现把持续时间较短的事件统一提前10天判定为“到达开始时间”，并直接写入`进行中事件`，但运行时结束时间仍使用原定结束时间。结果是同一事件链中未来10天内的多条事件可能同时进入`进行中事件/参与事件`，提前开始后的描述窗口、结束判断与归档窗口也不一致。

#### 当前规则

1. “可发现”“原定开始”“提前到场开始”是三个独立判断：
   - 持续时间不超过短事件阈值的事件，原定开始前10天只开放传闻。
   - 未提前到场时，只在`当前时间 >= 原定开始时间`后正式启动。
   - 玩家位于事件的完整精确地点时才允许提前启动；层级前缀或同一二级区域不算到场。
2. 提前触发还要求所有有效的入向前置事件已经完成。前置关系从世界书中可解析的`后续事件.事件名`反向派生；`XX/待定/全书完`等占位或悬空引用不构成阻塞。
3. 提前开始按小时保留原事件持续时长：实际开始为当前时间，实际结束为`当前时间 + 原事件持续小时数`。`事件系统.进行中事件.<规范键>`保存该实际结束时间，`参与事件.描述`与`世界事件.时间`读取同一运行窗口。
4. 事件在`当前时间 >= 实际结束时间`时进入结算，不再多等一个时间单位。
5. 完成流程为：应用差分 → 归档世界事件 → 写入已完成 → 删除进行中与参与事件 → 清理人物占用 → 写入后续线索及计数 → 回读验证。`前端变量.事件结算进度`记录可重试阶段；归档、删除或线索写入部分失败时，下一轮优先继续结算，已经应用的差分不会重复应用。只有终态全部验证通过后才清除进度。
6. 后续事件线索不在事件开始时生成。事件完成后，`后续事件线索.<前置事件键>`与`后续事件线索计数.<前置事件键>=3`在同一直接变量写入中成对创建。
7. 回合结算串行执行。只递减回合开始前已经存在的计数，本回合完成事件新建的计数保持3；此后成功回合按`3 → 2 → 1 → 同时删除线索及计数`运行。

#### 开发期重建

- `前端变量.事件运行时键版本`已升级为2，新游戏直接写入2。
- 旧存档检测到版本不一致时，继续采用开发期重建策略：清空已污染的事件运行状态、参与事件、世界事件、传闻、后续线索及计数、结局/结算进度和人物事件经历，再按当前事件定义重建。
- 该重建不会回滚已经被旧错误窗口移动过的NPC即时位置；开发测试存档建议重新开局。

## 四、地点写入规则

### 1. 目标规则【已确认】

- 前端复用并升级只读的 `前端变量.周围地点`，再投影成 `<可用地点>...</可用地点>`；不另建语义重复的 `可用地点`变量。
- 只要当前提示词提供了 `<可用地点>`，AI 对任何 `所在位置` 的新值都必须与其中某条完整地点路径完全一致。
- 禁止自行创造地点、只写简称、改变层级或把 `大宋/临安府/B城`缩写成 `B城`。
- 当 `<可用地点>` 已提供但没有合适目标时，本轮不修改位置。
- 普通移动允许当前二级地点和相邻二级地点下已解锁的三级地点；不提供“移动到二级地点”的操作。
- 地图点击指定的完整三级路径作为本轮一次性授权，即使较远也可写入，但正文必须体现合理旅行时间。
- `附近传闻`和`后续事件线索`中明确写出的完整事件地点加入白名单；远途移动同样需要合理时间。

建议提示词格式使用只读列表，不使用 JSON 花括号：

```text
<可用地点>
[普通移动]
- 大宋/临安府/牛家村
- 大宋/嘉兴府/烟雨楼
[事件目标]
- 蒙古/大漠/荒山
[地图指定]
- 大理/大理城/天龙寺
</可用地点>
```

`[地图指定]` 只在本轮存在明确地图指令时出现；所有分组中的条目均为可写入的精确路径。

### 2. 实施状态【本轮已实施】

- `前端变量.周围地点`固定为`普通移动/事件目标/地图指定`三组完整三级路径。
- `普通移动`展开当前二级地点及最多四个相邻二级地点中已解锁的三级地点，不再把二级地点本身作为可写值；解锁判断与地图界面共用同一函数。
- `事件目标`合并附近传闻和后续事件线索中的完整地点；`地图指定`只保存本轮地图指令授权的完整目标，普通下一轮会自动清空。
- 地图点击仍由 AI 落库，不直接写位置变量；发送与重新生成都会从完整地图指令恢复本轮授权。
- `输出提示词.txt`将同一变量投影为只读`<可用地点>`，正文伴随与extra共用同一白名单。

## 五、头像变量与设置变量页

### 1. 头像唯一真值【本轮已实施】

头像采用稀疏的前端维护结构：

```json
{
  "前端变量": {
    "头像": {
      "玩家": "preset:...",
      "人物": {
        "黄蓉": "preset:..."
      }
    },
    "头像版本": 1
  }
}
```

- `前端变量.头像`是存档中唯一有效的头像引用真值；`user数据.头像`、`角色数据.<人物>.头像`和`角色数据.$template.头像`已经从新游戏结构删除。
- 玩家头像写在`前端变量.头像.玩家`；NPC头像写在`前端变量.头像.人物.<姓名>`。NPC没有显式选择时不创建空键，清除选择时删除对应稀疏键。
- 预设头像只保存`preset:<id>`；自定义头像只保存`custom:<entityKey>`。base64图片仍按聊天保存在localStorage，不写入聊天变量。
- 游戏内玩家/NPC的选择、上传和清除均通过前端背景写入更新该结构；写入失败时界面回滚乐观预览，自定义图片也恢复到写入前状态。
- 开局表单可以用localStorage暂存草稿选择；正式创建存档后把引用写入`前端变量.头像`并清理草稿选择。

### 2. 头像一次性迁移【本轮已实施】

- 每个实体按“已有新结构 → 当前聊天localStorage选择 → 旧人物变量头像”的优先级迁移。
- 即使`头像版本=1`和容器已经存在，只要某实体的新结构仍缺键而localStorage或旧变量有有效引用，也会补齐后再清理旧选择。
- 迁移成功后删除玩家、NPC和`$template`中的旧`头像`字段，并清理当前聊天遗留的头像选择记录；自定义图片本体继续保留。
- 正文输出与extra变量投影会过滤任何遗留的玩家/NPC头像字段；`变量指导`明确头像由前端维护，AI既不得重建旧字段，也不得写`前端变量.头像`。

### 3. 设置页变量分组【本轮已实施】

变量页只改变展示投影，不改变真实变量结构：

- 一级固定为`世界 / 事件 / 玩家 / 人物`。
- 二级固定映射为：
  - 世界：`世界信息 / 附近传闻 / 后续事件线索`
  - 事件：`事件系统 / 参与事件`
  - 玩家：`user数据`
  - 人物：`角色数据`
- `前端变量`、`后续事件线索计数`、`世界事件`在该变量页的导航、变量树和全局搜索中全部隐藏，但底层数据不删除，前端与事件脚本仍照常维护。
- 浏览、叶子编辑、复制路径和保存继续使用真实`stat_data`路径，不引入展示别名。
- 某个真实根缺失时只隐藏对应二级项；空的一级组禁用。当前选择失效时按固定组序回退到第一个存在的真实根，不创建空变量。
- 两级导航沿用现有水墨纸面风格，并补齐tab语义、表单标签和窄屏两列/换行布局。

## 六、战斗判定共识

### 1. 已确认规则

- 示例公式原错误位于 `50*(1234-5465)/5465)`，末尾多了一个右括号；总公式本身括号平衡。
- 战力差项四舍五入：
  - 至少一方战力大于0：`round(50 * (先手战力 - 后手战力) / max(先手战力, 后手战力))`
  - 双方战力均为0：战力差项固定为0。
- 最终值：`45 + 战力差项 + 随机数 + 环境因素 + 状态因素`。
- `环境因素`是地形、天气、光线、水面、狭窄空间等对本次行动形成的一个最终修正值，范围 `[-20,+20]`。
- `状态因素`是尚未计入战力的即时战术状态对本次行动形成的一个最终修正值，范围 `[-20,+20]`。
- 玩家战力区已经计入装备、有效的属性型状态效果和永久属性修正，不得在状态因素中重复加减。
- 只有尚未体现在战力值中的即时战术状态，例如重伤、束缚、失明、被震慑、蓄势或措手不及，才计入状态因素。
- 当前回复内从随机数1开始，每次独立交锋依次使用一个未使用随机数。

### 2. 无功法的当前实现【本轮已实施】

- 系统已有“境界隐含内外功保底”，用于气血、内力和无显性内功时的修为变化参考。
- 招式战力读取已经乘过境界系数的战斗属性，因此高手的具名招式会自然获得高战力。
- 战力区现在为每名角色提供一个统一的`基础`战力，不再为每个缺失功法类型输出“无”或分别建立空功法保底。
- 具名功法与基础招式二选一，不相加；基础招式也不凭空授予武器、暗器或特殊效果。双方所用战力都为0时跳过除法，主要依靠随机、环境和即时状态。

当前公式【本轮已实施，仍需游玩平衡测试】：

```text
不入流：基础招式 = 0
其他境界：基础招式 = round((臂力 + 根骨 + 机敏 + 洞察) × 0.15)
```

四项战斗属性已经乘过大/小境界系数，因此这个基础值等价于一门四项均分的粗浅功法，不再按境界额外升品阶，避免境界被计算两次。使用规则：具名功法使用具名战力；普通未具名攻击、招架或闪避才使用基础招式；两者不能相加，基础值不附带任何功法特性。

战力区已改成稀疏行，避免输出大量“无”，例如：

```text
郭靖｜基础:6000｜拳掌:降龙十八掌=15000｜轻功:金雁功=8000
```

需要重点比较“高一境界基础招式 vs 低一境界传说功法”和“同境界基础招式 vs 各品阶功法”，确认保底不会压过具名武学体系。

### 3. 延期项

- 五个随机数耗尽后的行为【延期】：等实际游玩确认是否会出现一轮超过五次独立判定，再决定扩容、循环还是生成新随机数。

## 七、输出提示词讨论结论

### 1. 安全 `statData` 不会妨碍微调测试

建议以后使用：

```js
const statData = variables?.stat_data ?? {};
```

这只是给同一个数据源建立安全别名，不切换到其他 API。正常情况下渲染内容不变；区别只是 `stat_data`缺失时不再让正文输出提示词整份 EJS 直接报错。extra 已经使用独立变量投影，不受这项正文模板安全改造影响。

状态：【延后】。正常存档中不影响输出；仅在 `stat_data` 缺失或损坏时用于避免 EJS 整块失败。等主要提示词与额外模型变量更新链路完成后再处理。

### 2. 删除角色对象内部姓名【本轮已实施】

同场角色最终形态类似：

```text
角色数据:{郭靖:{...},黄蓉:{...}}
```

姓名只由 `角色数据` 下的人物对象键表达；活动世界书中的登场事件和普通事件差分不再写入或删除内部 `姓名`，前端派生逻辑也不再读取内部姓名回退。本轮不归一化 `完颜康/杨康` 等外层人物键，也不改现有 Schema。

`身份`严格保持现有的扁平 `Record<string, string>`：身份名直接作为键，影响剧情的事实作为值。不新增 `称谓/本名/别名/字` 等固定字段或子结构，也不为不影响剧情的别名、字单独保存变量。完颜康首次登场时以 `"赵王完颜洪烈养子":"被完颜洪烈收养，视若己出，不知道自己的真实身份，一直以为自己是亲生的"` 表达会影响剧情的身份，并同步使用同一身份键处理后续删除或重新写入。

### 3. 人物经历、关系网与历史压缩【延期】

- 人物经历用于维持旧事、恩怨和玩家造成的长期改变。
- 关系网用于决定角色之间的立场、称呼、合作与敌对。
- `关系网`不压缩，继续保留结构化原值。
- `人物经历`达到可配置数量阈值后，由额外模型压缩较早条目；近期3条或5条原文保留，不参与压缩。
- 人物经历总结与世界事件历史总览分开维护，不能混成一份摘要。

### 4. 不增加“所有已有角色键”列表【已确认】

- 角色可能有几十到上百个，额外发送完整角色名列表浪费注意力。
- 同场对象本身已经以姓名为键。
- ERA Insert 不会覆盖已存在节点；不需要为防误 Insert 把全角色库键名发给模型。

### 5. `toCompact` 与严格 JSON 的差异【本轮已实施】

输入示例：

```json
{
  "备注": "他说\"取{秘籍}\"，明日再来\n勿忘",
  "关系网": { "黄蓉": "知己/90" }
}
```

旧 `toCompact()`可能产生：

```text
{备注:"他说"取{秘籍}"，明日再来
勿忘",关系网:{黄蓉:知己/90}}
```

这不是合法 JSON：键名没引号，内部引号和换行也没有可靠转义。

过滤内部字段后的无缩进 `JSON.stringify()`会产生：

```json
{"备注":"他说\"取{秘籍}\"，明日再来\n勿忘","关系网":{"黄蓉":"知己/90"}}
```

它会多占少量 token，但结构不会被人物对白、引号、花括号、反斜杠或换行破坏。

已替换为：递归过滤所有 `$`前缀内部字段，再用无缩进 `JSON.stringify()`。严格序列化另有独立契约测试；特殊字符夹具已覆盖引号、换行、花括号和反斜杠，仍需继续观察实际模型生成差异。

### 6. 空块规则【本轮已实施；顶层安全读取延后】

当前大部分可选块为空时已经省略，不需要大规模重写。

当前已统一：

- 核心当前状态使用 JSON；无同场人物可写 `角色数据:{}`。
- 没有参与事件时继续省略参与事件块。
- 世界事件、线索、传闻为空时继续省略。
- 真正读取失败时才使用独立 `<context_error>`，不要把错误提示伪装成剧情事实。

当整个`stat_data`都不存在时的安全别名与完整错误捕获仍随“安全 statData”一起延后；正常存档字段局部缺失时已经输出独立`<context_error>`。

### 7. 额外模型变量更新专用投影【本轮已实施】

额外模型变量更新不再长期复用正文输出提示词的宽叙事投影。第一版专用请求包含：

- 最新 assistant 正文，明确标注为本轮唯一变化来源。
- 最新正文之前一到两轮完整的 `user + assistant`，明确标注为只读理解上下文。
- `世界信息.时间`。
- 清理内部字段后的完整 `user数据`。
- 同场 NPC、当前参与事件 NPC、最新正文点名 NPC。
- 已有参与事件快照。
- 本轮合法地点完整路径。

不再发送完整世界事件、附近传闻、后续线索和五层旧 assistant 正文；事件地点只通过只读`前端变量.周围地点`进入投影。

设置页只增加extra只读上下文轮数（1或2轮，默认1轮）。temperature、top_p、max_tokens及其他生成参数继续继承当前选用的预设/请求配置，不为extra再造一套独立参数，避免配置重复和前端无法完整操控请求的问题。

## 八、世界事件的数量与总结

### 1. 当前确实有16条上限

- `输出提示词.txt`当前默认 `limit = 16`、`priorityLimit = 8`。
- 先选最多8条 `偏离/未知`，再用最近事件补足到16条，最后按时间正序发送。
- 16/8只用于正文输出提示词中的世界事件投影；extra专用变量投影不发送世界事件，因此不再复用该筛选逻辑。

### 2. 为什么不立即用额外模型总结替换上限

- 当前额外模型变量更新请求不是历史总结器；若让同一请求临时总结，它仍需先接收原始事件。真正能降低以后输入的是独立、持久化、按数量阈值触发的批量历史总览。
- 另开总结请求会增加延迟、费用、失败点和事实失真风险。
- 单一总结还可能抹掉事件名、精确时间、地点和“偏离/未知”状态。

### 3. 长期推荐的混合方案【延期】

- 最近事件、偏离/未知事件、与当前地点/人物/事件链高度相关的事件保留精确记录。
- 世界事件达到可配置数量阈值后，由额外模型周期性生成持久化“历史总览”；近期3条或5条原始事件不压缩，先从最早记录开始。
- 提示词同时发送精确近期记录和较短历史总览，而不是每轮即时总结并完全替代原记录。

当前决定：保留16条上限。以后根据真实 token、历史遗漏和叙事连贯性决定是否改成动态 token 预算或混合总结。

## 九、提示词块的排列与权威语义

世界事件作为长期只读历史，可以在排列上放到更靠近聊天上下文的位置。需要区分“排列位置”和“冲突时谁是真值”：

- 已完成世界事件：只读历史，说明过去发生了什么。
- 当前事件上下文：说明正在推进什么；参与快照按规则有条件可改。
- 当前时间与人物变量：说明此刻状态，可按本轮正文修改。

不再用简单的 `stat_data > 参与事件 > 事件底稿 > 世界事件`作为提示词展示顺序。每个块直接标明其时间语义和读写权限。若历史记录与当前人物状态看起来冲突，历史只解释过去，当前变量仍表示此刻状态。

状态：【本轮已实施】。

## 十、变量指导的目标结构

### 1. 不要求暴露完整决策思维链

“是否变化 → 谁负责 → 节点是否存在 → Insert/Edit/Delete”是维护者设计规则时的检查表，不要求模型输出完整推理过程。

模型只需知道：

- 哪些路径允许写。
- 哪些上下文只读。
- 当前相关对象的真实 JSON 是否已经存在。
- Insert/Edit/Delete 的最小选择规则。

### 2. 只展示相关且可能修改的 JSON

方向正确，但不能预先只给“本轮最终会修改的叶子字段”，因为生成前还不知道正文会产生什么变化。建议展示相关作用域：

- `世界信息.时间`
- 完整 `user数据`
- 同场相关 `角色数据`
- 已存在的 `参与事件`快照
- 另一区块中的必要只读历史和事件背景

不要发送全部角色键列表；暂不裁剪同场角色经历和关系网。

### 3. 不重复大段 Schema

- 已存在对象：直接参考当前真实 JSON，不再重复一套玩家/NPC完整 Schema。
- 新建节点：因为当前输出过滤 `$template`，仍需一条简短创建规则或正例。
- 当前先保留一个新功法 Insert 的最小结构示例；新 NPC、新物品若在实测中确实需要，再各补一个最小示例。

### 4. 示例策略【等待实测】

当前只保留一个新功法的必要新建结构示例。新 NPC、新物品示例以及行为正反例，等实际游玩暴露稳定需求或错误后再针对性增加，不提前猜测错误模式。

### 5. `<VariableThink>`目标格式【已实现】

`<VariableThink>`是通用变量小思维链，不是事件专用字段，也不只是一份机械审计：

```text
<VariableThink>
- 变化判断: 正文中真实发生了哪些需要持久化的变化？
- 当前对照: 当前值是什么，目标路径是否已经存在？
- 写入选择: 直接修改当前变量，还是修改/删除已有参与事件差分？
- 最终操作: 使用哪些 Insert / Edit / Delete 路径？
</VariableThink>
```

只有本轮涉及参与事件时才讨论参与事件差分；普通旅行、人物经历和物品变化仍按同一套变量判断流程处理。无需复述整段剧情。
