## 一、当前运行链与真值边界

### 1. 真值与维护目录

- 游戏变量真值是 `getVariables({ type: 'chat' }).stat_data`。
- 当前世界书真源是 `世界书/金庸群侠传1/世界书/*`。
- `角色卡/金庸群侠传/世界书/*` 是过时的卡包拆分副本，不作为默认编辑目标。
- 只修改仓库文件不会自动改变酒馆运行时；仍需 push 世界书或重新打包、导入。

### 2. inline 与 extra 的变量更新链

- `inline`：正文模型直接读取世界书中的 `变量指导`，在正文末尾输出 ERA 变量块。
- `extra`：正文生成时禁用正文侧的 `变量指导`；正文落楼后，前端重新读取精确名称为 `变量指导` 和 `输出提示词` 的世界书条目。
- extra 会执行 `输出提示词` 的 EJS 和宏，把渲染结果作为“当前变量上下文”，再与最近五层正文、原始 `变量指导` 一起交给额外变量模型。
- 因此，当前直接删除 `输出提示词` 中的字段，会同时影响正文模型和 extra 变量模型。长期若要分别裁剪，应先拆成“叙事上下文”和“变量上下文”两条投影链。
- `输出提示词`渲染失败时，extra 才会退回 `extraVariableUpdateManager.ts` 自行构造的变量快照。

## 二、已经确认的变量权限

### 1. AI 可写范围【已确认】

- `世界信息.时间`
- `user数据`
- `角色数据`
- 当前提示词中已经存在的：
  - `参与事件.<事件名>.结局`
  - `参与事件.<事件名>.insert`
  - `参与事件.<事件名>.update`
  - `参与事件.<事件名>.delete`

AI 不得自行新增、改名或缩写参与事件键。

### 2. 系统维护、AI 只读范围【已确认】

- `事件系统`
- `世界事件`
- `前端变量`
- `附近传闻`
- `后续事件线索`
- `后续事件线索计数`

这些字段由前端或事件脚本生成、刷新、归档、递减或删除。AI 可以把其中展示的信息用于叙事，但不得对这些路径输出 Insert/Edit/Delete。

### 3. “字段所有权矩阵”的含义

字段所有权矩阵是给维护者看的工程约束，不需要原样塞给 AI：

| 路径 | 维护者 | AI 权限 | 是否可作为上下文 |
| --- | --- | --- | --- |
| `世界信息.时间` | AI | 可写，只能前推 | 是 |
| `user数据` | AI 与前端动作协作 | 可写，但不得重复前端已结算动作 | 是 |
| 同场 `角色数据` | AI | 可写 | 是 |
| `参与事件.描述` | 事件脚本 | 只读 | 是 |
| `参与事件.结局/insert/update/delete` | AI 在参与期间调整 | 有条件可写 | 是 |
| `世界事件` | 事件脚本 | 只读 | 筛选后提供 |
| `前端变量` | 前端 | 禁写 | 只投影必要派生信息 |
| `事件系统/附近传闻/后续事件线索及计数` | 事件脚本 | 禁写 | 按叙事需要提供 |

实际给模型的规则只需简明列出“允许写哪些路径”和“哪些展示块只读”。

## 三、参与事件的实时变量与结局快照

### 1. 处理原则【已确认】

1. 如果变化不影响事件预期最终结局，则按已经发生的事实直接修改当前 `user数据/角色数据`。
2. 如果玩家介入改变了人物生死、长期状态、关系、阵营、关键物品归属、事件目标或后续事件成立条件，则修改 `参与事件.结局` 与对应 `insert/update/delete`，把它作为新的最终结算快照。
3. 同一份长期结果不得同时直接写入实时变量，又保留在参与事件差分中，否则事件结束时会重复结算。
4. 已经发生、但不属于最终结算的临时位置、伤势或状态，可以直接写当前变量。
5. `参与事件.描述`只读；结局文本与三类差分必须表达同一个最终结果。

### 2. 运行时限制

- `参与事件.insert/update/delete` 在事件结束时会被包装为 `角色数据`差分。
- 因此参与事件差分只能描述 NPC 的最终变量变化，不能承载 `user数据`。
- 玩家自身变化始终写 `user数据`；如果玩家行为改变了事件结局，则另外同步修改事件结局文本和 NPC 差分快照。

### 3. 提示词组织方向【待实现】

事件发展底稿与参与事件快照可以放在同一个“当前事件上下文”区：

- 事件发展/背景：只读，用于判断剧情推进位置。
- `参与事件.描述`：只读。
- `参与事件.结局/insert/update/delete`：有条件可写。

即时人物状态仍保留在 `user数据/角色数据`，避免出现第二套当前状态真值。

## 四、地点写入规则

### 1. 目标规则【已确认】

- 后续会把 `前端变量.周围地点`投影成 `<可用地点>...</可用地点>`。
- 只要当前提示词提供了 `<可用地点>`，AI 对任何 `所在位置` 的新值都必须与其中某条完整地点路径完全一致。
- 禁止自行创造地点、只写简称、改变层级或把 `大宋/临安府/B城`缩写成 `B城`。
- 当 `<可用地点>` 已提供但没有合适目标时，本轮不修改位置。

### 2. 当前时序风险

- 当前 `输出提示词.txt`尚未输出 `<可用地点>`。
- extra 模式已经有独立的动态地点白名单，但 inline 正文模型目前还看不到该标签。
- 因此本轮变量指导先使用条件式约束；在正式把 `<可用地点>`加入输出提示词后，再把它作为所有位置修改的强制前提进行完整测试。

## 五、战斗判定共识

### 1. 已确认规则

- 示例公式原错误位于 `50*(1234-5465)/5465)`，末尾多了一个右括号；总公式本身括号平衡。
- 战力差项向下取整：
  - 至少一方战力大于0：`floor(50 * (先手战力 - 后手战力) / max(先手战力, 后手战力))`
  - 双方战力均为0：战力差项固定为0。
- 最终值：`45 + 战力差项 + 随机数 + 环境因素 + 状态因素`。
- `环境因素`表示本次行动全部环境利弊的净修正，汇总后限幅一次 `[-20,+20]`。
- `状态因素`表示本次行动全部即时状态利弊的净修正，汇总后限幅一次 `[-20,+20]`。
- 不能把多个环境或状态拆开，让每一项分别获得一个 `[-20,+20]`上限。
- 玩家战力区已经计入装备、有效的属性型状态效果和永久属性修正，不得在状态因素中重复加减。
- 只有尚未体现在战力值中的即时战术状态，例如重伤、束缚、失明、被震慑、蓄势或措手不及，才计入状态因素。
- 当前回复内从随机数1开始，每次独立交锋依次使用一个未使用随机数。

### 2. 无功法的当前事实

- 当前代码没有“无功法默认战力”的数值兜底。
- 默认初始属性10不是无功法战力兜底；无对应功法类型时，战力区实际输出“无”。
- 当前提示词暂按“无 = 0”处理；双方都是0时跳过除法，主要依靠随机、环境和即时状态。
- 如果以后需要基础拳脚、境界或属性产生非零默认战力，应在前端战力区生成逻辑中实现并测试，不能只让模型自行猜一个数值。

### 3. 延期项

- 五个随机数耗尽后的行为【延期】：等实际游玩确认是否会出现一轮超过五次独立判定，再决定扩容、循环还是生成新随机数。

### 4. 修炼参考【本轮已实施】

- `<修炼速度参考值>`已接入真实字段 `前端变量.修为变化参考`。

## 六、输出提示词讨论结论

### 1. 安全 `statData` 不会妨碍微调测试

建议以后使用：

```js
const statData = variables?.stat_data ?? {};
```

这只是给同一个数据源建立安全别名，不切换到其他 API。正常情况下渲染内容不变；区别只是 `stat_data`缺失时不再让整份 EJS 直接报错。extra 每轮仍会重新读取并执行当前世界书中的输出提示词，所以微调同步到实际绑定世界书后仍能立即测试。

状态：【待实现】。实施时应做渲染前后对照，确认正常存档输出逐块一致。

### 2. 姓名当前没有丢失

同场角色最终形态类似：

```text
角色数据:{郭靖:{...},黄蓉:{...}}
```

姓名已经作为对象键发送。当前排除的是对象内部重复的 `姓名: 郭靖`字段，不是完全不发送姓名。此前“姓名不发”的表述不准确。

### 3. 人物经历与关系网暂不裁剪【已确认】

- 人物经历用于维持旧事、恩怨和玩家造成的长期改变。
- 关系网用于决定角色之间的立场、称呼、合作与敌对。
- 当前不默认删除完整经历和关系网。
- 只有游玩实测出现明显 token 膨胀后，才讨论适应性裁剪：关系只保留玩家、同场人物、当前事件人物；经历保留总结和近期记录。

### 4. 不增加“所有已有角色键”列表【已确认】

- 角色可能有几十到上百个，额外发送完整角色名列表浪费注意力。
- 同场对象本身已经以姓名为键。
- ERA Insert 不会覆盖已存在节点；不需要为防误 Insert 把全角色库键名发给模型。

### 5. `toCompact` 与严格 JSON 的差异【待微调测试】

输入示例：

```json
{
  "备注": "他说\"取{秘籍}\"，明日再来\n勿忘",
  "关系网": { "黄蓉": "知己/90" }
}
```

当前 `toCompact()`可能产生：

```text
{备注:"他说"取{秘籍}"，明日再来
勿忘",关系网:{黄蓉:知己/90}}
```

这不是合法 JSON：键名没引号，内部引号和换行也没有可靠转义。

过滤内部字段后的无缩进 `JSON.stringify()`会产生：

```json
{"备注":"他说\"取{秘籍}\"，明日再来\n勿忘","关系网":{"黄蓉":"知己/90"}}
```

它会多占少量 token，但结构不会被人物对白、引号、花括号、反斜杠或换行破坏。

建议方向：递归过滤所有 `$`前缀内部字段，再用无缩进 `JSON.stringify()`。正式替换前先用正常存档和特殊字符夹具对比，不与其他字段裁剪同时进行，便于微调测试归因。

### 6. 空块风险不大

当前大部分可选块为空时已经省略，不需要大规模重写。

建议只统一：

- 核心当前状态使用 JSON；无同场人物可写 `角色数据:{}`。
- 没有参与事件时继续省略参与事件块。
- 世界事件、线索、传闻为空时继续省略。
- 真正读取失败时才使用独立 `<context_error>`，不要把错误提示伪装成剧情事实。

状态：【待实现】，低优先级。

## 七、世界事件的数量与总结

### 1. 当前确实有16条上限

- `输出提示词.txt`当前默认 `limit = 16`、`priorityLimit = 8`。
- 先选最多8条 `偏离/未知`，再用最近事件补足到16条，最后按时间正序发送。
- extra fallback 使用的共享筛选逻辑同样是16/8。

### 2. 为什么不立即用额外模型总结替换上限

- 如果让当前 extra 变量模型总结，它仍需先接收原始世界事件，不能降低自己的本轮输入。
- 另开总结请求会增加延迟、费用、失败点和事实失真风险。
- 单一总结还可能抹掉事件名、精确时间、地点和“偏离/未知”状态。

### 3. 长期推荐的混合方案【待验证】

- 最近事件、偏离/未知事件、与当前地点/人物/事件链高度相关的事件保留精确记录。
- 更早历史由额外模型周期性生成一份持久化“历史总览”。
- 提示词同时发送精确近期记录和较短历史总览，而不是每轮即时总结并完全替代原记录。

当前决定：保留16条上限。以后根据真实 token、历史遗漏和叙事连贯性决定是否改成动态 token 预算或混合总结。

## 八、提示词块的排列与权威语义

世界事件作为长期只读历史，可以在排列上放到更靠近聊天上下文的位置。需要区分“排列位置”和“冲突时谁是真值”：

- 已完成世界事件：只读历史，说明过去发生了什么。
- 当前事件上下文：说明正在推进什么；参与快照按规则有条件可改。
- 当前时间与人物变量：说明此刻状态，可按本轮正文修改。

不再用简单的 `stat_data > 参与事件 > 事件底稿 > 世界事件`作为提示词展示顺序。每个块直接标明其时间语义和读写权限。若历史记录与当前人物状态看起来冲突，历史只解释过去，当前变量仍表示此刻状态。

状态：【待实现】。

## 九、变量指导的目标结构

### 1. 不要求暴露完整决策思维链

“是否变化 → 谁负责 → 节点是否存在 → Insert/Edit/Delete”是维护者设计规则时的检查表，不要求模型输出完整推理过程。

模型只需知道：

- 哪些路径允许写。
- 哪些上下文只读。
- 当前相关对象的真实 JSON 是否已经存在。
- Insert/Edit/Delete 的最小选择规则。

### 2. 只展示相关且可能修改的 JSON

方向正确，但不能预先只给“本轮最终会修改的叶子字段”，因为生成前还不知道正文会产生什么变化。建议展示相关作用域：

- `世界信息.时间`
- 完整 `user数据`
- 同场相关 `角色数据`
- 已存在的 `参与事件`快照
- 另一区块中的必要只读历史和事件背景

不要发送全部角色键列表；暂不裁剪同场角色经历和关系网。

### 3. 不重复大段 Schema

- 已存在对象：直接参考当前真实 JSON，不再重复一套玩家/NPC完整 Schema。
- 新建节点：因为当前输出过滤 `$template`，仍需一条简短创建规则或正例。
- 保留新 NPC、新功法、新物品等必要 Insert 的最小结构示例即可。

### 4. 示例规划【待实现】

保留三到四个短正例：

1. 玩家学习新功法并推进时间。
2. NPC 已有字段修改。
3. 参与事件结局与差分快照改变。
4. 新建必要节点。

保留两个反例：

1. 前端已经结算装备或药品，本轮不得重复写。
2. 没有持久变化，只输出简短审计，不输出任何 Insert/Edit/Delete。

### 5. `<VariableThink>`目标格式【待实现】

从剧情复述改成简短变更审计，例如：

```text
<VariableThink>
变化：本轮发生的持久变化
写入：Edit 世界信息.时间；Insert user数据.人物经历.某条
事件：不影响结局 / 修改参与事件快照
</VariableThink>
```

不要求复述整段剧情，也不要求输出责任判断的完整思维链。

- 先记录实际 token、被截断历史和叙事遗漏。
- 再比较固定16条、动态 token 预算、精确近期记录 + 持久历史总结三种方案。

### 阶段F：经历与关系网适应性裁剪

- 仅在实测确认同场角色对象导致明显膨胀后启动。
- 任何裁剪都必须保留玩家关系、同场人物关系、当前事件人物关系以及影响当前行为的重要经历。

## 十二、验收标准

- 变量指导中玩家只写 `user数据`，NPC 只写 `角色数据.<姓名>`。
- 不再使用已废弃的 `技能`字段。
- 所有位置示例使用完整层级路径；提供 `<可用地点>`后只能从白名单选择。
- AI 提示词不再把系统维护字段列为可写。
- 同一事件长期结果不会同时实时写入并在结束时重复结算。
- 战斗公式无除零、括号和取整歧义；装备和属性型状态不重复计算。
- extra 默认模板、变量指导、正常输出上下文与 fallback 的字段所有权保持一致。
- 所有示例动作块都是严格 JSON。
- `git diff --check`通过，相关 Vitest 和快速构建通过。
