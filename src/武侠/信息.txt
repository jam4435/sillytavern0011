## 架构入口

- `src/武侠/index.html` 加载 `src/武侠/index.tsx`。
- `index.tsx` 使用 `React.StrictMode` 渲染 `App`，开发环境会让 effect 执行两次，容易放大初始化副作用。
- `App.tsx` 初始化路径: `initializeApp()` -> `loadMartialArtsDatabase()` -> `get变量('当前游戏存在')` -> `readGameData()` -> `getLastMessage()` -> 设置游戏状态。
- 保存存在时首屏通常是 `StartScreen` 后转入 `GameContent`，但大量非首屏代码已经被静态 import 进首包。

## 构建与首包问题

- `webpack.config.ts` 对 `src/武侠` 输出单个内联 HTML。
- 当前配置包含 `HtmlInlineScriptWebpackPlugin`、`HTMLInlineCSSWebpackPlugin`、`LimitChunkCountPlugin({ maxChunks: 1 })`。
- `LimitChunkCountPlugin({ maxChunks: 1 })` 会阻止 `React.lazy/import()` 真正拆出异步 chunk。
- `dist/武侠/index.html` 约 `793KB`，没有 `.chunk.js`；运行时还会在酒馆 iframe 里叠加若干 SillyTavern/JS-Slash-Runner 依赖。
- `App.tsx` 静态 import 了 `NewGameSetup`、所有面板聚合、`SettingsPanel`、`createOpeningStoryMessage` 等，导致设置页、新建流程、面板和部分 JSON 数据进入启动包。
- `gameInitializer.ts` 静态 import 多个 JSON，事件数据约 `49.7KB`，出生地数据约 `9.6KB`。
- `_合并后功法.json` 约 `304KB`、357 条功法；`martialArtsDatabase.ts` 虽然写了 dynamic import，但 `App.tsx` 启动时立即 `loadMartialArtsDatabase()`，且单 chunk 构建会把它压回首包。

## 数据读取/写入问题

- `src/武侠/utils/variableReader.ts` 的 `readGameData()` 不是纯读取。
- `readGameData()` 先 `getGameVariables()`，再 await:
  - `autoUpdatePlayerAttributes`
  - `autoUpdateCharacterAttributes`
  - `autoUpdateMartialArts`
- 这些 autoUpdate 会通过 ERA 写变量，并等待 `era:writeDone` 或 500ms timeout。
- `readGameData()` 后续仍基于最开始的变量快照映射 UI 数据，所以写入后的 `era:writeDone` 刷新在补偿旧快照问题。
- `useEventListeners.ts` 监听 `MESSAGE_RECEIVED`、`CHAT_CHANGED`、`era:writeDone`，每个都可能触发一次完整 `readGameData()`。
- `useSummaryDetection.ts` 也监听 `MESSAGE_RECEIVED`，随后调用 `checkSummaryTrigger()`，会再次扫描变量。
- 结果: 一条消息可能触发多次全量变量读取、自动补全写入、等待写入完成、再刷新。

## 渲染与样式问题

- `GameContent.tsx` 每次 render 都有较多日志，并对当前消息全文做 split/map。
- `settingsManager.applyRegexRules` 每次应用都会重新构造正则。
- `handleSettingsChange` 直接应用 DOM 设置，同时 effect 又会再应用一遍。
- `main.scss` 全量 import 所有模块样式，包括设置页、新建页和各面板样式。
- 样式中存在较多 `backdrop-filter`、`filter`、blur、动画、远程背景图。全屏背景加滤镜可能明显增加绘制压力。
- 用户背景如果是 base64 存在 localStorage，启动读取并应用到全屏背景也会放大首屏成本。

## 优化优先级建议

1. 先把 `readGameData()` 拆成纯读取与后台补全写入。
   - 新增类似 `readGameDataPure()`，只读取变量并映射 UI。
   - 新增类似 `completeGameDataInBackground()`，单飞执行自动属性/功法补全。
   - `MESSAGE_RECEIVED` 先纯读刷新 UI，再后台补全。
   - `era:writeDone` 只做纯读刷新，避免再次触发写入。

2. 给事件刷新加单飞/防抖。
   - 合并同一轮 `MESSAGE_RECEIVED`、`CHAT_CHANGED`、`era:writeDone` 的重复刷新。
   - 对自身后台补全产生的 `era:writeDone` 做标记，避免立刻循环进入重补全。

3. 调整启动加载。
   - 不要在 `App.initializeApp()` 无条件加载 `_合并后功法.json`。
   - 只在功法面板、角色功法详情、新建开局真正需要时加载。
   - `createOpeningStoryMessage` 可改为提交新建角色时 dynamic import。

4. 拆包需要先改构建。
   - 若仍保留 `LimitChunkCountPlugin({ maxChunks: 1 })`，lazy import 基本不会降低首包。
   - 若酒馆卡支持多文件加载，可对 `src/武侠` 移除/条件禁用 `maxChunks: 1`，再 lazy `NewGameSetup`、`SettingsPanel`、面板组件和重数据模块。
   - 如果必须单 HTML，优先做数据读取/事件风暴治理，因为拆包收益有限。

5. 降低渲染和绘制成本。
   - 缓存 regex 编译结果。
   - memo 当前消息分段和面板 props。
   - 开发模式关闭大对象日志或按类别打开。
   - 降低全屏 blur/backdrop-filter 使用，尤其是 iframe 内全屏背景。

## 第一阶段较低风险改法

- 在 `variableReader.ts` 增加纯读函数，不改变现有数据结构。
- 在事件 hook 中用纯读替换 `era:writeDone` 和消息刷新路径。
- 后台补全加 in-flight guard。
- 保持原有 autoUpdate 行为，但从阻塞首屏改为后台执行。
- 验证点: 角色状态、功法、地图、事件、侠缘面板数据一致；收到新消息后 UI 能快速刷新；ERA 变量补全仍会落库。

### 当前卡顿点排序

1. 酒馆/提示词模板扩展重新处理整段消息。
   - 直接证据: `Prompt Template` 处理 18 条消息耗时 `27650ms`。
   - 放大因素: 最新消息原文 `157KB`，变量块超过 100 个。
2. 最新消息原文膨胀。
   - 直接证据: 编辑框内重复出现大量属性 `VariableEdit` 块。
   - 影响: 编辑确认、正则/模板处理、楼层格式化、iframe 重建都会按原文体量付费。
3. ERA 在确认后的变量写入/同步链路继续占主线程。
   - 直接证据: `era:writeDone` 后触发事件检查，扫描 272 个未发生事件并大量输出日志。
4. 武侠 iframe 自身 reload。
   - 生产 iframe HTML 约 `796KB`，内部导航在正常 5500 可用时约数秒级；但本次 57 秒等待中，新 iframe 尚未加入 DOM，所以不是此次确认卡顿第一原因。
