# 事件系统研究与候选内容

> 目的：把 CK2 / CK3 的事件思想移植为适合 HTML 游戏和 SillyTavern 角色卡的可验证框架。本文讨论的是系统结构和内容门类，不复制原作文本或精确数值。

## 结论先行

事件系统不是“偶尔弹出一段故事”的附属功能，而是整款游戏的叙事总线：

1. 地图、人物、关系、旅行、宴会、计谋、摄政、战争和继承向事件系统发出事实信号；
2. 系统从满足条件的候选事件中选择合适内容；
3. 玩家或 NPC 依据性格、资源和局势作出选择；
4. 规则引擎先结算硬状态；
5. LLM 再根据已结算事实生成角色化场景、对白和后续反应；
6. 结果写入历史日志、人物记忆、承诺账本和后续事件链。

因此建议把事件引擎列为 P0。没有它，宴会、出巡和人物生活会退化成互不相干的聊天窗口；有了它，同一套框架可以逐步增加内容，而不必为每个 DLC 式功能重做流程。

## 一、从 CK2 和 CK3 提炼出的共同结构

CK2 Wiki 将事件描述为“满足某些条件后发生的事情”，并按野心、破产、私生子、战斗、出生、童年、内战、内阁、宫廷、十字军、文化转化、监护等主题组织。CK2 的许多主动决议——宴会、集市、狩猎、朝圣、闭门隔离、寻找医师——本质上都是“检查前置条件和成本，然后开启一条事件链”。

CK3 的事件脚本进一步把结构拆得很清楚：

- 事件需要由 on_action、决议、互动、故事循环或其他事件触发；
- 触发条件决定事件对谁、何时有效；
- scope 保存本次故事涉及的人物、地点、头衔和物品；
- immediate 在展示前准备上下文；
- option 有自己的可见条件、成本、效果和 AI 选择权重；
- after 负责选项完成后的统一清理；
- 延迟事件和故事循环负责多阶段叙事；
- random、weighted 与 first valid 等选择方式控制随机性和优先级。

酒馆版无需复制 Clausewitz 脚本语法，但应保留这套因果分层。

## 二、建议的事件流水线

### 1. 事实信号

事件不能凭空扫描整个世界。先由其他系统发出结构化信号：

| 信号组 | 例子 |
|---|---|
| 日历 | 清晨、黄昏、季度、年度、季节、节庆日、承诺到期 |
| 人生 | 出生、成年、结婚、怀孕、患病、康复、死亡、继承 |
| 政治 | 获得/失去头衔、成为强力封臣、任命、请愿、投票、派系成立 |
| 地图 | 出发、进入伯爵领、抵达地点、路线受阻、离开领国 |
| 活动 | 发出邀请、宾客到场、宴会阶段开始、私下会面、活动结束 |
| 对话 | 作出许诺、拒绝请求、当众羞辱、透露线索、提交正式提案 |
| 阴谋 | 招募同谋、取得优势、发生泄密、决定执行、计谋败露 |
| 战争 | 宣战、战斗结束、围城完成、伯爵领被占领、俘虏、议和 |
| 领地 | 收支转负、控制变化、疾病进入、饥荒、工程完成 |
| 摄政 | 摄政开始、授权、滥权、权力越过阈值、君主归来 |

### 2. 候选筛选

每个信号只检查相关事件池。候选事件至少经过：

- 硬前置条件：人物存活、地点正确、关系存在、活动阶段正确；
- 信息前置条件：玩家是否知道该秘密或只知道传闻；
- 内容前置条件：相关角色未被另一个关键场景占用；
- 唯一性：同一故事不能并发两次；
- 冷却：同类事件近期没有重复；
- 权重：性格、关系、地区、季节、压力、风险等影响概率；
- 配额：一段时间内只展示有限数量的非关键事件；
- 无事件权重：即使存在候选，也允许世界安静地推进。

### 3. 场景装配

事件实例保存明确作用域：

| 作用域 | 说明 |
|---|---|
| 主角 actor | 当前需要作出选择的人 |
| 发起者 initiator | 谁造成或提出了这件事 |
| 对象 target | 被说服、受害、受益或被调查者 |
| 见证者 witnesses | 能知道公开事实的人 |
| 地点 location | 伯爵领及内部地点 |
| 政治对象 | 头衔、派系、内阁席位、战争、摄政 |
| 叙事对象 | 信件、宝物、秘密、承诺、记忆 |

这一步先由规则系统完成。LLM 只能使用提供的作用域，不得随意召来不在场角色或把未知秘密写成公开事实。

### 4. 展示与选择

事件可有四种表现形态：

1. 通知：纯结果，不打断玩家；
2. 事件卡：短场景和 1—4 个明确选项；
3. 对话场景：进入 SillyTavern 自由对话，结束后整理成正式提案；
4. 危机暂停：继承、宣战、死亡、摄政政变等强制玩家处理的事件。

每个选项都应显示：

- 为什么可选或不可选；
- 即时成本；
- 确定后果；
- 风险范围或可能结果；
- 哪个性格特质、关系或把柄在影响它；
- 是否会创建承诺、秘密、罪行或后续事件。

### 5. 规则结算

结算顺序固定为：

1. 重新校验选项在提交时仍合法；
2. 扣除成本并进行确定性检查/随机检定；
3. 修改硬状态；
4. 创建后续计划、期限、承诺和冷却；
5. 生成公开事实与各角色可知事实；
6. 写入历史日志；
7. 再请求 LLM 叙述已经发生的结果。

任何 AI 文本都不能先于硬状态宣布领地转移、角色死亡、怀孕、逮捕成功、婚姻成立或战争胜负。

## 三、推荐事件数据结构

每个事件定义至少包含以下字段：

| 字段 | 用途 |
|---|---|
| id / version | 稳定标识与存档迁移 |
| category / tags | 主题、强度、内容分级和事件池 |
| triggerSignals | 响应哪些事实信号 |
| preconditions | 硬触发条件 |
| weight | 候选权重及性格/环境修正 |
| cooldown / uniqueKey | 防止重复与并发 |
| priority / interrupt | 是否暂停、是否压过普通事件 |
| scopes | 人物、地点、头衔、战争、秘密等对象 |
| knowledgePolicy | 谁知道什么，是否可被转述 |
| presentation | 通知、事件卡、对话场景或危机 |
| options | 玩家可见选项及各自前置条件 |
| aiChoiceWeights | NPC 按性格与利益选择的理由 |
| resolution | 交给规则引擎执行的白名单效果 |
| memories | 哪些角色以何种强度记住此事 |
| followUps | 延迟事件、分支事件或故事循环 |
| cleanup | 释放场景锁、临时角色和暂存变量 |
| sourceNote | 灵感来源和原创边界 |

事件实例还要保存随机种子和结算版本，确保读取存档后不会因为重新抽取而改变结果。

## 四、事件并不等于纯随机

建议区分五种内容单位：

| 单位 | 用途 | 示例 |
|---|---|---|
| 规则反应 | 必然响应一个事实，通常只显示通知 | 承诺逾期、头衔继承、信件送达 |
| 加权事件 | 在合法候选中随机抽取 | 路遇盗匪、宴会失言、医师治疗事故 |
| 主动决议 | 玩家支付成本主动开启 | 办宴会、巡游、朝圣、寻找医师 |
| 活动阶段 | 依附于活动状态机 | 迎宾、入席、敬酒、私谈、散席 |
| 故事循环 | 数周到数年的多阶段进度 | 教育、宿敌升级、摄政夺权、社团晋升 |

首版应以“规则反应 + 活动阶段 + 少量加权事件”为主。长故事循环需要跨存档、去重和角色死亡后的收尾能力，适合在基础验证后扩展。

## 六、首条竖切的事件包

目标已经确认为：真实欧洲的 12—20 个伯爵领中，玩家出巡赴宴，并争取两名封臣支持。

建议至少准备以下事件槽位；每个槽位可有 2—4 个性格化变体，而不是一开始追求上百条。

| 编号 | 阶段 | 事件槽位 | 验证的系统 |
|---|---|---|---|
| VS-E01 | 规划 | 决定出巡目的、路线和随从 | 地图、成本、意图 |
| VS-E02 | 规划 | 确定留守摄政与授权范围 | 摄政、职位、信任 |
| VS-E03 | 邀请 | 宴会邀请送达、接受或附条件 | 信件、延迟、接受度 |
| VS-E04 | 出发 | 强力封臣要求临行前承诺 | 谈判、承诺账本 |
| VS-E05 | 途中 | 道路、天气或战争迫使改道 | 邻接、危险、时间 |
| VS-E06 | 途中 | 与旅伴/当地人发生可选会面 | 同地对话、传闻 |
| VS-E07 | 抵达 | 主人以礼仪或冷遇表态 | 身份、好感、公开记忆 |
| VS-E08 | 开宴 | 座次安排触发荣辱冲突 | 排名、宿敌、见证者 |
| VS-E09 | 开宴 | 公开敬酒：和解、施压或许诺 | 声望、性格、承诺 |
| VS-E10 | 席间 | 第一名封臣提出明确支持条件 | 反提案、资源校验 |
| VS-E11 | 席间 | 竞争者打断或抬价 | 多人场景、利益冲突 |
| VS-E12 | 私谈 | 创造私密会面窗口 | 场景权限、秘密 |
| VS-E13 | 私谈 | 第二名封臣要求职位/婚约/减税 | 契约、未来义务 |
| VS-E14 | 插曲 | 酒后失言暴露线索或制造误会 | 信息边界、怀疑 |
| VS-E15 | 插曲 | 宴会主人请求玩家裁决争端 | 领主裁决、两难 |
| VS-E16 | 远方 | 摄政来信报告紧急事务 | 异步事件、缺席代价 |
| VS-E17 | 结宴 | 宾客依据公开表现重新站队 | 派系、关系、记忆 |
| VS-E18 | 返程 | 是否绕路拜访未被说服者 | 路线、时间压力 |
| VS-E19 | 结算 | 检查两份支持是否真实、附带何条件 | 目标、协议状态 |
| VS-E20 | 后续 | 承诺期限、摄政行为和宴会传闻开始发酵 | 延迟事件、世界推进 |

竖切不能只检查“支持数达到 2”。支持应至少有三种状态：

- 口头倾向：随时可能改变；
- 有条件承诺：条件成立或被登记后生效；
- 正式支持：可用于一次指定投票、派系、战争或继承争议。

否则自由对话很容易把一句客套话误判成政治盟约。

## 七、LLM 在事件系统中的权限

### 可以做

- 根据已经选定的事件和作用域写出场景；
- 依据人物性格、关系、记忆和秘密生成台词；
- 在白名单范围内提出反条件；
- 从已提供的原因中解释接受、犹豫或拒绝；
- 将硬结算结果改写为有戏剧性的后果叙述；
- 为同一个事件模板生成不同措辞和小型非状态细节。

### 不可以做

- 自行选择未通过触发条件的事件；
- 创造不在场、已死亡或未知的人物；
- 把传闻自动变为真相；
- 自行决定随机检定结果；
- 绕过资源、法律、位置和身份限制；
- 直接新增/删除头衔、婚姻、孩子、死亡、囚禁或战争；
- 通过叙述覆盖已经结算的事实；
- 把闲聊中的假设当作正式承诺。

推荐使用“规则选事件 → LLM 演场景并提交行动调用 → 规则自动校验与结算 → 写入事件/协议记录 → LLM 叙述已提交后果”的闭环。只有事件或提议在规则上要求玩家回应时才暂停；已经发生的负面结果不能被玩家用不确认取消。

## 八、内容节奏与性能

CK3 Wiki 的 on_action 资料专门提醒不要在每个周期对所有角色做嵌套全量扫描。酒馆版更需要控制上下文和请求次数：

- 玩家当前场景、旅行队伍、当前活动宾客使用高精度事件；
- 重点角色按日/周推进；
- 背景角色按月/季度批处理；
- 不可见的普通事件只记录一行摘要，不调用 LLM；
- 只有事件卡、重要信件和对话场景调用 LLM；
- 每个时段设置打断预算，例如最多 1 个关键事件 + 2 个普通通知；
- 重复事件按标签和参与人物共同冷却；
- 背景结果在人物重新进入视野时合并成“近况”。

## 九、验收标准

事件引擎进入实现前，建议用以下标准审批：

1. 同一存档重载不会重新抽取已经确定的事件；
2. 角色死亡、离场或活动取消后，相关事件能安全失效；
3. 不满足地点和信息条件时，事件不会泄露角色或秘密；
4. NPC 选项能显示性格与利益为何提高/降低权重；
5. 事件效果只能调用登记过的规则命令；
6. 每个硬状态变化都有来源事件和历史记录；
7. 事件链可超时、取消和收尾，不留下永久场景锁；
8. 纯背景推进不会为每个 NPC 调用一次 LLM；
9. 玩家可区分“已发生事实、传闻、意图和承诺”；
10. 首条竖切能够从 VS-E01 走到 VS-E20，并在多个选择路径下正确成功或失败。
