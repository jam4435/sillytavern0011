# 04. 验收与排错

目标：用可复现证据证明角色卡能初始化、能更新、能在下一回合读取最新状态，并在存在界面时正确双向同步。

## 1. 静态结构检查

- [ ] 成品位于 `src/角色卡名/`。
- [ ] `schema.ts` 只定义并导出 `Schema` 与类型。
- [ ] `脚本/变量结构/index.ts` 单独调用 `registerMvuSchema(Schema)`。
- [ ] `initvar.yaml`、更新规则和 Schema 字段完全一致。
- [ ] `变量列表.txt` 使用单数 `<status_current_variable>`。
- [ ] 输出格式来自当前初始模板的 JSON Patch 协议。
- [ ] `index.yaml` 已注册四个变量条目和必要脚本。
- [ ] `[initvar]变量初始化勿开` 保持禁用。
- [ ] 三个常驻变量条目为系统 D0，并禁止互相递归激活。
- [ ] JSON Patch 路径从 Schema 根开始，不带 `/stat_data`。
- [ ] 有状态栏才放占位符与加载正则；没有状态栏则两者都没有。
- [ ] 脚本库和正则 UUID 固定且互不重复，没有在每次生成时随机改已有 ID。

## 2. 构建检查

根据改动范围选择：

```powershell
pnpm dump
pnpm build:src
pnpm lint
pnpm test
```

或开发时运行：

```powershell
pnpm watch
```

至少确认：

- 目标 `schema.ts` 能导入；
- 目标目录生成 `schema.json`；
- `initvar.yaml` 不再有 schema 类型错误；
- 变量结构脚本和状态栏能编译；
- `dist/角色卡名/...` 中出现 `index.yaml` 引用的产物。

不要为了让检查变绿而手改 `schema.json` 或 dist。应修正源文件后重新生成。

若仓库本身已有无关错误，要区分“本次改动导致”和“原有问题”，并在交付时说明。

## 3. 运行验收顺序

### A. 初始化

1. 导入或更新角色卡脚本。
2. 新建聊天；旧聊天不会自动按新 initvar 重置。
3. 在日志中确认 MVU 和变量结构脚本已加载。
4. 在变量管理器中确认最新楼层存在 `stat_data`。
5. 对照 `initvar.yaml` 检查字段、类型和初始值。

### B. 一次真实更新

1. 输入一个必然触发某字段更新的测试行为。
2. 查看原始 AI 回复，确认包含完整 `<UpdateVariable>`。
3. 确认 `<JSONPatch>` 是合法 JSON 数组。
4. 确认路径和 value 类型正确。
5. 在变量管理器中确认实际值已更新并通过 Schema transform。

### C. 下一回合

1. 再发送一条普通消息。
2. 用提示词查看器确认变量列表展示的是更新后的值。
3. 确认模型没有再次处理上一回合已经完成的事件。

### D. 多开局

分别新建聊天选择每个开局，确认各自 `<initvar>` 生效，且不存在公共 initvar 与开局覆盖互相打架。

### E. 状态栏

1. 确认第一条消息的占位符被正则替换成界面。
2. 确认状态栏读取的是它所在楼层，而非最新楼层。
3. 修改一个允许玩家编辑的字段。
4. 等待同步后检查变量管理器。
5. 切换到旧楼层再回来，确认值仍然正确。

## 4. 故障树

### 没有 `stat_data`

按顺序检查：

1. 是否是新聊天；
2. `index.yaml` 中 MVU 脚本是否启用；
3. `[initvar]变量初始化勿开` 名称是否保留、条目是否存在且禁用；
4. initvar 文件路径是否正确；
5. initvar 是否为合法 YAML，且满足 Schema 输入结构；
6. 变量结构脚本是否加载，远程/编译产物 URL 是否正确；
7. 日志是否出现初始化或 Schema 注册错误。

不要先改状态栏；没有 `stat_data` 是初始化链路问题。

### 日志没有 Schema 注册成功

检查：

- `脚本/变量结构/index.ts` 是否编译；
- `index.yaml` 是否导入正确的 dist URL；
- 角色卡目录名是否仍是模板占位名；
- `schema.ts` 是否导出 `Schema`；
- 脚本是否在 `$(() => {})` 中注册；
- 控制台是否有远程资源或 TypeScript 错误。

### AI 不输出 `<UpdateVariable>`

检查提示词查看器中的最终请求：

- 变量列表、更新规则、输出格式是否真的存在；
- 条目是否启用、插入位置是否正确；
- 输出格式是否被其他提示词覆盖；
- 本轮是否真的有更新依据；
- 模型是否把更新块放在代码围栏或使用了错误标签。

不要把“本轮无需更新”误判为故障。先设计一个必然触发的测试事件。

### 有更新块，但变量没有变化

检查原始回复，而非只看折叠后的显示：

- `<JSONPatch>` 是否为合法 JSON；
- `op` 是否是模板支持的操作；
- path 是否存在、是否错误包含 `/stat_data`；
- `value` 类型是否符合 Schema；
- 是否尝试更新 `_` 只读或派生字段；
- `replace` 是否用于不存在的路径；新增键应使用 `insert`；
- Schema transform 是否把结果纠正回原值；
- 日志是否指出某条命令被丢弃。

### 出现变量更新错误或整表校验失败

1. 保存更新前 `stat_data`。
2. 保存原始 `<JSONPatch>`。
3. 逐条应用或缩小到单条操作。
4. 用 Schema 对预期结果执行 `safeParse`。
5. 对照 `z.prettifyError()` 的路径修正类型或缺失字段。

常见原因：数字写成无法转换的文本、枚举值不合法、动态对象子字段不完整、remove 后仍为必填、transform 非幂等。

### 下一回合重复更新同一事件

检查：

- `[不发送]去除变量更新` 正则是否只格式提示词并正常工作；
- 变量列表是否展示最新值；
- 更新规则是否强调只根据当前回复中的新事实更新；
- 模型是否把历史事件当成当前事件；
- 任务/物品是否在完成后正确移除或标记完成。

### EJS 没有按条件生效

检查：

- 提示词模板插件是否安装且游玩时启用；
- EJS 语法是否闭合；
- `getvar` 路径是否带正确的 `stat_data`；
- 变量不存在时是否有默认值；
- 条目是否经过模板处理；
- 提示词查看器中的最终文本是否只保留预期分支。

制作卡时给 AI 阅读源提示词，应避免让宏/EJS先被展开；游玩测试时则必须启用处理。具体开关依用户所用写卡工具而定。

### 状态栏不显示

检查：

- 第一条消息是否有 `<StatusPlaceHolderImpl/>`；
- 状态栏正则是否启用且为仅格式显示；
- 替换内容中的远程 URL、角色卡目录名和 dist 路径是否正确；
- `index.html` 是否已构建并可访问；
- 浏览器控制台是否有加载或挂载错误。

### 状态栏显示但不刷新/不保存

检查：

- store 是否显式使用 `getCurrentMessageId()`；
- 入口等待的是否是同一 `message_id` 的 `stat_data`；
- 组件路径是否写成 `store.data.角色...`，而不是 `store.data.stat_data...`；
- 传给 `defineMvuDataStore` 的是否是完整 Schema；
- 修改后的整表是否能通过 `schema.safeParse`；
- 是否错误使用 `additional_setup` 做一次性赋值；
- 是否另有脚本持续覆盖同一字段。

## 5. 排错时应收集的证据

向他人或 AI 提问时提供：

- 目标角色卡目录与相关文件；
- 当前楼层号和是否为新聊天；
- 更新前后的完整 `stat_data`；
- 原始 AI 回复中的 `<UpdateVariable>`；
- 日志/控制台完整错误，而非只说“不能用”；
- 提示词查看器中实际发送的变量三件套；
- 可复现的最短操作步骤；
- 预期结果与实际结果。

不要只发美化后截图；变量路径、JSON 和错误堆栈通常更有价值。

## 6. 旧资料禁止照搬表

| 旧写法                                  | 当前做法                                 |
| --------------------------------------- | ---------------------------------------- |
| Schema 与注册代码放一起                 | `schema.ts` 纯定义，注册脚本独立         |
| `<status_current_variables>`            | `<status_current_variable>`              |
| 世界书 D4、顺序 200                     | 复制当前模板；现模板为系统 D0、14720     |
| JSON Patch 路径 `/stat_data/角色/...`   | `/角色/...`                              |
| 用 `_.set()` 作为角色卡输出协议         | 使用当前模板 `<JSONPatch>` 协议          |
| MVU 自动加状态栏占位符                  | 第一条消息显式放置                       |
| 状态栏用 `getAllVariables()` 手工刷新   | `defineMvuDataStore`                     |
| 状态栏 HTML 手写 module script          | Webpack 注入                             |
| `COMMAND_PARSED` 只有 commands 一个参数 | `(variables, commands, message_content)` |
| 修改 `schema.json` 修错误               | 修改 `schema.ts` 后重新生成              |

## 7. AI 最终交付清单

- [ ] 变量只覆盖真实玩法需求，没有无界增长字段。
- [ ] Schema、initvar、规则和界面路径一致。
- [ ] 四个变量条目及脚本已在 `index.yaml` 接入。
- [ ] 可选 EJS、脚本、界面都有明确需求，不是模板堆砌。
- [ ] `schema.json` 和 dist 由命令生成。
- [ ] 至少验证一次初始化和一次真实更新。
- [ ] 若有状态栏，验证了旧楼层读取和玩家修改回写。
- [ ] 交付说明列出已运行命令、结果和未验证部分。
