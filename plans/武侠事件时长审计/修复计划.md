# 武侠事件时间线修复计划

依据 `审计报告.md` 与 `final-adjudication.json`（2026-07-26 审计定稿）制定。审计只举证未修改，本计划描述如何把问题真正改掉并验证。

> **决策已定稿（2026-07-26 用户确认）**：
>
> 1. 换算约定表采用**保守下限**口径（见 Phase 0 第 2 条）。
> 2. 5 条"较可能"项**一并修复**，修复范围为全部 **121 个候选文件**。
> 3. 段内时间预算不足时：约数锚点先取下限压缩，仍不够的段落汇总上报，逐段由用户裁决，不自作主张动硬锚点。
> 4. 硬锚点表：脚本初筛后**暂停，由用户逐条确认**再进入 Phase 1。

## 一、修复对象

630 条事件条目（`世界书/**/*事件条目-*.yaml`，JSON 内容）中：

| 类别                                   | 数量           | 修复动作概述                     |
| -------------------------------------- | -------------- | -------------------------------- |
| A. 单条事件时长明确过短                | 104            | 延后 `事件结束时间`              |
| B. 相邻事件间隔不足（开头承接锚点）    | 10（+2 较可能）| 延后本条 `触发条件`，级联顺延    |
| C. 依赖前序修复而必须顺延              | 4              | 随 A/B 修复自动顺延              |
| D. 向后计划落空（"明日"未兑现）        | 2              | 调整兑现事件的触发时间           |
| 去重合计                               | **116 明确 + 5 较可能** | 射雕 29 / 神雕 87（另 5 条较可能）|

分布：射雕覆盖 17 个回目，神雕覆盖 31 个回目；神雕第 2–16 回、第 24–26 回、第 32 回、第 35–39 回是密集区。

问题清单以 `final-adjudication.json` 的 `finalOverallConfirmedEventIds` / `finalOverallLikelyOnlyEventIds` 为准。

## 二、修复后必须满足的不变量

1. **单条自洽**：`触发条件` < `事件结束时间`；时长 ≥ 详情内最大时间锚点（"次日决斗"必须跨到翌日，"十余日"必须 ≥ 十余日）。
2. **相邻留白**：同作品按时间排序后，上一条结束 ≤ 本条触发；本条开头若有"次晨 / 数日后 / 半年"等承接锚点，留白必须满足锚点。
3. **向后计划**：条目中"明日赴约 / 三日后再会"等计划，其真实兑现事件（沿 `后续事件` 链，允许中间插入同期事件）必须落在承诺的时间。
4. **硬锚点不动**：
   - 有原著/历史依据的年月（蒙古南征、襄阳战事、两次英雄大宴、华山之会、神雕十六年之约等）；
   - 两部作品的衔接时间（射雕结尾 → 神雕开场）；
   - `登场事件`（58 个，同样以 `触发条件.时间` 触发）：默认以该回 `01` 事件的完整触发时间为基准同步到其**上一个月**（仅月字段减 1；1 月回退上一年 12 月；日、时、分沿用 `01`）。若同一登场包包含尚未出生、或在本回长跨度后段才实际登场的人物，先拆分该人物，再同步其余人物。
5. **顺序不变**：只顺延和拉伸，不改变任何回目内事件的相对先后。
6. **最小 diff**：除时间字段（`触发条件` 的年/月/日/时、`事件结束时间`）外，不改动任何其他字段；未被标记的事件只允许因级联顺延被动移动。

## 三、总体策略

- **最小改动 + 级联顺延**：不做全书重排。只改 121 个候选，被迫顺延的后续事件由验证器自动检出、机械后移。
- **补丁先行**：所有改动先生成补丁 JSON（`eventId → {新触发, 新结束, 依据引文}`），经验证器全量校验 + 人工抽查后，才由脚本一次性写回文件。禁止子任务直接编辑世界书。
- **锚点分段**：以硬锚点切分时间段，段内时间预算 = 锚点间隔。预算不足是本计划最大的风险点（见第六节）。

## 四、实施阶段

### Phase 0 — 工具与锚点准备

1. 在 `scripts/audit-wuxia-event-durations.mjs` 基础上新增修复模式（或独立 `scripts/fix-wuxia-event-durations.mjs`）：
   - `--patch <file> --dry-run`：内存中应用补丁后重跑全部审计规则（单条时长、相邻留白、向后计划、锚点校验），输出违规清单与"被迫顺延但补丁未覆盖"的事件；
   - `--apply`：按 JSON 精确写回 `.yaml` 文件，保持现有字段顺序与缩进，diff 仅时间字段。
2. 制定**换算约定表**并写入脚本常量，子任务统一引用、不得各自发明：
   次日 = +1 日；次晨 = 翌日 6–8 时；数日 = 3 日（下限）；十余日 = 12 日；连日 = 4 日；数月 = 3 月；半年 = 6 月；"朝行晚宿"长途 = 按里程估日。
3. 产出 `anchors.json` 硬锚点表：脚本先筛出候选（回目首事件、登场事件、含绝对年代/历史事件的条目），**由用户确认后冻结**。这是唯一需要人工先拍板的输入。

### Phase 1 — 分段补丁提案（并行子任务）

1. 按回目连续性把 121 个候选切成 **10–14 个工作包**（射雕 3–4 包，神雕 7–10 包，密集区一回一包）。每包输入：段内全部事件（含未标记者，供顺延计算）、审计 JSON 中的判定理由、前后硬锚点。
2. 每包一个子任务产出补丁提案，逐条给出：新触发/结束时间、引用详情原文的时间词依据、该包内被迫顺延的未标记事件及新时间。
3. 分类细则：
   - A 类：`结束时间 = 触发时间 + 按约定表换算的最大锚点`；
   - B 类：把本条触发时间推到满足开头锚点（如"次晨"→ 翌日晨），而不是把上一条提前；
   - C 类：不单独出提案，由验证器在前序修复后检出并机械顺延；
   - D 类：`神雕第12回-05`（英雄大宴须为 11回-09 的"明日"）、`神雕第22回-06`（金轮"明日回拜"）按承诺日期落位，中间同期事件一并核对。

### Phase 2 — 仲裁与合并

1. 合并各包补丁，重点检查**包边界衔接**（上一包末事件新结束 vs 下一包首事件触发）。
2. 照审计时的 hard-qc 流程做一轮逆向复核：对每条补丁验证"依据引文确实在详情中、换算符合约定表"；然后全量跑 `--dry-run`，迭代直至违规清单为空。
3. 5 条较可能项（`射雕16回-05、25回-06，神雕25回-05、27回-01、40回-01`）按用户决策**一并修复**：与明确项同流程出补丁、同批应用，但在提案中单独标注"较可能"类别及推断依据，便于复核时重点抽查。

### Phase 3 — 应用与回归

1. `--apply` 写回；`git diff` 抽查确认只有时间字段变化、格式无损。
2. 重跑审计原命令（`node scripts/audit-wuxia-event-durations.mjs --event-dir 世界书 --output-dir plans/武侠事件时长审计 --shards 3`），验收标准：单条时长明确项 0、跨事件明确项 0、向后计划明确项 0。
3. `pnpm generate:events` 重建 `src/事件脚本/generated/event-data`（runtime 分片是生成物，必须重建）。
4. `pnpm test`：`era-*` 测试中有 48 处引用具体事件时间，若 fixture 恰好引用被改事件，同步更新 fixture（属预期改动，逐条说明）。
5. 视需要 `pnpm build:src` 与 `pnpm sync` 推送酒馆。

### Phase 4 — 收尾

1. 在 `审计报告.md` 追加"修复结果"章节；补丁 JSON、`anchors.json`、复核记录留档在 `plans/武侠事件时长审计/`。
2. 存档兼容性说明：老存档中"已触发 / 已过期"事件状态基于旧时间，改时间后同一存档继续游玩可能出现事件重复触发或提前过期；建议新开档，或在说明中列出受影响区间。

## 五、验收标准

- 审计脚本重跑：三类"明确"问题全部归零；较可能项数量与用户决策一致。
- 全部 628 组相邻事件满足开头锚点约束；硬锚点事件时间与 `anchors.json` 完全一致。
- diff 仅含时间字段 + 必要的测试 fixture；`pnpm generate:events && pnpm test` 通过。

## 六、风险与决策点

| # | 风险 / 决策 | 处理（已定稿的标 ✅） |
| - | ----------- | -------- |
| 1 | **段内时间预算不足**：一回内叙事总需求（如"数月授诀"+ 后续多条）超过两个硬锚点的间隔 | ✅ 约数锚点取下限；仍不够的段落汇总上报，由用户逐段裁决（动锚点 vs 压缩叙事口径），不自作主张动硬锚点 |
| 2 | 级联顺延波及面：121 条之外预计还有 100–200 条未标记事件被动后移 | 全部进补丁、全部过验证器；报告中单独列出被动顺延清单 |
| 3 | 换算约定表数值（次日/数日/半年等） | ✅ 保守下限口径（Phase 0 第 2 条） |
| 4 | 登场事件与事件条目时间脱钩 | 验证器加规则 4 的登场事件检查，违规则同步顺延登场事件 |
| 5 | 5 条较可能项是否纳入 | ✅ 一并修复，提案中单独标注类别 |
| 6 | 硬锚点表确认方式 | ✅ 脚本初筛后暂停，用户逐条确认后冻结，再进入 Phase 1 |
| 7 | 老存档兼容 | 不做代码兼容，只做说明（见 Phase 4） |
| 8 | 是否同步酒馆 / 重打包（`pnpm sync` / `pnpm build:src`） | 未定，Phase 3 完成回归后再问 |

## 七、工作量预估

- Phase 0：脚本扩展 + 锚点表初稿，约半天；锚点确认需用户参与。
- Phase 1–2：10–14 个并行子任务 + 两轮复核，一个工作日内可完成。
- Phase 3–4：应用、回归、文档，约半天。
