武侠前端架构梳理
更新时间: 2026-06-08

一、构建与加载方式

`src/武侠` 是标准前端界面目录，不是后台脚本目录。它依赖 `index.html + index.tsx` 入口，由 webpack 打成单 HTML 偏内联产物，再通过 loader 正则挂入楼层 iframe。来源：src/武侠/index.tsx:5-35；webpack.config.ts:168-210；角色卡/金庸群侠传/正则/游戏页面.txt:1-7

当前构建层有三件事要一起看：

1. webpack 会对 `index.html` 入口做 bundle all，并倾向把脚本和样式内联到 `dist/武侠/index.html`。来源：webpack.config.ts:168-210
2. `npm run sync` 指向 `tavern_sync.mjs`，负责把构建产物和角色卡拆分文件同步回酒馆。来源：package.json:10-10；tavern_sync.mjs:62542-62630
3. 角色卡运行时实际加载的，是外层正则指向的 `http://localhost:5500/dist/武侠/index.html`。来源：角色卡/金庸群侠传/正则/游戏页面.txt:1-7；src/武侠/utils/loaderRegexGuard.ts:14-18,32-73

二、React 入口

`src/武侠/index.tsx` 的职责非常单纯：

1. 用 `$(() => {})` 等待酒馆 iframe 环境。
2. 查找 `#root` 并挂载 `<App />`。
3. 挂载后立刻执行 `ensureLoaderRegexSafety()`。
4. 在 `pagehide` 时卸载 root。

来源：src/武侠/index.tsx:11-35

这说明当前前端从一开始就不是“自己决定什么时候启动”，而是依赖酒馆消息 iframe 生命周期。来源：src/武侠/index.tsx:11-35；.cursor/rules/项目基本概念.mdc:175-198

三、页面与状态流

1. 页面流转

`App.tsx` 负责把 `start -> splash -> setup -> game` 串起来，并在启动时判断是空档、已初始化未开局，还是已有存档可直接继续。来源：src/武侠/App.tsx:144-179；src/武侠/架构.md:97-130

2. 主状态流

当前前端的主读链是：

`getAllVariables()` -> `getGameVariables()` -> `readGameDataPure()` -> `GameState` -> `App`

也就是说，前端不把本地 React state 当真源，而是把它视为 `stat_data` 的一次映射缓存。来源：src/武侠/utils/variableReader.ts:434-434,2285-2538；src/武侠/App.tsx:149-179

3. 存档恢复

检测到 `active` 存档后，`App.tsx` 会：

- 读 `readGameDataPure()`
- 异步安排 `scheduleGameDataCompletion('startup-existing-save', { fullScan: true })`
- 通过 `getLastMessageContent()` 取最近有效正文
- `parseOptions()` 提取选项
- 直接跳到 `game`

来源：src/武侠/App.tsx:149-170；src/武侠/utils/variableReader.ts:2470-2523

四、状态读取与补全链路

`variableReader.ts` 不是“简单读变量”的工具，而是当前前端最关键的数据枢纽：

1. `readGameDataPure()` 只读不写，用于渲染安全刷新。来源：src/武侠/utils/variableReader.ts:2285-2538
2. `scheduleGameDataCompletion()` 提供后台补全调度。来源：src/武侠/utils/variableReader.ts:2225-2285
3. `scheduleGameDataCompletionFromMvuUpdate()` 根据 MVU diff 做 scoped completion，而不是每次都 full scan。来源：src/武侠/utils/variableReader.ts:2225-2285；src/武侠/hooks/useEventListeners.ts:47-61
4. 变量值最终落在 `rawVariables.stat_data`，所以任何字段结构改动都必须从 `stat_data` 视角审视。来源：src/武侠/utils/variableReader.ts:434-434；@types/function/variables.d.ts:65-148；@types/iframe/exported.mvu.d.ts:1-10

五、事件监听与刷新

`useEventListeners.ts` 当前主要监听：

- `MESSAGE_RECEIVED`
- `CHAT_CHANGED`
- `era:writeDone`
- `Mvu.events.VARIABLE_UPDATE_ENDED`

职责分工是：

1. 消息或聊天变化时，刷新正文、选项和纯读状态。来源：src/武侠/hooks/useEventListeners.ts:78-113；@types/iframe/event.d.ts:193-224,289-320
2. MVU 变量更新结束时，只按 diff 调度补全，不直接强刷全部状态。来源：src/武侠/hooks/useEventListeners.ts:47-61；@types/iframe/exported.mvu.d.ts:94-118,179-188
3. `era:writeDone` 后做延迟纯读刷新，尽量把“写链”和“读链”拆开。来源：src/武侠/hooks/useEventListeners.ts:78-113；@types/iframe/event.d.ts:118-126

六、发送流程

用户发消息的主链在 `useMessageHandler.ts`：

1. `createChatMessages(user)` 先写用户楼层。来源：src/武侠/hooks/useMessageHandler.ts:18-226；@types/function/chat_message.d.ts:172-191
2. `flushPendingGameDataCompletion()` 确保补全落库再生成。来源：src/武侠/hooks/useMessageHandler.ts:18-226；src/武侠/utils/variableReader.ts:2225-2285
3. `generate({ should_stream: true })` 请求模型生成。来源：src/武侠/hooks/useMessageHandler.ts:18-226；@types/function/generate.d.ts:9-30,86-146
4. 写入 assistant 楼层后，解析正文与 `<option>`。来源：src/武侠/hooks/useMessageHandler.ts:18-226；src/武侠/utils/variableReader.ts:230-421

七、开局流程

新开局不是“前端先有一份 authoritative state，再同步回酒馆”，而是：

1. `NewGameSetup` 收集表单。
2. `initializeNewGameSession()` / `createOpeningStoryMessage()` 创建开场 assistant 楼层。
3. 通过 `era:insertByObject` 写入整份初始变量。
4. 等待 `era:writeDone`。
5. 再次用 `readGameDataPure()` 把状态读回前端。

来源：src/武侠/App.tsx:321-370；src/武侠/utils/gameInitializer.ts:238-456；@types/iframe/event.d.ts:118-126

八、ERA 变量块剥离与正文读取

这是当前前端正确性的关键层：

1. `stripEraVariableBlocks()` 剥离 `<VariableThink>` / `<VariableInsert>` / `<VariableEdit>` / `<VariableDelete>`。来源：src/武侠/utils/variableReader.ts:230-331
2. `stripFrontendLoaderArtifacts()` 剥离 loader 脚本和 body 壳。来源：src/武侠/utils/variableReader.ts:305-331
3. `getLastMessageContent()` 倒序扫描 assistant 楼层，跳过仅含 loader 的消息。来源：src/武侠/utils/variableReader.ts:349-365,2470-2523

如果这里被改坏，最直接的后果就是：正文被 loader 壳污染、选项解析失效、编辑确认后前端回退到错误楼层。来源：src/武侠/utils/variableReader.ts:230-421,2470-2523

九、loader guard

`loaderRegexGuard.ts` 的职责不是创建入口，而是保护入口：

1. 扫描当前角色、全局、当前预设三类正则。来源：src/武侠/utils/loaderRegexGuard.ts:4-12；@types/function/tavern_regex.d.ts:63-77,79-130
2. 识别“游戏页面”脚本名或 loader 特征字符串。来源：src/武侠/utils/loaderRegexGuard.ts:14-18,32-48
3. 若启用且 `run_on_edit=true`，就自动把它关掉。来源：src/武侠/utils/loaderRegexGuard.ts:57-73

这一步直接关系到编辑确认是否会把加载壳卷入重建链。来源：src/武侠/utils/loaderRegexGuard.ts:57-73；@types/function/tavern_regex.d.ts:48-56,92-130

十、性能优化现状

当前前端已经明确做过几类止血：

1. `readGameDataPure()` 和后台补全调度拆开，避免每次渲染都写变量。来源：src/武侠/utils/variableReader.ts:2225-2285,2285-2538
2. 监听层用 delayed refresh 和 MVU diff，尽量减少 full scan。来源：src/武侠/hooks/useEventListeners.ts:30-45,47-61,78-113
3. loader-only 楼层会被主动跳过，避免正文回退错误带来无谓刷新。来源：src/武侠/utils/variableReader.ts:349-365,2470-2523
4. `window.WuxiaRegexDebug` 被显式暴露出来，方便线上定位当前显示正则快照。来源：src/武侠/App.tsx:206-213

十一、主要风险

1. 最新 assistant 楼层仍是多用途承载体：正文、loader 壳、ERA 补丁可能叠在同一条消息里。来源：src/武侠/utils/variableReader.ts:230-421,2470-2523
2. 只要 loader URL 或脚本名变了，而 `loaderRegexGuard` / `variableReader` 没同步，入口识别就会失效。来源：src/武侠/utils/loaderRegexGuard.ts:14-18,32-73；src/武侠/utils/variableReader.ts:305-331,349-365
3. 自动总结、补全和事件脚本都可能继续触发写回，因此前端不能假设“一次 generate 后状态就稳定了”。来源：src/武侠/hooks/useEventListeners.ts:47-61,78-113；src/事件脚本/era-main.js:76-201
4. 当前构建是单 HTML 偏内联方案，不应把“再做更多动态拆包”当成首选性能解法。来源：webpack.config.ts:168-210

十二、结论

`src/武侠` 本质上是一条“变量纯读映射 + 后台补全调度 + 事件监听刷新 + 楼层生成发送”的前端链路，而不是普通展示页。后续修改最稳妥的顺序通常是：先看 `stat_data` 字段，再看 `variableReader` 与监听链，再看发送链，最后才动面板和样式。来源：src/武侠/架构.md:97-130,132-196；src/武侠/App.tsx:144-179,321-370；src/武侠/hooks/useEventListeners.ts:18-113；src/武侠/hooks/useMessageHandler.ts:18-226
