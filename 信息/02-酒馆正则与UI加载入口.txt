酒馆正则与 UI 加载入口梳理
更新时间: 2026-06-03

一、当前 UI 加载正则

根据用户截图，主要加载正则为：
- 脚本名称: 游戏页面
- 查找正则: /.+/s
- 替换为:
  <script>
  $('body').load('http://localhost:5500/dist/武侠/index.html')
  </script>
  </body>
  ```
- 作用范围: 用户输入、AI 输出
- 在编辑时运行: 是
- 仅格式显示: 是
- 最大深度: 1

这条正则的作用：
- 只要楼层正文非空，就把整条楼层显示替换为 loader script。
- loader script 再拉起武侠前端。
- 因此它是当前伪同层卡 UI 的显示入口。

二、为什么不能直接禁用

直接禁用“游戏页面”正则会导致：
- 楼层显示回退成原始正文。
- 大量 VariableInsert/Edit/Delete 变量块可能直接显示。
- 武侠前端不会加载。
- 当前伪同层体验失效。

所以它不能作为第一止血点粗暴关闭。

三、/.+/s 的真实性能定位

单看 /.+/s：
- 它不是灾难回溯正则。
- 对 15-16 万字符文本基本是线性扫描。
- 单次成本通常不是 30 秒级。

真正问题在于：
- 它在编辑时运行。
- 它每次都命中最新大消息。
- 它和其他显示正则、Prompt Template、ERA 变量块解析叠加。
- 最新消息体积已经到 16 万字符级。

四、重型正则旧热点

此前运行时基准发现过两类重型正则：
1. 思维链美化类
- 贪婪/跨全文匹配。
- 使用 ([\s\S]*) 这类全量捕获。
- 在 15 万字符消息上曾耗时 20 秒以上。

2. 去多余内容/Progress 类
- 大型 alternation。
- 对含大量变量块的长消息反复扫描。

优化后：
- messageFormatting 单独测试曾从约 33,683ms 降到约 4ms。
- 完整编辑确认从 30 秒级降到约 0.5-4.6s 级。

五、正则层短期建议

1. 保留“游戏页面”正则
- 它是当前 UI 入口。

2. 收窄“游戏页面”正则作用面
- 如果确认 UI 只需要 assistant 最新楼层，可考虑只勾 ai_output。
- 如果确认只需要最新楼层，可考虑 max_depth 从 1 收到 0。
- 这些需要在酒馆里实测，避免用户楼层也失去入口。

3. 关闭或优化其他重型显示正则
- 特别是 think/thinking、VariableEdit/Insert/Delete 美化、Progress 保留类规则。
- 对这种卡，显示正则应尽量做“短路、小范围、非贪婪、显式标签”。

4. 避免全消息捕获
- 少用 ([\s\S]*)。
- 优先锚定开头/结尾或明确标签。
- 避免为了替换短片段而让正则吞整条消息。

六、正则层长期方案

当前正则入口的根本问题：
- 用 /.+/s 吞整条消息作为 UI 入口。
- 任何编辑确认都必须重新对整条消息跑显示流程。

更稳的长期路线：
1. 改成显式占位符入口
- 例如消息中只放 <wuxia-ui></wuxia-ui> 或固定短标记。
- 正则只匹配这个短标记，不吞整条正文。

2. 改成脚本驱动挂载
- 由 Tavern Helper 脚本监听楼层渲染/更新。
- 脚本把前端挂到目标楼层 DOM。
- 这样 UI 入口和消息正文体积解耦。

3. 稳定资源地址
- 开发时可以用 localhost:5500。
- 实际使用应换成稳定静态地址或内联发布产物，避免没开端口时空白。

七、结论

“游戏页面”正则是必要入口，不是第一主犯。
当前正则层真正要处理的是：减少编辑确认时对 16 万字符最新消息的多轮扫描，尤其是与其他显示正则和 Prompt Template 的叠加。
