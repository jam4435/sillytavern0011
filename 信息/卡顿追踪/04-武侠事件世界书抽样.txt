三、文件类型

1. 登场事件
- 形如 射雕登场事件-第X回人物.json
- 数量约 23 个。
- 通常包含批量人物 insert。

2. 普通事件条目
- 形如 射雕事件条目-第X回-XX-事件名.json
- 数量约 256 个。
- 通常包含时间触发、事件详情、update/insert/delete。

四、变量指导文件

变量指导.txt 的意义：
- 它不是普通设定。
- 它规定 AI 每次回应先做 VariableThink。
- 再用 VariableInsert/Edit/Delete 输出纯净 JSON。

这说明世界书本身就是面向 ERA 变量写回的设计。
它会推动消息里持续产生变量块，间接放大最新消息体积。

五、字段结构

1. 登场事件常见字段
- 事件类型
- 所属回目
- 触发条件
- 新登场人物
- insert

触发条件基本是时间型：
{
  "类型": "时间",
  "年": ...,
  "月": ...,
  "日": ...,
  "时": ...
}

insert 中常放完整人物模板。

2. 普通事件常见字段
- 事件地点
- 触发条件
- 事件结束时间
- 事件引子
- 后续事件
- 事件详情
- update
- insert
- delete

事件详情是主体叙事，通常占据最多文本。

3. 人物模板常见字段
- 姓名
- 性别
- 外貌
- 性格
- 境界
- 初始属性
- 出生年份
- 状态
- 所在位置
- 身份
- 功法
- 重要物品
- 人物经历
- 关系网

4. delete 语义
- delete 多为字段级清空。
- 不是删除整个人物节点。
- 例如清空 所在位置、重要物品.铁杖 等。

六、触发方式

- 279/279 都有触发条件。
- 时间触发: 275 个。
- 前置事件触发: 4 个，集中在第 8 回连续事件。
- 后续事件字段出现在约 238 个文件。

判断:

这利于剧情推进，但也意味着事件系统或 Prompt Manager dry-run 会遇到大量可扫描节点。

八、卡顿相关判断

1. 世界书不是单个大文件拖慢。
- Top10 大文件只占总字节约 9.33%。
- 没有一个单独文件需要重点移除。

2. 压力来自重复全量扫描。
- 279 个 JSON。
- 每个都有触发条件。
- 大量 update/insert/delete 深层对象。
- 大量事件详情文本。

3. 对 Prompt Manager dry-run 有中等风险。
- 如果每次编辑确认都触发 world-info 扫描，会产生秒级剩余卡顿。
- 这与之前 2-3s 长任务判断一致。

4. 对事件脚本初始化有中等风险。
- 初始化/切聊天全量加载世界书时会扫描全部条目。
- 单次 checkEvents 也会扫变量中的未发生/进行中事件。

九、建议

1. 按章节拆分活跃世界书。
- 当前活跃章节常驻。
- 历史章节归档或按需启用。

2. 减少 dry-run 扫描面。
- Prompt Manager 如果能只扫描必要世界书，应启用。
- 避免所有事件条目在每次编辑确认后参与重算。

3. 压缩事件详情重复叙事。
- 重复设定外移。
- 事件条目保留触发、地点、结果差分和简要引子。

4. 批量人物登场只保留必要字段。
- 完整模板会放大 insert。
- 长期会继续推高变量块和消息体积。

十、结论

武侠事件世界书结构规整，规模中等。
它不是 57 秒卡顿的第一主因，但会放大 Prompt Manager/world-info dry-run、事件脚本初始化和全量扫描。
主要优化方向不是找单个大文件，而是减少重复全量扫描和常驻条目数量。
