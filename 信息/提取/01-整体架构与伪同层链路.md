# SillyTavern「伪同层 + ERA 变量 + 后台事件状态机」型 RPG 角色卡 —— 可复刻通用机制提取

> 本文从一张已完成的复合型角色卡（SillyTavern + 酒馆助手 / TavernHelper）的内部文档中提取**与题材无关的通用机制**。所有原文中的 IP 剧情、人名、门派、地名均已剥离，仅在需要说明数据格式时以占位形式保留（例如 `<事件条目->`、`大区/中区/小区`）。
>
> 阅读顺序建议：第 1 章（整体分工）→ 第 2 章（伪同层链路）→ 第 3 章（正则入口）→ 第 4 章（脚本与事件系统）→ 第 5 章（事件世界书）→ 第 6 章（前端）→ 第 7 章（复刻清单）。

## 0. 一句话心智模型

> **聊天消息楼层负责持久化；显示正则把最后一条 assistant 楼层改写成前端入口；隐藏楼层脚本只把其余楼层从宿主 DOM 上抹掉；`stat_data` 才是真状态；ERA 是变量补丁运输层；后台事件脚本是独立状态机；React 前端只是交互外壳。**

这句话是整套架构的压缩表示。复刻新卡时，**这七个角色一个都不能少，也一个都不能混**。绝大多数难以定位的 bug，都来自把其中两层的职责混在一起（例如"以为前端 state 是真源"、"以为楼层被删了"、"以为 display 正则不参与编辑链"）。

## 1. 卡的整体组成结构与分工

### 1.1 五层结构

一张这种类型的卡，**不是单页网页，也不是普通文本角色卡**，而是下面五层同时存在的复合体：

| 层 | 物理载体 | 职责 | 是否 authoritative |
|---|---|---|---|
| ① 角色卡内容层 | 角色卡 YAML（`index.yaml`）+ 世界书条目 | 首条消息、头像、世界书挂载、系统深度提示词条目、事件定义 | 内容定义的真源 |
| ② 显示层 | 酒馆正则（TavernRegex） | 决定楼层"最终显示成什么"，是 UI 入口 | 否（只改显示） |
| ③ 变量层 | `chat` 变量域下的 `stat_data`，由 MVU 维护，ERA 提供写入通道 | 保存全部游戏状态 | **是，唯一真状态** |
| ④ 事件层 | 后台脚本 iframe（事件状态机） | 何时触发事件、如何推进、何时结束、写哪些状态 | 状态变更的第二来源 |
| ⑤ 前端层 | 消息楼层 iframe 中的 React 应用 | UI 渲染、状态映射、发送消息、正文剥离、补全调度 | 否，只是 `stat_data` 的映射缓存 |

**关键认知：④ 和 ⑤ 是并列关系，不是父子关系。** 事件脚本运行在独立的脚本 iframe 中，前端运行在消息楼层 iframe 中，二者只通过 `eventOn` / `eventEmit` 和共享的 `stat_data` 协作。改 React 页面并不能覆盖全部状态变化来源。

### 1.2 角色卡 YAML 的双重身份

`index.yaml`（角色卡定义文件）同时是两样东西：

1. **角色卡内容清单**：首条消息、头像、描述、世界书挂载位。
2. **打包声明文件**：它记录了**正则矩阵**（每条正则的名称/启用/查找表达式/来源/目标/深度）、**脚本库矩阵**（每个脚本的名称/启用/按钮定义）、以及**事件脚本注入语句**。

这意味着：任何对正则、脚本、世界书的修改，最终都要能"回填"到这份 YAML 里，否则导出的卡与开发环境不一致。

### 1.3 拆分 / 回填（sync）流程

开发期采用"**拆分文件 ↔ 角色卡 YAML**"双向同步：

- **pull**：把角色卡中的长内容正则拆成 `正则/*.txt`、脚本拆成 `脚本/*.js`、世界书拆成 `世界书/*.yaml` 等外链文件。
- **push / bundle**：再把外链文件回填进角色卡 YAML，产出可发布的完整卡。
- 入口通常挂在 `package.json` 的一个 npm script（如 `npm run sync`）上，实现文件是一个独立的 mjs 同步脚本。

**两层产物概念**：
- 第一层：webpack 构建产物 `dist/<前端名>/index.html`、`dist/<事件脚本名>/index.js`。
- 第二层：角色卡拆分文件（正则/脚本/世界书）。

webpack 在 watch 模式下会串起 sync watch，使两层保持联动。

### 1.4 世界书的"三个发布面"陷阱（**通用坑，务必照搬这条纪律**）

同一份世界书内容会同时存在于三个地方：

1. **仓库真源目录**（开发期默认维护、单独 push/pull 的那份）。
2. **酒馆中角色实际绑定的世界书**（运行时真正被读取的那份）。
3. **角色卡包内的拆分副本**（发布时随卡携带的那份）。

**运行时只读第 2 份。** 只改真源而不 push 世界书、不重新打包角色卡，运行时数据不会有任何变化。发布检查必须覆盖三个面。

> 复刻建议：新卡从第一天就明确"哪个目录是真源"，并把另外两份视为**产物**而非编辑目标。文档中显式写明这一点，否则后期一定会出现"改了没生效"。

### 1.5 生命周期总览

1. **首次加载 / 继续存档**：loader 正则挂起前端 → React 入口渲染 App → App 用"会话状态探测 → 纯读状态 → 取最近正文"恢复界面，并安排后台补全。
2. **新开局**：前端创建开场 assistant 楼层 → 发 `era:insertByObject` 写入初始变量 → 等待 `era:writeDone` → 发出全局初始化信号唤醒事件脚本。
3. **用户发送消息**：创建 user 楼层 → flush 待处理补全 → `generate({ should_stream: true })` → 写入 assistant 楼层 → 解析正文与选项。
4. **变量更新后**：MVU 触发 `VARIABLE_UPDATE_ENDED` → 前端按 diff 调度 scoped 补全；事件脚本收到 `era:writeDone` 后决定是否跑事件检查。
5. **编辑确认**：酒馆改消息 → 重跑显示正则 → 变量重同步 → 外层事件处理；**旧 iframe 先被销毁，再由 loader 重新挂起前端**。

## 2. 伪同层链路：完整机制与实现要点

### 2.1 解决什么问题

用户期望的体验是"**一块常驻的游戏界面，随剧情不断更新**"，而不是"聊天记录一楼一楼往下堆"。真正的原生"同层组件"是对某条现有消息的 DOM 做增强（消息本体仍在，界面附着其上）。本方案不走这条路，而是用三个独立手段叠加出**视觉上的同层效果**，故称"伪同层"。

### 2.2 三个叠加手段

**手段一：显示正则改写楼层显示**
外层显示正则匹配整条消息，把**显示结果**（不是消息原文）替换成一段 loader HTML/脚本。

**手段二：loader 在楼层 iframe 内整页加载前端**
loader 的核心就是一行：在楼层 iframe 内把前端页面整体载入 body。开发期指向本地静态服务器地址，发布期指向内联快照或 CDN。

**手段三：后台脚本收缩宿主 DOM**
一个极小的脚本（十来行）做两件事：
1. 初始化时删除宿主页面 `#chat > .mes` 中**除 `.last_mes` 之外**的所有节点；
2. 监听 `CHAT_CHANGED`，之后 `reloadIframe()` 重载自身。

于是用户在页面上只看得到最后一楼，而那一楼被正则替换成了整个前端界面。

### 2.3 必须牢记的边界（复刻时原样照搬这些认知）

1. **DOM 被删 ≠ 消息被删。** 聊天文件里仍保存完整消息楼层，`getChatMessages()` / `setChatMessages()` 操作的都是完整消息对象。
2. **`is_hidden` ≠ 当前前台是否可见。** 这是两套正交的概念：`is_hidden` 是消息级属性（影响是否进提示词），DOM 收缩是纯视觉。
3. **隐藏楼层脚本是纯视觉层。** 它不负责消息裁剪、变量压缩、事件推进，也不减少 ERA 指令块。
4. **iframe 只是运行容器，不是状态源。** 前端在 `$(() => {})` 中挂载 React、在 `pagehide` 时卸载，生命周期完全由酒馆消息 iframe 决定，前端"不能自己决定什么时候启动"。
5. **最后一条 assistant 楼层是多用途承载体**：它可能同时承载「剧情正文 + loader 壳残留 + ERA 变量补丁块」，也可能**只剩 loader 壳**。这是后面第 6.4 节三层剥离逻辑存在的根本原因。

### 2.4 消息对象结构约定

`ChatMessage` 至少包含：`message_id`、`role`、`is_hidden`、`message`、`data`、`extra`。

`setChatMessages()` 的刷新粒度是重要开关：
- `{ refresh: 'affected' }`：只刷新受影响楼层（**默认选它**）。
- `{ refresh: 'all' }`：触发整聊天重载并发出 `CHAT_CHANGED`（**会连锁触发事件脚本重新初始化、隐藏楼层脚本重载，慎用**）。

### 2.5 复刻时改什么 / 照搬什么

**可原样照搬**：
- 隐藏楼层脚本（只需确认选择器 `#chat > .mes` / `.last_mes` 与你的酒馆版本一致）。
- 三层叠加的整体思路与职责划分。
- `refresh: 'affected'` vs `'all'` 的使用纪律。

**必须改**：
- loader 指向的 URL / 端口 / 路径（见第 3 章，改这个要连改三处）。
- 前端挂载节点约定（`#root` 或其他）。

## 3. 正则与 UI 加载入口机制

### 3.1 入口正则的配置模板

主入口是一条**显示侧**正则，通用配置形态如下（字段名按酒馆助手正则接口约定）：

| 字段 | 取值 | 含义 |
|---|---|---|
| 名称 | `游戏页面`（自定名，但要与 guard 的识别条件一致） | 脚本名，被 loader guard 用作识别键之一 |
| 启用 | `true` | |
| 查找表达式 | `/.+/s` | 匹配整条消息全部内容（`s` 使 `.` 跨行） |
| 来源 `source` | `用户输入=true`、`AI输出=true` | 两类楼层都命中 |
| 作用于 `destination` | `仅格式显示=true`（display 侧） | **不进入 prompt**，只改显示 |
| 最大深度 `max_depth` | `1` | 只作用于最新一层，历史楼层不被替换 |
| `run_on_edit` | **必须为 `false`** | 见 3.4 |
| 替换内容 | 在楼层 iframe 中执行 `$('body').load('<前端URL>')` | loader 本体 |

> `max_depth: 1` 是关键：它保证只有最新楼层变成游戏界面，历史楼层保持原样（虽然它们通常已被隐藏楼层脚本从 DOM 移除）。

### 3.2 显示链的执行顺序

楼层最终怎么显示，由这条链决定，**与 React 无关**：

```
消息原文 → 宏替换 → 酒馆正则（display 侧） → HTML 化 → 渲染
```

对应的显示侧接口是 `formatAsDisplayedMessage()` / `retrieveDisplayedMessage()`，它们**不改消息源**。所以"正则改写的是显示结果，不是聊天原文"——楼层里真实保存的正文和 ERA 变量块仍在，只是显示时被 loader 壳覆盖。

### 3.3 备用的"内联快照正则"位

除主 loader 正则外，卡里通常还会有一条**默认禁用**的 display 正则，其替换内容直接内联了一整份前端构建快照。

它的存在原因是 sync 机制：pull 把长内容正则拆到外链 txt，push/bundle 再回填。于是角色卡可以同时保留「开发期的 loader URL 正则」和「一次性内联的构建快照正则」。

> **复刻用途**：发布给最终用户时，用户机器上没有 `localhost:5500`，所以发布版必须切到内联快照那条（启用内联、禁用 loader），或改成公网 URL。这是一个**发布开关**，建议在文档里显式记录。

### 3.4 `run_on_edit` 为什么是高风险项（**通用机制，必须复刻**）

`destination.display = true` 只说明这条正则**不进入 prompt**，**不说明它不参与楼层重建**。酒馆在"编辑确认"后会重新格式化并重新渲染楼层，display 正则依然会在编辑链中执行。

对 loader 型正则来说，编辑确认会发生：
1. 旧 iframe 被销毁；
2. 楼层重新命中 loader 正则；
3. loader 再次执行整页加载；
4. 新前端稍后才挂回。

如果 `run_on_edit = true`，更严重的后果是：**最新 assistant 楼层可能退化成"只有 loader 壳"的消息**，进而让前端读正文时回退到更早的楼层，表现为"剧情倒退"。

### 3.5 loader guard：入口的第一道止血层

前端入口挂载后**立即**执行一个 guard 函数（如 `ensureLoaderRegexSafety()`），机制为：

1. **扫描三类正则**：当前角色正则、全局正则、当前预设正则。
2. **识别 loader 正则**，识别条件是"或"关系：
   - 脚本名等于约定的入口名（如 `游戏页面`）；
   - 或替换内容中包含 loader 特征字符串：`localhost:<端口>/dist/<前端名>/index.html`、`127.0.0.1:<端口>/dist/<前端名>/index.html`、`$('body').load(`。
3. **若该正则已启用且 `run_on_edit === true`，自动改成 `false`**。

修改正则时的接口纪律：**优先用 `updateTavernRegexesWith()`（增量更新），不要轻易用 `replaceTavernRegexes()`**，后者会触发整聊天重载和 `CHAT_CHANGED`。

### 3.6 改入口时必须一起改的四处（**照搬这份 checklist**）

改 loader URL / 端口 / 路径 / 脚本名时，必须同步：

1. **角色卡 YAML 的正则矩阵**（入口定义本身）；
2. **loader guard 的识别条件**（特征字符串数组）；
3. **正文读取器对 "loader-only 楼层" 的判断**（见 6.4），否则新 loader 壳会被误当作正文；
4. **前端 `index.html` / `index.tsx` 的挂载节点依赖**（若改了 `#root`）。

另外还要检查构建/同步脚本中的端口与输出路径。

## 4. 脚本与事件系统

### 4.1 脚本分层

随卡携带的脚本通常是四个，职责严格分离：

| 脚本 | 默认状态 | 职责 | 是否与题材耦合 |
|---|---|---|---|
| **隐藏楼层** | 启用 | 宿主页面 DOM 收缩（纯视觉） | 完全无关，可直接照搬 |
| **ERA 变量框架（魔改版）** | 启用 | 通用变量运输层：把 `<Variable*>` 补丁块追加到最后一条 AI 消息并广播写入事件 | 完全无关，可直接照搬 |
| **事件脚本** | 以 `import 'http://localhost:<端口>/dist/<事件脚本名>/index.js'` 形式注入 | 事件业务状态机 | 结构无关、字段名需按新题材调整 |
| **调试** | **默认关闭** | 诊断工具 | 无关，可照搬 |

**注入方式差异要注意**：事件脚本在角色卡里不是"外链文件字段"，而是一条 `import` 语句直接注入，指向构建产物。发布时同样需要切换为内联或公网地址。

### 4.2 ERA 变量框架（变量运输层）

**解决的问题**：让 AI 能用一种"可被稳定解析的协议"修改结构化游戏状态，同时让脚本侧也有一个统一的写入通道。

**实现机制**：
- 暴露三个 API 处理器：`insertByObject` / `updateByObject` / `deleteByObject`，通过 `eventEmit('era:insertByObject', payload)` 等事件调用。
- 核心动作是：**把 `<VariableInsert>` / `<VariableEdit>` / `<VariableDelete>` 指令块追加到最后一条 AI 消息末尾**，然后触发写入完成事件 `era:writeDone`。
- 框架同时暴露三个 UI 按钮（挂在脚本库矩阵里）：**写入变量修改 / 手动同步状态 / 强制完全重算**。

**边界**：它是**通用**运输层，不知道任何业务规则。事件业务判断全在事件脚本里。

**复刻**：整个框架可原样照搬，包括三个按钮。改的只有"业务侧调用它时传的字段路径"。

### 4.3 MVU 与通用变量接口

三套变量能力并存，各有分工：

1. **通用变量 API**：`getVariables({ type: 'chat' })` / `replaceVariables` / `updateVariablesWith`。这是最底层的高层读写接口，前端与事件脚本都用它操作 `chat` 变量域。
2. **MVU**：在其之上维护 `stat_data`，并广播事件。`MvuData` 至少包含 `initialized_lorebooks` 和 `stat_data`；事件包括 `VARIABLE_UPDATE_ENDED`、`BEFORE_MESSAGE_UPDATE` 等。
3. **ERA**：变量补丁的**运输**通道（写进消息楼层，再由框架解析落库）。

**前端主读取口的约定**：使用 `getAllVariables()` → 取 `stat_data` → 交给纯读函数，**而不是直接调 `Mvu.getMvuData()`**。这样前端与 MVU 的具体实现解耦。

### 4.4 direct write vs ERA write（**核心设计决策，必须复刻**）

这是整个变量层最重要的一条边界。

**`writeDirect*`（直接写）**
- 实现：直接 `updateVariablesWith(..., { type: 'chat' })` 修改 `stat_data`，然后由一个共享写入器发出**自定义来源事件**（如 `<卡名>:directVariableWriteDone`）。
- **不生成 ERA 指令，也不伪造 `era:writeDone`。**
- **适用**：脚本自维护的 bookkeeping 字段——事件系统状态、世界事件归档、前端只读状态、传闻列表、线索与计数器。

**`writeEra*`（走 ERA）**
- 实现：`eventEmit('era:insertByObject' | 'era:updateByObject' | 'era:deleteByObject', payload)`，最终回到"追加变量块到最后一条 AI 消息"的链路。
- **适用**：希望沿用 ERA 历史语义的人物数据差分、剧情差分。

**判断原则（原样照搬）**：
> 事件 bookkeeping 尽量 direct write；人物与剧情差分再考虑走 ERA write。**不要把所有字段都回流到最后一条 AI 消息**——否则最新 AI 消息体积会持续膨胀。

### 4.5 回环 / 重入防护（"回合锁"机制）

**解决的问题**：脚本写变量 → 触发写入完成事件 → 脚本监听到该事件 → 又去写变量 → 无限回环。

**实现要点**：

1. **动作来源标记（action tag）**：每次写入都带上来源标记。事件脚本在收到 `era:writeDone` 时，会检查标记并**跳过**以下三类：
   - 纯 resync（仅状态重同步，无实质变更）；
   - `directChatWrite`（自己刚做的直接写）；
   - `apiWrite`（脚本主动发起的 API 写）。
   只有"外部来源"（如 AI 输出的变量块）才会真正触发事件检查。
2. **去重签名窗口**：写入助手维护一个签名窗口，对短时间内**内容相同**的写入请求做去重，防止重复 patch。
3. **读写链拆分**：前端在 `era:writeDone` 后做**延迟纯读刷新**，而不是同步刷新；MVU 变量更新结束时**只按 diff 调度补全**，不直接强刷全部状态。核心思想是"不把'刷新 UI'和'再写变量'绑死在同一事件里"。

**复刻**：这三条是与题材完全无关的通用防护，应当原样照搬，只需把自定义事件名换成新卡的前缀。

### 4.6 事件脚本模块划分（通用骨架）

以下模块划分与题材无关，建议原样沿用，只改内部字段名：

| 模块 | 职责 |
|---|---|
| `index.ts` | 入口，仅加载主控文件 |
| `*-main.js` | 初始化、注册监听器、调度事件检查、处理地点触发与线索计数 |
| `*-event-loader.js` | 扫描当前角色**已绑定**的世界书，按条目名前缀 + JSON 内容构造 `eventDefinitions` |
| `*-event-checker.js` | 判断是否到达触发时间、是否超过结束时间 |
| `*-participant-entry.js` | 校验事件定义合法性、规范化地点与参与人物、构造玩家参与快照 |
| `*-event-operations.js` | 初始化事件池、批量开始/结束事件、玩家参与、归档前结算、生成后续线索 |
| `*-world-events.js` | 计算 `原定 / 偏离 / 未知` 状态、迁移旧存档、把完成结果归档到世界事件区 |
| `*-write-helper.js` | 去重签名窗口、构建 insert/update/delete patch、提供 direct write 与 ERA write 两类落库接口 |
| `shared/*Context.ts` | 结局/差分比较规则 + 提示词上下文筛选规则，**供事件脚本与前端共用** |

> 把"比较规则 + 提示词筛选规则"抽到 `shared/` 供两端复用，是一个值得照搬的做法：避免前端和后台对"同一事件是否偏离"给出不一致判断。

### 4.7 事件定义的来源：从绑定世界书动态读取

**不扫硬编码目录，而是读"当前角色实际绑定的世界书"**：

1. `getCharWorldbookNames('current')` → 拿到主世界书 + 附加世界书名单；
2. `getWorldbook(name)` → 逐本读取条目；
3. 按**条目名前缀**过滤：`事件条目-`、`登场事件-`、`成长条目-` 等；
4. 对命中条目执行 `JSON.parse(entry.content)`。

**这是本架构最值得复刻的一点**：事件脚本**不硬编码任何剧情**，换题材时只需要换世界书内容，脚本本体一行不改。

**已知限制**（复刻时要么接受、要么改进）：
- 事件定义**只在初始化和 `CHAT_CHANGED` 时重读**，没有监听 `WORLDINFO_UPDATED` / `WORLDINFO_ENTRIES_LOADED`。在线更新世界书后，通常需要重载脚本或切换聊天才生效。
- 事件检查与世界书扫描是**线性成本**，条目量大时成本随条目数上升。

### 4.8 初始化与监听链路

**初始化流程**：
1. 读 `getVariables({ type: 'chat' })`；
2. 确认 `stat_data` 与"世界时间"字段存在；
3. 加载世界书事件定义；
4. 初始化事件池（分入未发生/进行中/已完成）；
5. 迁移旧存档的参与结局；
6. 补建缺失的世界事件归档。

**失败兜底**：如果初次初始化失败（通常因为还没开局、`stat_data` 不存在），脚本会**等待一个全局初始化信号**（如 `GameInitialized`）。这个信号由前端在"新开局流程完成"后发出。这解决了"事件脚本与前端谁先就绪"的竞态。

**三个监听器**：

| 事件 | 事件脚本的响应 |
|---|---|
| `CHAT_CHANGED` | 重新初始化整套事件系统（重读世界书、重建事件池） |
| `MESSAGE_SENT` | 处理后续事件线索计数器，并调度一次事件检查 |
| `era:writeDone` | 感知变量写完后的状态变化；但按 4.5 的动作标记跳过 resync / directChatWrite / apiWrite |

### 4.9 事件系统维护的状态字段（结构约定，字段名可换）

事件脚本主读写 `chat` 变量域下的 `stat_data`，典型字段树：

```
stat_data
├── 世界信息.时间                    # 世界时钟，事件触发的主时间轴
├── 事件系统
│   ├── 未发生事件
│   ├── 进行中事件
│   └── 已完成事件
├── user数据.所在位置                # 层级路径地点，事件地点触发依据
├── 参与事件.<事件名>                # 玩家已加入的事件快照
├── 世界事件.<完整事件名>            # 已完成普通事件的归档
├── 前端变量.事件结局状态.<完整事件名> # 隐藏状态，AI 不可写
├── 附近传闻                         # 由事件引子派生的可见传闻
├── 后续事件线索
├── 后续事件线索计数
└── 角色数据
```

**三个关键结构的 schema**：

```jsonc
// 参与事件.<事件名>
{
  "描述":  "字符串",
  "结局":  "字符串 —— 玩家参与后的当前预期最终结果",
  "insert": { /* 差分 */ },
  "update": { /* 差分 */ },
  "delete": { /* 差分 */ }
}

// 世界事件.<完整事件名>   —— 已完成事件的实际结果归档
{ "时间": "...", "地点": "...", "概要": "..." }

// 前端变量.事件结局状态.<完整事件名>
"原定" | "偏离" | "未知"
```

### 4.10 「原定 / 偏离 / 未知」隐藏状态机（**高价值通用机制**）

**解决的问题**：玩家介入剧情后，事件结果可能与原定不同。系统需要知道"这条事件线到底有没有被玩家改变"，以便：① 优先把偏离的历史喂给 AI；② 保持长线一致性。

**计算规则**（与题材无关，可直接照搬）：

- **比较对象**：`参与事件.结局`（对比事件定义中的 `事件概要`）+ 三类差分（对比事件定义中的 `insert/update/delete`）。
- **结局比较**：只去除首尾空白后做字符串比较。
- **差分比较**：
  - 排序对象键（避免键顺序造成假阳性）；
  - **忽略 `$` 开头的元数据键**（ERA 框架的内部字段）；
  - 缺失的差分视为 `{}`。
- **判定**：当前结局或任一有效差分与事件定义不同 → `偏离`；全部一致 → `原定`。
- **`未知`**：只用于旧存档无法恢复具体参与结局的情况；**绝不为"未参与事件"创建状态**。

**同步时机**：初始化时、参与事件相关的 ERA 写入完成后、事件结算前。

### 4.11 归档与失败保护

**归档规则**：
- **未参与事件**完成 → 用定义中的 `事件概要` 归档；
- **参与事件**完成 → 用当前 `参与事件.结局` 归档（而不是原定义）；
- 智能初始化时"直接判定完成"的过期事件 → 走相同归档路径；
- **登场事件不归档**（它不是结算型事件）。

**失败保护（值得照搬的两阶段提交模式）**：
1. 归档写入用 direct write（不走 ERA）；
2. 写完后**重新读取变量确认记录有效**；
3. 确认成功**才允许删除参与事件快照**；
4. 失败则保留快照，等待下次重试。

**旧存档幂等迁移规则**：
- 空结局 + 差分未变 → 补入原定概要，标 `原定`；
- 空结局 + 差分已变 → 写入回退文本（如"具体结果尚未记录"），标 `未知`；
- 已完成 + 参与过 + 参与快照丢失 → 用旧存档回退文本归档，标 `未知`；
- **已有有效世界事件的条目不会被重复覆盖**（保证迁移幂等）。

### 4.12 提示词上下文预算控制（**必须复刻的通用机制**）

**解决的问题**：历史归档会无限增长，不能全量塞进提示词。

**实现规则**：
- 变量中保存**全部**世界事件记录；
- 但主提示词与额外变量更新模型**最多接收 16 条**；
- 筛选算法：**先保留最近 8 条 `偏离 / 未知` 的记录，再按时间补足最近的普通记录**；
- 发送内容只有：事件名、时间、地点、概要（紧凑只读格式，如 `日期|地点|概要`）；
- **`前端变量` 只参与后台筛选，绝不整体序列化给 AI。**

这条规则实现在共享模块中，事件脚本与提示词条目共用同一份判断。

### 4.13 AI 可写区 vs 前端只读区（**协议边界**）

这是必须在世界书规则条目里向 AI 明确声明的边界：

- **AI 可写**：角色数据、`参与事件.结局` 与其三类差分、常规状态字段。
- **AI 只读（禁止写）**：`世界事件`（后台归档区）、`前端变量`（含隐藏状态）。

并且要给 AI 设置**修改门槛**：只有在"人物生死、长期状态、关系、阵营、关键物品、事件目标、或后续事件成立条件"发生实质变化时才允许修改 `结局`，并需同步修改对应差分；普通对话、顺序变化、无长期影响的插曲**不得触发重写**。

### 4.14 需要守住的四条边界（结论，原样照搬）

1. 世界书**定义**与运行时**归档**的边界；
2. **AI 可写区**与**前端只读区**的边界；
3. **direct write** 与 **ERA write** 的边界；
4. **真源**与**实际发布的世界书 / 角色卡副本**的边界。

## 5. 事件世界书的条目组织方式

### 5.1 世界书目录的三类内容

```
世界书/
├── 基础规则条目
│   ├── 变量指导.txt      # AI 写变量的协议
│   ├── 输出提示词.txt    # 状态注入模板
│   ├── cot.txt           # 叙事约束 / 思维链
│   └── <数值/判定>.txt   # 可选：额外判定模块（如骰子），也承担部分上下文注入
├── 线路A 事件条目-*      # 主线1 的事件 JSON
├── 线路A 登场事件-*
├── 线路B 事件条目-*      # 主线2 的事件 JSON（多线并存）
└── 线路B 登场事件-*
```

**多线并存是设计意图**：一张卡可以同时挂载多条剧情线（原文中是两条），只要条目名前缀符合 loader 的识别规则即可。复刻时可以直接用这个模式做"多章节 / 多分支 / 多 IP"的内容层。

### 5.2 条目命名前缀协议（**核心约定**）

事件 loader 依靠**条目名前缀**识别条目类型：

| 前缀 | 类型 | 是否强制 `事件概要` | 是否进入世界事件归档 |
|---|---|---|---|
| `<线路>事件条目-` | 普通事件 | **是** | 是 |
| `<线路>登场事件-` | 登场事件（人物注入包） | 否 | **否** |
| `<线路>成长条目-` | 成长事件 | 否 | 否 |

命名建议保留可读的层级信息，例如 `<线路>事件条目-第N章-NN-<事件短名>`，便于人工排序与定位。

条目内容是**纯 JSON**，由 loader 直接 `JSON.parse(entry.content)`。

### 5.3 普通事件条目的 schema

```jsonc
{
  "事件地点":     "大区/中区/小区",   // 层级路径，至少两级（必填）
  "触发条件":     { /* 主流是时间窗 */ },
  "事件结束时间": "...",
  "事件引子":     "非空字符串 —— 传闻文本",     // 必填
  "事件详情":     "给 AI 的完整剧情描述",
  "事件概要":     "非空字符串 —— 按原定发展完成后的简短持久结果",  // 必填
  "参与人物":     [ /* 人物名列表 */ ],          // 必填
  "insert":       { /* 新增差分 */ },
  "update":       { /* 修改差分 */ },
  "delete":       { /* 删除差分 */ },
  "后续事件":     [ /* 链式推进的下游事件名 */ ]
}
```

**严格校验规则（照搬）**：普通事件的 `事件地点`、`事件引子`、`事件概要`、`参与人物` 会在加载时统一校验；**任一必填字段无效，整条事件被跳过**。这带来一个重要运维后果：如果脚本已升级、而酒馆绑定的仍是缺少 `事件概要` 的旧世界书，**普通事件会整批加载失败，只有免校验的登场事件仍能加载**——表现为"游戏里什么剧情都不触发，但人物都在"。

### 5.4 登场事件条目的 schema

```jsonc
{
  "事件类型":     "登场事件",
  "所属回目":     "第N章",
  "新登场人物":   [ /* 人物名 */ ],
  "insert":       { /* 人物完整档案 */ }
}
```

它本质是"**人物数据库注入包**"，而不是结算型事件：不要求 `事件概要`，不进入世界事件归档，加载时免校验。

### 5.5 关键字段的运行期语义

**`事件地点`（层级路径 + 两级派生规则）**
- 格式：`大区/中区/小区`，至少两级。
- **传闻范围派生规则**：由 `事件地点` **前两级**派生。例如 `大区/中区/小区` → 传闻范围为 `大区/中区`。
- 行为：玩家在该范围**及其下级**地点时看到传闻；抵达**完整** `事件地点` 时转为参与事件。

> 这是一个非常干净的通用机制：一个字段同时驱动"远处听说"和"就地参与"两种交互，无需额外配置。复刻时只需把地名换成新世界的层级地名。

**`事件引子`**
- 普通事件的传闻文本，必须是非空字符串；
- **不携带地点 key**（地点由 `事件地点` 派生），运行时只读字符串本身。

**`事件概要`**
- 是"按原定发展完成后的**简短持久结果**"，**不是过程复述**；
- 玩家加入事件时 → 成为 `参与事件.结局` 的初始值；
- 未参与事件完成时 → 直接成为 `世界事件.概要`。

**`触发条件` / `事件结束时间`**
- 主流是时间触发；检查器以"时间窗 + 结束时间"为主路径。
- 复刻时可扩展为条件表达式，但要同步改 checker。

**`insert / update / delete`**
- 对应 ERA 支持的三类差分写法：人物经历、关系网、所在位置、状态、能力、物品等都在这三块结算。
- **玩家加入事件时，三块差分连同 `事件概要` 一起深拷贝进 `参与事件`**，成为允许 AI 按实际剧情修改的**结局快照**；
- 参与事件完成时，**以快照而非原定义结算**。

**`后续事件`**
- 事件天然链式推进；事件脚本会为这类事件生成**后续线索**与**倒计时计数器**。

### 5.6 三份基础规则条目的职责（**这三份比事件全文更重要**）

**① `变量指导.txt` —— AI 写变量的协议**
- 约束 AI 何时输出 `<VariableInsert>` / `<VariableEdit>` / `<VariableDelete>`；
- 明确"**无变化则不操作**"；
- 明确"**思考写在 `<VariableThink>` 中，指令块只放纯 JSON**"（这条极其关键：保证指令块可被稳定 `JSON.parse`）；
- 定义 `参与事件` 的固定结构与"结局修改门槛"；
- 把 `世界事件`、`前端变量` 声明为 AI 只读区域。

**② `输出提示词.txt` —— 状态注入模板**
- 把 `世界信息`、`user数据`、`参与事件`、`后续事件线索`、`附近传闻`、同场景角色数据拼装给模型；
- 使用**紧凑只读格式**降低 token（如传闻用 `日期|地点|传闻`）；
- 直接读取 `stat_data.*`，也就是说**事件结算结果是在提示词层就进模型的，不依赖前端 UI 展示**。

**③ `cot.txt` —— 叙事边界**
- 约束叙事一致性、时间推进、空间移动、参与事件优先、线索自然引出、同场景角色反应；
- 它不是事件 JSON，也不是前端代码，而是整张卡的**叙事宪法**。

**④（可选）判定模块条目**（原卡中是战斗骰子）
- 在数值区之前注入世界历史（最多 16 条，优先最近 8 条 `偏离/未知`，格式 `日期|地点|概要`）。
- 这说明"历史上下文注入"可以挂在任意合适的深度条目上，不必单独开一条。

### 5.7 复刻时改什么 / 照搬什么

**可原样照搬**：
- 条目命名前缀协议（`事件条目-` / `登场事件-` / `成长条目-`）；
- 普通事件 / 登场事件的完整 schema 骨架；
- `事件地点` 层级路径 + 前两级派生传闻范围的规则；
- `事件概要` 是"结果不是过程"的语义约定；
- `变量指导` 中"思考在 `<VariableThink>`、指令块只放纯 JSON"、"无变化则不操作"、只读区声明这三条协议；
- 提示词的紧凑只读格式与 16 条 / 8 条预算规则。

**必须改**：
- 所有地名、人名、事件名、章节编号；
- `事件详情` / `事件引子` / `事件概要` 的具体文本；
- `insert/update/delete` 中的字段路径（若新题材的角色属性结构不同）；
- `cot.txt` 的叙事风格约束。

## 6. 前端架构要点

### 6.1 构建与加载

- `src/<前端名>/` 是**前端界面目录**（区别于后台脚本目录），入口为 `index.html + index.tsx`；
- `index.html` **只提供 `#root`**，界面全由 `index.tsx` 在 iframe 内挂载；
- webpack 对入口做 **bundle all**，倾向把脚本与样式**内联**到 `dist/<前端名>/index.html`（单 HTML 偏内联方案）；
- 运行时实际加载的是 loader 正则指向的那个 URL。

> **性能取向纪律**：既然选了单 HTML 偏内联方案，就**不应把"再做更多动态拆包"当成首选性能解法**——iframe 内的动态 chunk 加载在酒馆环境下代价更高。

### 6.2 React 入口的四件事

```
1. 用 $(() => {}) 等待酒馆 iframe 环境就绪
2. 查找 #root 并挂载 <App />
3. 挂载后立刻执行 ensureLoaderRegexSafety()   ← loader guard
4. 在 pagehide 时卸载 root
```

第 3 步的位置很重要：**必须在挂载后立刻执行**，因为编辑确认链随时可能触发，越早关掉 `run_on_edit` 越安全。

### 6.3 页面流转与主状态流

**页面流转**：`start → splash → setup → game`
启动时判断三种情形：① 空档；② 已初始化但未开局；③ 已有存档可直接继续。

**主读链（照搬这个链条形状）**：
```
getAllVariables() → getGameVariables() → readGameDataPure() → GameState → App
```
**前端不把本地 React state 当真源，只把它视为 `stat_data` 的一次映射缓存。**

**存档恢复流程**：
1. `readGameDataPure()` 读状态；
2. 异步安排 `scheduleGameDataCompletion('startup-existing-save', { fullScan: true })`；
3. `getLastMessageContent()` 取最近有效正文；
4. `parseOptions()` 提取选项；
5. 直接跳到 `game` 页。

### 6.4 正文读取的三层剥离（**前端正确性的关键层**）

因为"最后一条 assistant 楼层"可能同时含正文、loader 壳、ERA 补丁块，所以必须做三层处理：

1. **`stripEraVariableBlocks()`** —— 剥离 `<VariableThink>` / `<VariableInsert>` / `<VariableEdit>` / `<VariableDelete>` 四类块。
2. **`stripFrontendLoaderArtifacts()`** —— 剥离 `<script>`、`<body>` 等 loader 壳残留。
3. **`getLastMessageContent()`** —— **倒序扫描** assistant 楼层，用 `isFrontendLoaderOnlyMessage()` 判断，遇到"只剩 loader 壳"的消息就**继续往前找**。

改坏这里的直接后果：正文被 loader 壳污染、选项解析失效、编辑确认后前端回退到错误楼层。

> **复刻要点**：三个函数的结构可原样照搬；`isFrontendLoaderOnlyMessage()` 的特征字符串必须与新卡的 loader URL / 脚本内容同步（见 3.6）。

### 6.5 状态读取与补全调度

`variableReader` 类模块不是"简单读变量的工具"，而是前端最关键的数据枢纽，四个能力：

1. **`readGameDataPure()`** —— **只读不写**，用于渲染安全刷新。这是"不要在渲染路径里写变量"这条纪律的实现。
2. **`scheduleGameDataCompletion(reason, opts)`** —— 后台补全调度（补齐缺失字段、修正结构），可指定 `fullScan`。
3. **`scheduleGameDataCompletionFromMvuUpdate(diff)`** —— 根据 MVU diff 做 **scoped completion**，而不是每次都 full scan。
4. **`flushPendingGameDataCompletion()`** —— 在发送消息前强制把待处理补全落库。

变量值最终落在 `rawVariables.stat_data`，**任何字段结构改动都必须从 `stat_data` 视角审视**。

### 6.6 事件监听与刷新分工

前端监听四个事件：

| 事件 | 响应 |
|---|---|
| `MESSAGE_RECEIVED` | 刷新正文、选项和纯读状态 |
| `CHAT_CHANGED` | 同上（整体重建） |
| `era:writeDone` | **延迟**纯读刷新（把写链和读链拆开） |
| `Mvu.events.VARIABLE_UPDATE_ENDED` | **只按 diff 调度补全**，不强刷全部状态 |

三条优化纪律（照搬）：
1. 纯读与后台补全调度拆开，避免每次渲染都写变量；
2. 监听层用 **delayed refresh** + **MVU diff**，尽量减少 full scan；
3. loader-only 楼层主动跳过，避免正文回退带来的无谓刷新。

### 6.7 发送流程（顺序不可颠倒）

```
1. createChatMessages(user)              // 先写用户楼层
2. flushPendingGameDataCompletion()      // 确保补全落库再生成
3. generate({ should_stream: true })     // 请求模型
4. 写入 assistant 楼层
5. 解析正文 与 <option> 选项
```

第 2 步在第 3 步之前是**必须**的：否则模型会读到未补全的状态。

### 6.8 开局流程（前端与后台的握手）

```
1. NewGameSetup 收集表单
2. initializeNewGameSession() / createOpeningStoryMessage() 创建开场 assistant 楼层
3. eventEmit('era:insertByObject', 整份初始变量)
4. 等待 era:writeDone
5. readGameDataPure() 把状态读回前端
6. 发出全局初始化信号（唤醒等待中的事件脚本）
```

**注意方向**：不是"前端先有一份 authoritative state 再同步回酒馆"，而是"**前端把初始变量写进变量层，再从变量层读回来**"。这保证前端和后台看到的是同一份数据。

### 6.9 调试出口

把正则快照调试对象显式挂到 `window`（如 `window.<卡名>RegexDebug`），方便线上定位"当前显示正则到底是什么状态"。这是一个低成本高收益的做法，建议照搬。

### 6.10 前端主要风险清单

1. 最新 assistant 楼层是多用途承载体（正文 / loader 壳 / ERA 补丁可能叠在一起）；
2. loader URL 或脚本名一改，guard 与正文读取器没同步 → 入口识别失效；
3. 自动总结、补全、事件脚本都可能继续触发写回，**前端不能假设"一次 generate 后状态就稳定了"**；
4. 单 HTML 内联方案下不要盲目做动态拆包。

### 6.11 修改前端时的推荐顺序

> 先看 `stat_data` 字段 → 再看 `variableReader` 与监听链 → 再看发送链 → **最后才动面板和样式**。

## 7. 复刻新卡的操作清单

### 7.1 可以原样照搬（几乎零改动）

- 隐藏楼层脚本（十来行，只需确认 DOM 选择器）；
- ERA 变量框架（魔改版）及其三个按钮；
- loader guard 的整体逻辑（只改特征字符串）；
- 正文三层剥离逻辑的结构；
- direct write / ERA write 的双通道设计与选择原则；
- 回环防护三件套（动作来源标记跳过、去重签名窗口、读写链拆分）；
- `原定 / 偏离 / 未知` 的比较算法（含"忽略 `$` 开头元数据键"、"排序对象键"、"缺失差分视为 `{}`"）；
- 归档的两阶段提交（写入 → 回读确认 → 才删快照）；
- 提示词预算控制（最多 16 条、优先最近 8 条偏离/未知、紧凑分隔格式）；
- 事件脚本的模块划分骨架；
- 世界书条目名前缀识别机制；
- 前端主读链形状与"纯读 / 补全调度分离"纪律；
- `shared/` 共享比较与筛选规则的做法；
- 三个发布面（真源 / 绑定世界书 / 卡内副本）的运维纪律；
- pull / push 拆分回填的 sync 机制。

### 7.2 必须逐项修改

| 项 | 改动内容 |
|---|---|
| loader URL / 端口 / 目录名 | 连改四处：角色卡正则矩阵、loader guard 特征串、正文读取器 loader-only 判断、构建输出路径 |
| 入口正则的"脚本名" | 与 loader guard 的名称识别条件同步 |
| 事件脚本 import 语句 | 指向新的 `dist/<事件脚本名>/index.js` |
| 自定义事件名前缀 | 如 `<卡名>:directVariableWriteDone`、全局初始化信号名 |
| `stat_data` 字段树 | 按新题材设计（世界时钟单位、位置层级、角色属性、事件系统三态） |
| 世界书条目名前缀 | 如 `<新线路>事件条目-` |
| 事件 schema 的字段值 | 地点层级、时间格式、参与人物、差分路径 |
| 三份基础规则条目 | `变量指导`（字段路径与只读区）、`输出提示词`（注入模板）、`cot`（叙事约束）全部重写 |
| 地点派生规则的级数 | 若新世界的地理层级不是三级，需调整"前两级派生传闻范围"的常数 |
| 前端 UI / 面板 / 样式 | 完全重做 |
| 发布开关 | 内联快照正则 vs loader 正则的启停切换 |

### 7.3 新卡搭建的推荐顺序

1. **先定 `stat_data` 字段树**（这是所有层的公共契约）。
2. 搭最小可运行的伪同层链路：loader 正则 + 空白前端 + 隐藏楼层脚本 + loader guard。
3. 接 ERA 框架，跑通"前端写初始变量 → `era:writeDone` → 读回状态"这条握手。
4. 写 `变量指导.txt`，跑通 AI 输出 `<Variable*>` 块 → 落库 → 前端刷新。
5. 写 `输出提示词.txt` + `cot.txt`，跑通剧情生成与正文/选项解析。
6. 再上事件系统：先写 2~3 条事件条目验证 loader 前缀识别与时间/地点触发，再补参与快照、偏离判定、归档。
7. 最后做 UI 打磨与提示词预算调优。

### 7.4 最容易踩的结构性误区（贴在显眼处）

1. "只剩最后一楼"是**视觉事实**，不是存档事实。
2. "最新 assistant 楼层" ≠ "最近剧情正文"——它可能只剩 loader 壳或变量补丁。
3. `仅格式显示 = true` **不代表**不参与编辑确认链；`run_on_edit` 对 loader 型正则是高危项。
4. 事件脚本**不是**前端的附属模块，只改 React 页面覆盖不了全部状态变化来源。
5. 只改世界书真源而不 push / 不重新打包，运行时**完全不会变**。
6. 必填字段（尤其 `事件概要`）缺失会导致**整批普通事件静默跳过**，而登场事件仍能加载——症状具有极强误导性。
7. 不要把所有字段都走 ERA write 回流最后一条 AI 消息，否则消息体积无限膨胀。

## 8. 已知未完成 / 可改进方向（复刻时可考虑一开始就做对）

1. **世界书热更新**：当前只在初始化和 `CHAT_CHANGED` 时重读事件定义，未监听 `WORLDINFO_UPDATED` / `WORLDINFO_ENTRIES_LOADED`。可在新卡中直接加上这两个监听。
2. **事件检查的线性成本**：事件检查与世界书扫描随条目数线性增长。可在新卡中提前做按时间/地点的索引分桶。
3. **参与事件差分仍走 ERA write**：这会让最新 AI 消息继续增长。新卡可考虑把更多差分也改为 direct write。
4. **世界推衍未实现**：当前"世界事件区"只是**可靠归档 + 受控上下文注入**，不是完整世界模拟器。额外 API 的后续事件推衍、后台人物自主推衍属于后续阶段。若新卡需要，应在架构上预留独立的推衍模块（与 checker / operations 并列）。
